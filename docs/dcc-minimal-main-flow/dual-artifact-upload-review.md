# DCC 双文件上传设计Review记录

## 1. Review结论

专项设计满足用户确认的三点：可编辑版本非必填、不可编辑版本必填、平常在线浏览使用不可编辑版本。需要优化的重点不是页面文案，而是把旧的“源文件、原始文件、图纸PDF、发布件”混用合同切开，否则后续实现容易继续把同一个ticket传给多个字段，导致源文件缺失、PDF缺失和浏览回退无法被测试发现。

本轮已按以下review意见同步优化设计文档、主方案、技术设计、验收计划和变更记录。

## 2. Review发现与优化

| 编号 | 发现 | 风险 | 优化 |
|---|---|---|---|
| R01 | 原技术设计写“新上传/换稿只收真实PDF” | 与“可编辑版本可选”冲突，开发可能误删源文件能力 | 改为“浏览版PDF必填、可编辑源文件可选”，并新增专项文档 |
| R02 | 现有前端把 `originalUploadTicket` 和 `sourceUploadTicket` 指向同一文件 | 无法区分可编辑源文件和不可编辑浏览版 | 新合同使用 `readOnlyUploadTicket`、`editableUploadTicket` |
| R03 | 现有 `SOURCE` purpose 允许PDF | 用户把PDF放到可编辑槽位时会被错误接受 | 新增 `EDITABLE_SOURCE` 且禁止PDF；PDF只能作为 `READ_ONLY_VIEW` |
| R04 | 只说“不浏览源文件”仍可能在缺浏览件时fallback | 审批或历史预览可能泄露可编辑源文件，或把错误显示成成功 | 明确返回 `CONTROLLED_FILE_PREVIEW_ARTIFACT_MISSING`，禁止回退到 `sourceFileId`、`originalFileId` |
| R05 | `publishedFileId/stampedFileId` 与浏览版关系未定义 | 受控后到底看上传PDF还是盖章副本不清楚 | 明确未受控看 `readOnlyFileId`，受控后看盖章/发布派生件，派生缺失也不回退 |
| R06 | 只覆盖首次上传会漏掉检入 | 小版本和大版本可能继续只传源文件 | 将双文件合同扩展到所有产生新内容快照的检入 |
| R07 | 源文件可选后，下载入口容易出现空按钮或下载PDF | 用户以为拿到可编辑文件，实际拿到浏览版 | 增加源文件下载单独接口/角色、权限、缺失错误和审计 |
| R08 | 历史数据没有 `readOnlyFileId` | 自动猜测会制造错误证据链 | 历史接入必须显式补齐或保持只读，不在查询时自动修复 |
| R09 | 签名证据若仍绑定 `sourceSha256` | 可编辑源文件和审批正文可能不一致 | 设计要求签名和盖章绑定浏览版PDF哈希 |
| R10 | 仅改文档容易遗漏测试入口 | 后续实现可能没有RED/GREEN门槛 | 新增9个BDD-D场景和6个专项测试包 |

## 3. 优化后的开发切入顺序

1. 先写后端上传策略RED：`EDITABLE_SOURCE` 禁止PDF，`READ_ONLY_VIEW` 必须是真PDF。
2. 再写提交服务RED：缺 `readOnlyUploadTicket` 不写入任何业务对象；只有PDF时 `sourceFileId` 为空也可提交。
3. 实现DO、迁移和VO合同，保存 `readOnlyFileId` 与可空 `sourceFileId`。
4. 改盖章、签名和预览解析，确保所有默认浏览都使用不可编辑链路。
5. 改前端两个上传槽位和payload；再写表单静态/组件测试。
6. 最后补源文件下载入口、权限、审计和详情页状态。

这个顺序能先守住数据合同和证据链，再做交互优化；不会先做页面按钮却让后端继续混用旧字段。

## 4. 保留问题

- 第一版把不可编辑版本限定为真实PDF。如果业务以后允许图片或其他不可编辑格式，应另开需求定义预览、签名和盖章规则。
- 可编辑源文件是否需要长期保留策略、加密或水印，不在本主流程中扩展；当前只要求授权下载和审计。
- 历史数据批量迁移不在本轮文档授权内。后续开发前需只读列出旧数据分布，再决定显式迁移或只读保留。

## 5. Review后的验收门槛

- 文档中不再出现“普通新上传只收PDF”这类否定可编辑源文件的描述。
- 所有新内容快照都必须有 `readOnlyFileId` 或受控浏览派生件。
- 所有普通在线浏览路径都禁止读取 `sourceFileId`。
- 可编辑源文件缺失是正常状态，页面和接口都必须明确表达。
- 缺少不可编辑浏览版是业务错误，不能被旧字段、历史字段或自动转换掩盖。
