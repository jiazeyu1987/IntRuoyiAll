## 2. Given/When/Then 场景

| 编号 | Given | When | Then |
|---|---|---|---|
| BDD-01 | 新上传，needTraining=true，类别 trainingRequired=false，全部配置有效 | 通过真实业务服务按节点完成 | 只启动 upload key；会签 -> 批准 -> 培训 -> 分发 -> 文控审核 -> ACTIVE，不能被类别开关关闭培训 |
| BDD-02 | 新上传，needTraining=false，类别 trainingRequired=true | 批准通过，之后完成其余步骤 | upload key 直接进入分发；零培训任务/人员记录/通知；文控通过且效果成功才 ACTIVE |
| BDD-03 | 当前有正式版，升版 needTraining=true | 完成新版全部节点 | 使用 revision key，顺序同含培训上传；通过前旧版 ACTIVE，通过后新旧版本及 Master 一致切换 |
| BDD-04 | 当前有正式版，升版 needTraining=false | 完成新版全部节点 | 使用 revision key，跳过培训但不能跳过分发；旧版只在最终生效成功时失效 |
| BDD-05 | 受控文件原上传曾 needTraining=true；作废配置有效 | 发起及完成作废 | 只使用 obsolete key；会签 -> 批准 -> 文控审核 -> OBSOLETE；零培训/分发记录；伪造培训字段被拒绝 |
| BDD-06 | 矩阵有生产、质量，质量未配置负责人 | 启用配置或正式创建会签任务 | 明确质量部负责人缺失；不创建生产部单独任务；首次送审整事务回滚 |
| BDD-07 | 部门保存请求包含多值/数组，或解析返回同部门多条冲突结果 | 保存或创建任务 | 明确多负责人/合同错误；不先去重、不选择第一人、不落半份快照；正常单值主数据不伪造多人场景 |
| BDD-08 | 分别构造部门停用、负责人停用/删除/跨租户或无签名资格 | 预检及创建会签任务 | 按部门/人员给具体错误；不自动补管理员、上级负责人、申请人，不静默过滤 |
| BDD-09 | 预览显示负责人 A，尚未创建会签任务 | 管理员改为 B，之后真正创建任务 | 新任务 assignee=B，快照记录创建时配置，A 无此任务；矩阵部门集合仍来自本轮配置快照 |
| BDD-10 | 会签任务已创建且快照为 A | 负责人改为 B，A/B 分别尝试办理 | A 保持账号和签名资格时可办理；B 不能凭新负责人身份办理；历史仍显示 A |
| BDD-11 | 任务批次已提交为 A，但客户端未收到响应 | 改为 B 后用同一创建/提交键重试 | 只返回原任务与 A 快照，无重复任务、无覆盖；另测首次创建回滚后重试应取当时的 B |
| BDD-12 | 生产部和质量部负责人是同一用户 A | 创建并逐一办理部门会签 | 两份带不同 departmentId/obligationId 的任务；完成一份仍待会签；两份独立签名后才进入批准 |
| BDD-13 | 两部门不同负责人并行会签 | 一人同意，另一人分别待办/同意/驳回 | 待办时不推进；全部同意只推进一次；任一驳回结束本轮并取消余下待办，证据保留 |
| BDD-14 | 申请人恰为某部门负责人，BPM 有通用跳过同人策略 | 发起流程及调用通用审批/转办/加签入口 | 本人会签义务仍存在；不得自动通过；新三 key 都执行 DCC 签名/权限合同，禁止绕过冻结分配 |
| BDD-15 | 新请求篡改负责人/部门、任意 key，或缺 needTraining/传字符串/null | 从上传、工作稿送审、作废和旧入口提交 | 服务端拒绝越权或非法合同；缺部署/动作绑定错误报错；不转向另一个可用 key；培训变量与持久事实不一致不得推进 |
| BDD-16 | NEW 返工、受控后大版本及小版本修订三种正式来源 | 分别检入、打开送审弹窗并提交培训值 | NEW 返工仍为 upload；各受控修订为 revision；小版不直效（按 D05）；升版 checkbox 必填合同且纳入幂等载荷 |
| BDD-17 | 分发必经；分别缺分发计划、类别 distributionRequired=false、含培训但无人员 | 预检/进入节点 | 缺计划或空培训人员明确阻断；false 不能跳分发；合法冻结计划可用；生成培训计划不提前创建分发通知 |
| BDD-18 | 多人培训，有明确最低时长，文件尚未生效 | 一人时长不足确认、部分人完成、最后一人完成、重复确认 | 不足拒绝；未全员完成不分发；最后完成只推进一次；重复完成幂等；培训任务能读取冻结 PDF，不能冒充 ACTIVE |
| BDD-19 | 电子、纸质、混合介质三组有效计划 | 分别只发消息/只打印/发放人整单登记、部分本人签收、全部签收；尝试追加接收人 | 前三者不代替本人签收；部分不进入文控；全部真实签收才推进；冻结名单不可追加/替换；待生效纸件不冒充正式受控纸件 |
| BDD-20 | 文件在会签、批准、培训或分发阶段，前序证据不足 | 调用文控通过、发布、release/activate 或伪造等待节点完成命令 | 均无提前生效副作用；节点、实例、版本和证据不符明确拒绝；通用审批同意不能替代培训确认或签收 |
| BDD-21 | 文控已通过，上传/升版最终效果执行中 | 正常执行、注入存储失败/数据库回滚，再以同事件重试 | 正常才 ACTIVE；失败显示处理失败且旧正式版可用；重试不重复签名/培训/通知/产物，时间字段不被覆盖，Master 与版本链一致 |
| BDD-22 | 作废 FormCenter 申请绑定独立 key，目标原文件 changeType=NEW/REVISION | 完成最终文控，重放事件，并注入效果失败 | 原文件按 OBSOLETE 动作处理；不误走上传/升版；效果唯一执行，失败不假作废；成功才状态/指针/名称/审计一致 |
| BDD-23 | 最终文控完成前任一人工审批阶段，或培训/分发等待期间 | 驳回或申请人撤回，再修正重提；旧回执迟到；最终审核后再尝试撤回 | 旧轮终结、待办取消、纸件收回可追溯；新轮不复用旧证据，负责人重解析；作废撤回原文件仍 ACTIVE；最终审核后拒绝撤回，只能按权限重试效果 |
| BDD-24 | 同租户同动作提交键已有成功申请 | 相同载荷重放，或修改培训值、目标版本/动作后重放 | 相同载荷返回原申请；冲突明确拒绝；不同租户不能读到该申请；不能因当前状态已推进使合法重放失败 |
| BDD-25 | 创建部门任务与负责人更新并发；另有最后两人完成、升版/作废竞争 | 用真实事务测试制造交错 | 负责人读取边界明确，批次全有或全无；节点仅推进一次；同 Master 互斥变更；不能因普通单测顺序执行而宣称并发通过 |
| BDD-26 | 部门管理员、申请人、会签人、批准人、文控、培训/分发人员及无关用户 | 分别访问配置、待办、预览、签名、下载与其他租户 | 配置/任务/签名/下载权限各自校验；负责人变更不把旧任务交给新用户；冻结负责人停用时阻断且无自动转办 |
| BDD-27 | 三动作页面与审批中心可用 | 保存配置后刷新，切换培训 checkbox，执行任务并回看 | checkbox 只在上传/升版；矩阵只选部门，负责人只读；每部门任务可见；流程预览/当前节点/详情状态一致，长部门名不遮挡操作 |
| BDD-28 | 存在旧模型历史记录、新模型各动作记录、作废 FORM_ACTION | 查询审批列表、历史与时间线 | 历史用原快照；新三 key 均可定位；作废不解析成裸文件数字 key；无双适配器重复待办，无历史补造负责人 |
| BDD-29 | 迁移首次/重复执行及旧在途不为零两种环境 | 执行正式迁移门禁、模型校验及启用预检 | schema 幂等、依赖完整、历史不回填；旧在途阻断启用；三 key/绑定独立且新合同完整，旧直效入口不能绕过 |
| BDD-30 | 提交后矩阵变更、负责人变更；冻结分发计划中的人失效 | 创建会签及后续培训/分发节点 | 会签部门来自原矩阵，负责人取任务创建时；分发计划不被当前配置静默替换；冻结对象失效报错，预览不产生业务写入 |

BDD-16、BDD-17 至 BDD-19、BDD-23 的纸件收回及 BDD-29 的切换窗口依赖需求文档 D03-D07 默认值；若业务调整，先修改对应设计和验收，不能边实现边改口径。

## 3. 严格 TDD 与定向验证

生产实现应在实施任务中逐批记录：场景、预期失败、实际 RED 输出、最小实现、GREEN、相邻回归及证据路径。不得将文档检查写作 RED/GREEN，也不得靠测试名称或代码字符串就宣称流程可执行；已完成的开发期证据仍需与本验收计划的真实 DB、正式 Flowable、真实页面 E2E 和收尾门禁分开记录。

| 层级 | 测试内容 | 既有位置及实施要求 |
|---|---|---|
| 部门/路线单元测试 | 基数、停用、租户、只存部门、动作配置隔离 | 扩展 DccControlledFileApprovalRouteAssigneeResolverTest、DccControlledFileRouteReadinessServiceTest、DccCategoryApprovalMatrixAdminServiceImplTest；新增任务创建快照聚焦测试 |
| BPM 引擎集成 | 三份真实定义、五路径、MI 同人多部门、严格候选、签名及完成门禁 | 使用隔离测试引擎部署正式 BPMN；不得用 mock 完成事件替代网关与多实例验证 |
| 业务集成 | 培训/分发聚合推进、作废 FormCenter 效果、版本激活与失败重试 | 扩展 DccTrainingAssignmentAckServiceTest、DccTrainingConcurrentAcknowledgementTest、DccDistributionReceiptServiceImplTest、DccPaperDistributionAckServiceTest、DccControlledFileFinalizationServiceImplTest、DccControlledFileObsoleteFormEffectExecutorTest |
| 数据库合同 | 唯一性、事务锁、并发、schema 首次/重复执行及历史保护 | 隔离测试库；跨模块事务与真实 MySQL 行为必须有实测，H2/替身不能证明生产库锁和 DDL |
| 前端合同/组件 | checkbox、工作稿字段、部门只读预览、三 key、错误/阶段/权限 | 定向更新现有 dcc-route-fixed-approval-policy、dcc-review-matrix、dcc-working-iteration-submit、training/distribution 合同，增加本需求行为测试 |
| 真实页面 E2E | 五条正常路径及关键异常、权限、负责人变更 | 仅取得当轮明确授权后执行；实施任务已记录真实页面登录、上传预览和升版工作稿检入，但提交及审批链因测试路线/负责人配置未就绪而阻断，不能视为完整 E2E 通过 |

测试文件定位：后端 DCC 测试位于 `IntRuoyiBackend/yudao-module-dcc/src/test/java/cn/iocoder/yudao/module/dcc/`；BPM 测试位于 `IntRuoyiBackend/yudao-module-bpm/src/test/`；前端合同位于 `IntRuoyiFronted/scripts/`、`IntRuoyiFronted/tests/e2e/`。具体测试命令以实施时存在的类/脚本为准，不把尚未创建的测试类标作已运行。

后端定向 Maven 带 `-am`，包含变更模块依赖；指定测试时说明 `surefire.failIfNoSpecifiedTests` 的使用边界并核对实际非零执行数。前端使用 pnpm，类型检查及定向合同按仓库规范运行。旧四阶段断言若确为本次需求替代，应更新合同并保留签名、权限、双文件、版本、幂等等相邻回归，不能删断言冒充 GREEN。

## 4. 后续真实页面验收方法

遵循实施当轮最新 AGENTS 和 E2E 规则，所有被验收动作必须由 Playwright 在真实前端完成，包括管理员配置负责人/矩阵、上传/升版/作废、各账号审批、阅读确认、分发签收、撤回/重提。使用指定测试租户、真实测试账号与任务自有业务数据；凭据只按运行环境取得，不写入本开发文档。

准备任务自有部门和测试负责人，避免变更真实生产/质量负责人。测试账号必须具备对应正式岗位、签名图片与授权；缺失时用页面按权限配置或如实阻断，不用 admin 代签。仅允许规则授权的只读方式辅助核验，不用 fetch、apiGet、直接业务 API 或数据库写入执行任何验收动作，也不把浏览器注入状态视为真实办理。

证据至少包含五条实际流程顺序、三个不同 key/定义身份、部门任务快照及签名、培训/分发记录、文控前未生效与完成后生效、作废原文件状态和失败场景。明确区分静态设计推导、单元测试、集成测试、页面 E2E；未执行的一层保留未执行状态。
