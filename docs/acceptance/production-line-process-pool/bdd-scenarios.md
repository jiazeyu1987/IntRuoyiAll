# 生产一线报工工序池 BDD 场景

## Purpose and Scope

本文档覆盖本次线程中已确认、且用户要求可以先推进的 6 个功能点：

- F1：工序池基础模块。
- F2：报工 + 记录本一体提交模块。
- F3：固定模板录入模块。
- F4：设备账号内切换员工模块。
- F7：生产工单 FIFO 分配基础逻辑。
- F8：工序池时间轴 / 甘特图查询模块。

本文档只定义行为验收场景，不代表已经进入实现。审核副本上下限修正、原始记录修改重签名属于相关约束，本轮 6 个功能点必须保留接口和状态边界，但不在本文档中作为独立实现模块展开。

## Review Gate

6 个功能点的 BDD 必须同时满足以下 21 条需求门禁：

| ID | 需求门禁 |
| --- | --- |
| R01 | 尽量复用现有报工、记录本、eDHR、生产工单能力，不新增孤立系统。 |
| R02 | 一线入口是“报工”，同时也是记录本入口。 |
| R03 | 一线员工只填当前工序相关简单数据。 |
| R04 | 员工 UI 固定几类模板，不做无限自由配置。 |
| R05 | 生产模板至少包含上一个工序输入数量、设备/设备参数、输出数量、损耗数量。 |
| R06 | PQC 第一版只判定检测成功或失败，且必须进入工序池过程检验记录。 |
| R07 | 提交时间由服务端自动生成，员工不手填。 |
| R08 | 每次提交必须有唯一电子签名，签名主体是实际员工。 |
| R09 | 有限设备使用设备账号或共享操作账号，账号绑定 `X >= 1` 个工艺路线。 |
| R10 | 设备账号内切换的是用户，不是切换系统账号。 |
| R11 | 员工切换到自己时不做额外身份验证，电子签名代表身份。 |
| R12 | 账号只能切换绑定路线下工序；工序只能切换绑定员工。 |
| R13 | 工艺路线可配置，但一线实际提交不受路线前后置顺序限制。 |
| R14 | 必须新增正式工序池，不能用现有 `mes_pro_feedback_surplus_pool` 替代。 |
| R15 | 提交到工序池的统一对象为“工序池提交事件”。 |
| R16 | 工序池提交事件必须保留原始 payload、报工来源、记录本来源、员工、账号、设备、生产工单、路线、工序、模板类型。 |
| R17 | 同一工序允许多人、多次、分片填写，工序完成按累计数量判断。 |
| R18 | 一线提交不按上下限拦截原始值；审核副本才按上下限处理，原始和修正值都要保留。 |
| R19 | 原始记录修改必须留日志并重新电子签名；已 FIFO 分配的记录或数量片段不能修改。 |
| R20 | FIFO 只面向生产工单，按生产工单计划开始时间排序。 |
| R21 | 工序池时间轴 / 甘特图按提交时间展示每天谁提交了什么，且视图只读可追溯。 |

## Feature Scenarios

### F1 Scenario: 新增工序池提交事件

Given 生产工单、工艺路线、路线工序、实际员工、设备账号、设备、模板类型、报工来源和记录本来源均有效  
When 一线组合提交成功并写入工序池  
Then 系统创建一条“工序池提交事件”  
And 事件保存原始 payload、生产工单、工艺路线、工序、实际员工、设备账号、设备、模板类型、报工来源 ID、记录本来源 ID  
And 事件保存服务端提交时间和唯一电子签名  
And 事件不得以 `mes_pro_feedback_surplus_pool` 作为主记录

### F1 Scenario: PQC 过程检验进入工序池

Given PQC 人员针对某生产工单和工序录入过程检验结果  
When PQC 结果为检测成功或检测失败  
Then 系统把结果保存为对应工序池的过程检验记录  
And 该记录关联工序池提交事件、实际员工、电子签名和服务端提交时间  
And PQC 记录不得脱离工序池成为旁路数据

### F2 Scenario: 报工和记录本一次组合提交

Given 设备账号已登录，实际员工已在账号内切换到自己，当前工序、模板、生产工单、记录本模板、工序池上下文和电子签名均有效  
When 员工在报工入口填写输入数量、设备参数、输出数量、损耗数量并点击确定提交  
Then 系统在同一事务内完成报工、写入记录本原始条目、写入记录本事件并创建工序池提交事件  
And 返回或可查询 `feedbackId`、`recordbookEntryId`、`processPoolEventId`  
And 三者具有正式来源关联

### F2 Scenario: 同一 payload 拆分报工信息和记录本信息

Given 页面 payload 包含生产工单、工序、输出数量、损耗数量、上一个工序输入数量、设备和设备参数  
When 后端处理组合提交  
Then 输出数量、损耗数量等报工字段进入报工链路  
And 上一个工序输入数量、设备参数和原始模板 payload 进入记录本和工序池事件  
And 系统不得用备注、标签或文本匹配替代正式关联字段

### F3 Scenario: 固定生产模板只展示当前工序简单字段

Given 员工已选择当前授权工序并加载生产模板  
When 页面渲染一线报工 UI  
Then 页面显示上一个工序输入数量、设备、设备参数、输出数量、损耗数量  
And 页面隐藏与当前工序无关的完整批记录字段  
And 页面不展示可编辑提交时间

### F3 Scenario: 固定模板不拦截原始超限值

Given 某设备参数字段审核范围为 `20~40`  
When 员工在一线模板输入 `50` 或 `10` 并提交  
Then 前端不得阻止提交  
And 后端不得在一线提交阶段裁剪成 `40` 或 `20`  
And 原始 payload 保留员工输入值  
And 上下限修正仅由审核副本模块处理

### F3 Scenario: PQC 简化模板

Given 当前员工加载 PQC 简化模板  
When 页面渲染 PQC 填报 UI  
Then 页面只提供检测成功和检测失败两个结果  
And 提交 payload 包含生产工单、工序、实际员工、模板类型和 PQC 结果  
And 该 payload 能进入对应工序池过程检验记录

### F4 Scenario: 设备账号路线和工序切换

Given 设备账号绑定工艺路线 `R1` 和 `R2`  
And `R1` 包含工序 `P10`、`P20`，`R2` 包含工序 `P30`  
When 一线入口加载可切换工序  
Then 系统只返回 `P10`、`P20`、`P30` 及其路线来源  
And 不因为路线前后置顺序限制选择  
And 未绑定路线下工序不得被选择

### F4 Scenario: 工序内切换实际员工

Given 当前工序 `P10` 绑定员工 `E1001` 和 `E1002`  
And 员工 `E2001` 未绑定 `P10`  
When 操作员在设备账号内切换实际员工  
Then 系统只允许选择 `E1001` 或 `E1002`  
And 登录账号不变化  
And 不要求密码、验证码、扫码或二次身份验证  
And UI 按实际员工和当前工序重新加载

### F4 Scenario: 提交时留痕身份和现场上下文

Given 设备账号 `device_account_A` 登录在设备 `EQ-01` 和工作站 `WS-01`  
And 当前实际填写员工为 `E1001`  
When 员工完成电子签名并提交  
Then 工序池提交事件保存登录账号、实际填写员工、电子签名员工、设备、工作站、路线、工序和模板编号  
And 电子签名员工必须等于实际填写员工

### F7 Scenario: 生产工单按计划开始时间 FIFO 分配

Given 工序池中工序 `P1` 有可分配数量 `100`  
And 生产工单 `WO-A` 计划开始时间早于 `WO-B`，需求数量均为 `60`  
When 系统执行 `P1` 的 FIFO 分配  
Then 系统先满足 `WO-A` 的 `60`  
And 只把剩余 `40` 分配给 `WO-B`  
And 分配目标必须是生产工单，不得写入排产目标字段

### F7 Scenario: 分配流水追溯到事件和数量片段

Given 工序池提交事件 `E1` 产生可分配片段 `S1=50`  
And 工序池提交事件 `E2` 产生可分配片段 `S2=40`  
And 生产工单 `WO-A` 需要 `70`  
When 系统执行 FIFO 分配  
Then 系统生成 `E1/S1 -> WO-A = 50` 和 `E2/S2 -> WO-A = 20` 两条明细  
And 每条明细可追溯来源工序池、来源事件、来源数量片段、目标生产工单、目标工序和分配数量

### F7 Scenario: 分配后禁止修改

Given 工序池数量片段 `S1` 已 FIFO 分配给生产工单 `WO-A`  
When 用户尝试修改影响 `S1` 数量、质量状态或可分配状态的原始记录字段  
Then 系统拒绝修改  
And 返回明确原因  
And 不允许通过重新电子签名绕过已分配禁止修改规则

### F7 Scenario: 多人多次提交按数量累计完成

Given 生产工单 `WO-A` 的工序 `P1` 要求数量为 `100`  
And 员工 `U1`、`U2` 多次提交形成可分配数量 `30`、`40`、`30`  
When 系统计算 `WO-A/P1` 的工序完成状态  
Then 三次提交作为独立原始事件保留  
And 累计数量达到 `100` 后工序判定为完成  
And 完成判断不依赖是否由同一个人填写

### F8 Scenario: 按天查看工序池提交事件

Given 工序池存在多条不同员工、工序、设备、模板类型的提交事件  
And 每条事件都有唯一提交时间和唯一电子签名  
When 管理人员按某一天打开时间轴或甘特图  
Then 系统按提交时间展示当天事件  
And 每条事件显示实际填写员工、电子签名员工、登录账号、工序、设备、模板类型、生产工单和提交摘要

### F8 Scenario: 时间轴多条件过滤和只读追溯

Given 工序池中存在生产模板、损耗、设备参数和 PQC 过程检验事件  
When 用户按日期、员工、工序、设备、模板类型、生产工单组合过滤  
Then 系统只返回匹配事件并按提交时间排序  
And 事件详情可追溯 FIFO 分配状态、审核副本状态和修改历史  
And 时间轴不提供原始记录修改、审核副本调整或 FIFO 分配写操作

## Failure Scenarios

### Scenario: 缺少正式前置条件时整体失败

Given 组合提交缺少生产工单、工序、记录本模板、工序池上下文、实际员工绑定、设备账号授权、固定模板或电子签名中的任一项  
When 员工点击确定提交  
Then 系统返回明确失败原因  
And 不写入报工、记录本或工序池事件  
And 不使用默认模板、空工序池、默认员工、模拟成功或静默降级

### Scenario: 生产工单缺少计划开始时间时阻塞 FIFO

Given 候选生产工单缺少 `plannedStartTime`  
When 系统尝试执行 FIFO 分配  
Then 系统拒绝本次分配并不写入分配流水  
And 不使用创建时间、工单号、当前时间或空值排序替代

### Scenario: 签名员工与实际员工不一致时失败

Given 当前实际填写员工为 `E1001`  
When 提交请求携带 `E2001` 的电子签名  
Then 系统拒绝提交  
And 不写入报工、记录本或工序池事件

## Boundary Scenarios

### Scenario: 批记录术语边界

Given 当前工序同时配置正式逐工序批记录表单、表单槽位 `formBindings` 和工序开始配置  
When 一线组合提交需要保存批记录或记录本来源上下文  
Then 正式批记录表单来源只允许读取工序设置中的逐工序批记录表单绑定  
And 不允许用 `formBindings`、默认 `MAIN` 或工序开始配置替代

### Scenario: 工艺路线只作为上下文和权限边界

Given 工艺路线存在前后置关系  
When 当前账号、工序、员工、模板和签名均有效  
Then 一线提交、模板打开和工序池事件创建不因前置工序未完成被阻断  
And 路线仍作为上下文、权限范围和追溯依据保存

### Scenario: 视图不改变业务状态

Given 用户打开工序池时间轴或事件详情  
When 用户查看原始记录、PQC、FIFO、审核副本和修改历史  
Then 系统只读展示数据  
And 不允许通过时间轴接口修改原始记录、重签名、生成审核副本或执行 FIFO 分配

## Open Questions

- 组合提交采用新增接口还是扩展现有 `createFeedback/updateFeedback/submitFeedback`。
- 工序池归集维度是否包含产品、物料、批号、班次、质量状态、工作站等字段。
- 设备账号绑定路线、工序绑定员工、员工工序模板绑定的正式配置入口。
- 第一版固定模板是否只包含生产简化和 PQC 简化，是否同步包含生产分片、损耗补充。
- PQC 失败如何影响待检数量、可分配数量和 FIFO 消耗。
- 工序完成数量最终使用完成数量、合格数量、PQC 通过数量还是可分配数量。
- 同一 `plannedStartTime` 的生产工单二级排序规则。
- 原始记录修改原因、审批要求和字段级修改历史粒度。
- 审核副本状态枚举和展示粒度。

## Test Blockers

- 缺少新增正式工序池模型和工序池提交事件模型。
- 缺少电子签名正式接口和签名员工校验契约。
- 缺少记录本、报工、工序池之间的正式来源关联字段。
- 缺少测试租户、设备账号、实际员工、设备、工作站、生产工单、工艺路线、工序、记录本模板和固定模板数据。
- 现有记录本 `min/max` 若仍在一线提交阶段拦截原始值，必须先拆分结构校验和审核限值规则。
- 生产工单 `plannedStartTime` 为空时业务规则未确认，FIFO 分配必须阻塞。
