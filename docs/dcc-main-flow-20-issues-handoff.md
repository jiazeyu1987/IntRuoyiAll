> 本版替代此前交接文档中的流程、修复方向和验收标准。接收电脑请按本版处理，不再执行旧版“恢复工作稿、独立发布、退回、转办、加签”的建议。
> 本次只修订文档，没有修改生产代码。原问题被业务取消不等于代码已修复。

## 修订依据与交接边界

用户最新业务回复：批准即生效并上传盖章PDF存默认目录；先选模板文件夹再上传；名称与内容查看权限分开；上传不能升版但允许初始版本；仅大版本变化通知有权限人员并由其决定关联新版；驳回重新上传，无退回、转办、加签。

统一文件名称为“受控文件”，审批/生效进度单独描述。旧代码内部枚举不得仅改显示名就宣称完成业务调整。
本版不考虑培训、分发。接收方按其实际源码复核并实施BDD/TDD；不得把旧静态结论或过去测试PASS当成新业务已完成。
原DCC-MAIN-01至20保留用于追溯，07、08、17取消旧功能修复方向，11移除旧上传升版设计；其余按新规则保留或改写。不要把这些编号对应到旧DCC-STATIC编号。
本文自包含，复制本文件即可交接，代码路径使用仓库相对路径。本轮未执行产品回归、E2E、Git提交推送、服务或数据库操作。
源码附录仍是上一轮整理基线7393f67315e1ae5adf53fe9c4239da732d0e0efe的历史定位索引，未在本轮重做源码审计或更新指纹；方法可能被后续代码修改，必须重新定位。

## 已确认的业务规则

- B1：文件最终批准即生效；必须上传盖章PDF并存储进入默认目录，取消独立发布动作。
- B2：上传文件前先选择模板文件夹。
- B3：名称查看权限与内容查看权限分离，内容权限包含名称权限；仅有名称权限时可索引、搜索、关联，不能查看详细内容。
- B4：上传不走升版路线，可填写初始版本号；已有文件版本变更只能通过检出、检入操作。
- B5：已有文件关联在大版本变化时通知有权限的人，由接收人决定是否关联新版本；小版本变化不通知，不自动切换关联。
- B6：驳回后重新上传文件；取消退回、转办、加签。
- 术语：统一称“受控文件”，审批或生效进度单独表达，不使用“工作稿”“工作版本”“现行版”作为业务名称。

## 仍需确认的实施细节

这些细节不阻碍文档修订，但接收方不得把下述建议当成业务已确认的配置或数据库设计。

| 待确认项 | 已确定边界 | 尚待业务确定 |
|---|---|---|
| 模板文件夹 | 必须先选后上传 | 是现有项目模板分类还是独立文件夹对象；具体层级 |
| 默认目录 | 批准时自动使用有效正式默认目录 | 是否由模板文件夹映射；映射在哪维护及是否按类别限定 |
| 审批路线 | 最终批准即生效，仅通过/驳回 | 原固定四环节是否保留；固定审核会签是否保留；并非把“取消加签”等同于“取消会签” |
| 初始与后续版本 | 初始版本可填写，变更走检出检入 | 格式、默认值、大小版本递增规则、检入时如何选择 |
| 大版本通知 | 只对大版本变化通知，不自动换关联 | 在检入还是批准生效后发送；建议生效后，但尚未确认 |
| 通知接收人 | 有权限的关联处理人员 | 负责人、可修改关联人员或其他正式权限群体；如何去重 |
| 驳回重新上传 | 必须新上传并重新审批，保留驳回事实 | 文件编号、版本号、逻辑身份及原申请链如何继承；不能误开普通上传升版 |
| 名称与内容边界 | 名称权限不得获得详细内容 | 可索引的编号/版本/其他元数据白名单、内容搜索摘要及关联操作授权细则 |

## 修订后主流程（1—90）

1. 本流程按最新业务回复编写，是目标规则，不代表当前代码已经实现。
2. DCC统一使用“受控文件”名称，另外显示审批、生效等进度。
3. 登录正确企业或租户，使用具备项目维护权限的账号。
4. 进入“基础数据／DCC项目代码”，新增项目。
5. 填写项目名称、项目代码及必要业务资料。
6. 同一项目名称与项目代码组合不得重复。
7. 按需要填写负责人、工程师、类别等项目信息。
8. 需要关联产品时，维护正式产品关联，区分项目代码与产品编号。
9. 将项目启用，使有权限的人员可以选择。
10. 配置项目负责人和文件编制权限。
11. 负责人姓名文本不能代替账号授权。
12. 配置文件分类及其对应的正式文件类别。
13. 配置项目所需的模板文件夹。
14. 模板文件夹的具体层级与现有模板如何对应，实施前需确认。
15. 为模板文件夹配置正式默认存储目录。
16. 默认目录必须有效，不能缺失后临时猜测目录。
17. 配置模板中的文件名称及允许上传的文件范围。
18. 同一分类内的模板文件名称不得重复。
19. 名称保存前清理首尾空格，保持显示和校验一致。
20. 模板分类失效时，管理员应能看见原因并修正。
21. 保存模板，并在项目中查看配置结果。
22. 配置正式审批路线，明确各审批环节及办理人员。
23. 固定审核会签是否保留及具体环节，实施前确认。
24. 审批办理动作仅保留通过和驳回。
25. 不设置退回、转办、加签操作入口。
26. 审批人员需要有效账号、审批资格、岗位及电子签名条件。
27. 为文件分别配置名称查看权限和内容查看权限。
28. 内容查看权限同时包含名称查看权限。
29. 仅有名称权限的人可以查找文件，但不能查看详细内容。
30. 编制、审批及关联变更权限分别校验，不能以查看权限代替。
31. 上传人员进入DCC上传，选择项目。
32. 系统加载该项目可用的模板文件夹。
33. 先选择模板文件夹，再选择要上传的源文件。
34. 未选有效模板文件夹时，不能上传。
35. 系统按模板文件夹确定文件归属和默认目录配置。
36. 选择模板允许的文件名称，核对对应类别。
37. 填写文件编号，并检查同一逻辑身份是否已经存在。
38. 首次上传用于新建文件，不提供上传升版路线。
39. 已有同身份文件时，不能通过上传入口创建新版本。
40. 初次上传允许填写初始版本号，不强制所有文件从A/1开始。
41. 初始版本号须符合明确的编号规则，具体格式实施前确认。
42. 核对产品编号及来源，页面与保存结果必须一致。
43. 按需要填写提交备注等资料。
44. 生效以最终批准为准，不另选日期来推迟或提前自动生效。
45. 如需关联文件，打开关联文件选择入口。
46. 名称权限允许索引、搜索和发现可关联的文件。
47. 只有名称权限时，不展示正文、详细内容或正文预览。
48. 有内容权限时，可按授权查看内容及文件名称。
49. 建立关联还须满足关联操作权限和业务范围。
50. 选择要关联的具体文件版本，保存其版本身份。
51. 候选文件较多时，应能通过分页或搜索找到后续文件。
52. 选择源文件，核对文件名称与格式。
53. 源件可使用系统正式支持的Word、Excel、PDF或工程图纸格式。
54. 工程图纸源件同时提交对应PDF，便于有内容权限的人员审阅。
55. 等待本次文件上传完成，检查结果与当前选择一致。
56. 删除或换文件时，正确清理未绑定的上传凭证。
57. 上传未完成或失败时，不能提交成使用旧正文的文件。
58. 提交前校验模板归属、编号、初始版本、附件和审批资格。
59. 提交后保存本次文件及初始版本，并记录提交人和时间。
60. 不要求用户先进入“工作稿”页面再另行启动审批。
61. 提交审批的具体版本与正文、配套PDF保持一致。
62. 审批期间，该版本内容锁定，不能被检出修改。
63. 审核人员按正式审批路线处理当前文件。
64. 每次审批核对当前办理人、文件身份及实际审批状态。
65. 具备内容权限的审批人员才能查看本次送审内容。
66. 审批通过时填写意见并完成规定的电子签名。
67. 批准意见、签名与审批记录关联到具体版本。
68. 配置中的必需审批人失效时，应明确阻止少签通过。
69. 任一环节驳回时，本次审批结束并保留原因和记录。
70. 驳回不会把任务退回某个前序节点。
71. 申请人查看驳回结果，重新上传修正后的文件。
72. 重新上传必须提交新文件，不能直接重用原文件一键通过。
73. 重传与原申请的关联、编号及版本继承规则，实施前确认。
74. 驳回重传重新进入审批，历史驳回记录不得被覆盖。
75. 最终批准前，由有资格的人员上传盖章PDF。
76. 系统校验盖章PDF内容、用途、上传人和目标版本归属。
77. 最终批准使用正式默认目录，不再让用户临时选择存入目录。
78. 盖章PDF和默认目录有效且存储成功，才能完成最终批准生效。
79. 最终批准即生效，没有额外待发布或人工发布操作。
80. 生效失败必须显示真实原因，不能仅把状态改为已生效。
81. 生效的文件统一称为“受控文件”，不称“现行版”。
82. 需要修改已有文件时，有权限的人员通过检出取得编辑权。
83. 修改后通过检入提交内容，并按规则确定小版本或大版本变化。
84. 大小版本具体编号规则和选择方式，实施前确认。
85. 检入保留旧版本及修改说明，新版本仍需最终批准才生效。
86. 小版本变化不触发关联文件的大版本变更通知。
87. 大版本变化按确认的通知时点告知有权限的关联处理人员。
88. 已有文件关联仍指向原先选定版本，不自动切到新版。
89. 接收人决定是否关联新版本，确认时复核权限并保存变更记录。
90. 浏览和搜索始终分别检查名称与内容权限，切换目录和版本不串数据。

这些是新业务验收要求，不能只修复原20个局部问题便宣称完成。

| 规则 | 正向验收 | 反向及完整性验收 | 对应处置 |
|---|---|---|---|
| B1 批准即生效 | 合法PDF和默认目录存储成功后最终批准即生效 | 无待发布/人工发布按钮；存储失败不误报生效；重试不重复批准或覆盖签名 | 01、02、08、12、19 |
| B2 模板先于上传 | 先确定有效模板文件夹再上传 | 未选择/失效拒绝；切换文件夹不串用附件、类别、权限或默认目录 | 10、12、13、20 |
| B3 名称与内容分离 | 内容权限包含名称；仅名称权限可检索、索引、关联 | 详细内容、预览接口、源件、下载直链及内容摘要均防越权；关联写权限单独校验 | 14、16、19 |
| B4 上传新建与版本变更分开 | 初始版本可填写；大小版本均通过检出检入形成 | 无上传REVISION路线或独立升大版绕行；审批锁定；新版本批准前不替代已生效内容 | 03、04、05、09、11、20 |
| B5 大版本通知与人工关联 | 到确认的触发时点，仅大版本变化通知有权限人员，由其决定关联新版 | 小版本不通知；忽略通知不改关系；重复事件不重复通知；点击时复核权限，原版本关系有审计 | 新增验收N1（详见下节） |
| B6 驳回重传 | 驳回结束原审批，新上传修正文件再审批 | 无退回/转办/加签入口或后端写能力；不覆盖原记录、不允许旧票据重提冒充新上传 | 07、08、17、20，新增验收N2 |

### 新增验收N1：关联版本与大版本通知

- 原20项没有完整覆盖该新规则，必须新增正式测试，不能仅修改通知文案。
- Given 文件甲已关联乙的某个具体版本；When 乙发生小版本变化；Then 不发送大版本变更通知，甲的关联不变。
- Given 乙的新大版本达到业务确认的通知触发时点；When 系统生成通知；Then 仅发送给符合确认后接收规则的有权限人员，原关联不自动改变。
- Given 接收人收到通知；When 不处理或选择保持原关联；Then 关联保持原版本。
- Given 接收人有名称查看及关联变更权限；When 主动选择关联新版；Then 服务端核对目标版本、范围和当前授权，记录旧关联、新关联及操作者。
- 接收人没有内容权限时，通知、详情跳转和关联操作不能泄漏正文；内容权限失效后不能靠旧通知继续访问。
- 同一个大版本事件重复投递时保持幂等；通知失败可恢复，不撤销已完成的批准生效。
- 实施前确认触发时点及接收人规则；建议批准生效后通知，但不得把建议冒充业务已确认。

### 新增验收N2：驳回后重新上传

- Given 原申请已被驳回；When 用户未上传新文件，仅提交旧版本/旧票据；Then 拒绝以旧内容直接重新审批。
- Given 用户已重新上传修正文件并满足模板与权限规则；When 再次提交；Then 建立可追溯的新审批记录，保留原文件、驳回原因和原审批证据。
- 具体文件编号、版本号和版本链继承方式待确认；该重传入口不能成为普通上传升版的漏洞。
- 取消的退回、转办、加签动作须同时检查页面、审批中心、业务接口；历史记录仍可按权限只读查询。
- 已存在的审批中旧任务如何迁移/终止另行制定方案，不能批量伪造通过、删任务或改审计来适配新规则。
