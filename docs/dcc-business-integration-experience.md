# DCC 业务需求整合经验

适用范围：对照 `docs/product/dcc-final-requirements.html` 整合项目创建、正常新上传和后续位置链路。

HTML 是业务结果依据。原实现额外要求的主数据编码格式、预设文件名模板或第二个目录选择，需要按业务合同审查；不能因为代码已有门禁就添加成新业务步骤。

项目产品来源必须有正式证据。已绑定 MDM 的项目继续校验真实 MDM；批准创建的 DCC 产品使用同租户完成申请、有效项目产品关系和实际目录身份。两种 ID 分列保存，申请正文保留冻结来源，前端只展示服务端投影。声明的来源损坏时直接报错，不能回退到项目代码或任意产品。

移除多余模板限制前，应检查模板服务是否同时承担正式类型资格。项目文件名建议可以取消必选，启用叶子和唯一类别映射仍由服务器在预览、送审分别校验。前端唯一类别请求不能替代后端资格。

正常上传的名称事实来自真实原件完整名称，包括大小写和后缀。预览票据与实际源名称严格一致；切换项目或类型时清理原上下文，清理失败保留原会话并准确报错。测试应运行真实页面 handler、类型解析与正式 Mapper 边界，不能仅断言实现字符串。

验证分层记录：定向 TDD、完整类型/构建、数据库结构升级、真实页面操作分别报告。源码通过不代表运行库已升级，也不代表业务页面已验收。重叠测试轮次不相加。共享文件按阶段冻结指纹再交接，主管理独占 Git、实际库及运行服务操作。

Flowable 同一个流程 key 可以保留多个合法历史部署。新申请按租户选择最新定义，最新定义停用时明确拒绝，不能因 active 查询返回多个结果而手改历史定义，也不能回退旧部署。精确 definition ID 的历史实例仍按原定义追溯。

会签整改安排只适用于升版。当前任务的实际流程定义决定适用性，不能用文件初次上传时保存的 key 判断后来的作废或升版任务。新上传和作废不加载或提交整改安排，电子签名、部门负责人和真实办理轮次校验照常保留；升版读取失败必须明确阻止提交。

受控、生效和下发分别核验正式日期。真实页面受控成功不能代替下发完成，分发记录存在也不能代替接收人已签收。电子签名提示须分别描述上传/升版完整流程与作废批准结束，不沿用“文控批准直接生效”的旧文案。

KeepAlive 详情组件离开路由时仍可能收到参数变化。每个读取入口都应冻结合法文件 ID 和准确详情路由，旧请求返回或报错不能再向空 ID 或新页面补请求；不能仅在最外层 watch 中检查一次。项目与产品在详情中各自展示正式身份，不能用产品名称填项目标题。

重新打包前先停止已核归属的任务后端。运行中覆盖同路径可执行 Jar 会使旧进程后续加载嵌套类失败；即使新包包含该类，也不能继续把旧进程用于验收。新包核对后按正式启动入口恢复，再读取业务终态并明确重新操作；原失败记录保留，不自动补写或重复提交。

项目逻辑文件夹和内部存储目录必须分开。正常新上传由正式租户、文件夹、类别映射解析位置，不能取第一个叶子或借目录名接管旧目录；文件、映射、位置和审计同事务保存。历史升版和检入只继承源版本明确位置。新增派生目录要保持配置根的当前访问权益；叶子已手动配置时停止根权益投影，撤销根权限同步撤销投影。目录维护和新建映射共享实际目录锁，锁后重读类别资格，防止位置创建与配置修改互相覆盖。

统一待办接入须先核对提供者注册规则。当前一个模块只允许一个提供者，项目申请应组合到现有 DCC 提供者；申请 ID 和阶段是独立业务身份，不能充当文件或 Flowable 身份。前端同模块显示也应按真实任务来源区分项目字段和文件字段。

线下培训记录的等待节点是 ReceiveTask，不会产生 UserTask。按用户任务查询会遗漏文控工作；应在现有唯一 DCC 提供者组合以真实文件、当前 BPM 和实际等待执行为身份的原生待办，复用正式通知。上传资格、元数据读取和通知人员采用同一启用账号、文控角色、类别和文件项目范围，正文仍独立授权。审批中心读权限只决定该入口能否读取，不替代或额外限制已有业务上传资格；合法站内通知也可以直达详情。进入培训等待的通知须与批准、签名和流程状态处于同一事务，缺模板或消息失败整体回滚。上传完成后待办从正式状态自然消失，不新增培训批准、假任务编号或线上阅读时长。

文控上传培训记录使用独立类别操作 TRAINING_RECORD，不能要求成为文件内容批准人。批准类别权限仍归矩阵管理，不能为验证文控上传把文控账号塞进批准人员。配置与业务权限分别核验；工作台无权的旧阅读确认区域不请求接口，读取失败的授权区域显示错误和未知数量，不把其它成功区域清空为假0。

项目文件检出导航必须取得当前文件自己的正式位置事实。绑定项目并不能证明位置属于逻辑文件夹，内部存储映射编号也不是物理目录树节点；正常详情明确返回位置类型，项目位置附准确文件夹，历史物理位置保留原目录。错误或缺失的正式映射报错，不能借 Master 或别的版本推测位置。前端仍同时核对所选文件、Master和正式编号，再进入已有版本操作页。

只读页面应核真实路由守卫和全部可写子组件。构造了 traceability 参数不代表命中只读分支；从正文进入档案必须匹配正式入口上下文。元数据修改、会签指派等也必须遵守现有管理态门禁，不能只以账号角色判断。培训、受控和下发分别展示正式记录证据，不提示不存在的节点签名。

隔离验收使用 RAM Quartz 时，服务重启会丢调度对象。数据库任务存在、页面暂停/恢复或编辑成功都不能证明调度已恢复；缺 Trigger 的 reschedule 可能返回空值。任务模式只能显式恢复已核的那一条生效检查，核对身份、处理器、表达式及实际触发日志，不能为恢复单一任务启用共享任务全量同步。普通部署仍沿原正式启动同步。

DCC 受控状态与公共受控内容投影须在同一事务交接。未来生效的受控版本要关闭未决候选，但不占当前执行标记；生效时再将新版本置 ACTIVE、旧正式受控版本置 OBSOLETE并记录后继。只同步 DCC 指针却让公共候选留 FINALIZING，会阻止下一次合法升版。新共享动作只授予 DCC 类型，原 MES 与注册证守卫保持；源、原状态、标记、后继和事件载荷均精确核验后CAS，不能正常业务静默修正损坏投影。

已产生的投影差异经显式只读预览和原因二次确认维护。服务器重读原文件、Master、BPM、完整同租户签名、原件及生命周期事件；只更新共享投影并以实际维护时间审计，不冒充新的批准或原受控时间。JDBC 时间事实应按正式 Timestamp、LocalDateTime 类型分别精确比较，不能字符串解析、截断精度或改变数据库日期。已有有效与待生效文件的独立作废，都要从锁定文件前像选择正确共享动作，并让详情、列表、历史及审批入口采用同一业务资格。

本机少量增量迁移不能直接套用通用发布器的全日期扫描和 skip 状态写入。先冻结本次精确执行白名单，完整依赖闭包仅核当前事实；同 SHA 的旧 APPLIED 记录也不能因“跳过”而被改写 releaseTag 或更新时间。首次和重复应分开封存实际执行材料，重复只核验已有账本，不补假历史。只读备份按当前真实表数和保护旧列建立摘要，不复用旧任务硬编码数量作为新范围证明。

证据：`doc/tasks/20261001-dcc-integration-unblock/g47-root-verification.md`，及其引用的 LD01、LD02 原始交付清单和验证收据。


## 正式申请快照与正常待办入口（2026-10-06）

独立作废的部门义务必须在表单中心createInstance序列化草稿前写入；submitInstance根据已保存JSON构造BPM，而不是根据仍可变的调用者Map。测试要复制保存时的JSON，再执行正式BPM请求构造，不能以captor持有同一个可变Map误证明字段已保存。保留缺冻结义务的失败守卫，提前正式保存真实义务即可。

正常审批中心页面需要按当前native任务、租户和轮次显示会签指派组件；隐藏元数据和其他管理操作时，不能连必需的部门负责人指派一并隐藏。只读浏览页仍无指派入口，签名指派和后续会签分别校验正式task/BPM及负责人。

新版提前受控与执行生效不同。实际自然跨日验证已证明分钟任务将新版ACTIVE、旧执行版OBSOLETE、Master执行指针及共享状态同事务切换；界面不能继续套用旧外部审阅的SUPERSEDED说明。完成面板必须区分正式流程类别，并以真实后继关系展示作废旧版，不从当前ACTIVE状态猜master执行指针。


## 新流程类型的驳回回调与错误消息（2026-10-06）

BPM拒绝回调的状态CAS必须匹配经过核验的真实流程key，不能保留旧approval固定key：原生UPLOAD/REVISION会在拒绝时得到零更新并整笔回滚。用真实Flowable结束回调与真实mapper证明旧失败、正确key、外部轮次拒绝和晚失败回滚；接口HTTP200或页面toast不能单独证明检出、签名、流程成功，应核实际页面和所属业务终态。

对Axios Error先读取正式response.data.msg，否则泛HTTP400遮蔽服务端具体原因。同名与同编号错误不能用一个exists关键词统一归类；完整原名被占用时指出20年保留并提供引用/原链升版入口，禁止建议换编号或先作废释放名字。实际名称拒绝从正常文件选择器/上传预览验证，诊断自然响应仅用于根因，业务PASS仍来自页面明确提示及原记录不变。

失败申请的修正必须从正常版本列表选择失败版本，而不是从受控基线强行检出：已有工作稿时基线guard正确拒绝；所选失败版本的真实前驱链允许合法继续修改。当前账户夹具也要有真实租户、启用状态、用户名、昵称，不能让残缺DTO导致GxP当前身份校验挡住实际权限断言；并发override必须与普通seed一致。

正式消息已有 detailUrl 并不意味着用户能打开：需同时核对发送模板、解析器分支与消息按钮。关联整改消息的 sourceControlledFileId 是准确来源申请，relatedMasterId 是关联文件身份，两者不可互换。入口须绑定完整发送载荷及只读地址，继续由原服务端权限控制；离线解析/按钮测试与真实收件点击分别记录。证据：主任务 g67-notification-root-review.md。

工作稿保存后修改当前受控文件的关联，新正式升版申请必须在提交事务冻结当时的当前集合。不能继承旧稿审批历史，也不能仅在旧快照为空时回退读取当前集合；当前空集合也可能代表真实取消。准确锁定来源 Master、最新受控基线和 current set 版本，保留旧稿正文/属性及旧申请历史，同键重放不重新冻结。证据：主任务 g67-revision-relations-root-review.md。

原生升版撤回仍须能沿原目标修正重提；页面按钮可见或 checkout HTTP200 不能证明获锁。服务资格、checkout SQL CAS、checkin 真实正文和失败前驱策略需同时接通，且读取真正已结束、取消的原 BPM 历史。不能把 legacy nextMinor 重提或删除旧流程当作保持目标和历史的修复。证据：主任务 g68-withdrawn-revision-root-review.md。

检出修正链还需正式multipart上传上下文同样核验已结束的原生撤回申请，隔离票据测试不能证明真实上传预检接通。普通文件详情不应主动读取没有消费者的旧关联字段，导致合法主文件被无权旧关联阻断；独立历史入口继续严格拒绝。明确选定文件的检出浏览将准确同租户File/Master身份传到后台，以同Master全部版本限制候选，再保原权限、版本聚合与关键词规则；全域33k逐版本权限扫描不是提高超时或授管理员可以代替的修复。菜单权限需随正式脚本交付，类别规则不代系统permission。证据：主管理 g69-checkin-upload-root-review.md、g70-menu-root-review.md、g71-main-detail-root-review.md、g72-exact-selection-root-review.md，真实最终链见 g73-final-html-business-alignment.md。
