# ADR-0002：统一 GxP 审计内核与只追加账本

## Status

Accepted。用户在 2026-09-07 当前会话明确同意“统一审计写入服务 + 统一审计账本 + 领域审计明细 + 统一只读查询中心 + CI 强制覆盖门禁”方案。该批准仅覆盖架构和文档；代码实施、生产配置、数据库写入和发布仍需后续授权及业务参数确认。

## Context

当前系统存在多种审计能力：通用操作日志、DCC 访问与生命周期审计、eDHR 字段变更 hash 链、多个领域的电子签名记录、Migration 台账、签名周期审查规则和长期留存校验。但是能力分散，通用日志不能强制保存原因和前后值，部分关键写操作没有结构化审计，周期审查未形成持久化闭环，WORM 和可信时间也尚无正式运行证据。

初版统一设计经独立复审后又发现六个会影响最终审查的缺口：只明确把每日清单写入 WORM 而未定义自包含法规归档包；周期审查接口未证明按周期自动执行；覆盖登记没有固定 schema 和全写边界发现算法；数据库特权篡改与最终清单前的未封存窗口未闭合；CREATE/DELETE 的不存在状态没有标准表达；系统变更事件缺少 OpenAPI、配置、Migration 和产物的可重算清单。本 ADR 将六项整改纳入必需架构，而非可选增强。

检查清单 2.1 至 2.10 要求审计能力不仅存在，还要完整、覆盖关键操作、关联电子签名、不可篡改、定期审查、长期保存、覆盖系统变更、使用可信时间并以规范格式呈现。

## Decision Drivers

- 成功业务写入和审计事件必须原子提交。
- 审计必须取得领域真实 before/after，不能从 HTTP 参数猜测。
- 现有 eDHR、DCC 和签名专业证据不能丢失或被低质量通用日志替代。
- 新增功能必须默认进入可执行覆盖门禁，避免未来再次遗漏。
- 缺少原因、签名、时间、保存或不可变前置时必须失败关闭。
- 当前系统是 Spring Boot Maven 模块化单体，应优先使用内部服务契约而非新增远程微服务。
- 法规归档必须能够在主数据库不可用时独立恢复和查阅完整证据，不能只保留 hash。
- “支持周期审查”和“实际按期执行审查”必须由不同证据分别证明。
- 特权账号与审计外送保护边界必须职责分离，最终清单前的风险窗口必须有水位和时限。

## Options Considered

### Option 1：继续按模块独立建设审计

各模块自行设计表、字段、查询和保存规则。

优点是短期改动小；缺点是格式继续分裂、覆盖无法统一检查、周期审查和保存证据难以形成全局结论。

### Option 2：只使用 Controller 拦截器或 API 访问日志

统一记录用户、URL、请求参数和响应结果。

优点是接入快；缺点是不能可靠取得业务含义、原因、数据库真实前后值、对象版本和电子签名关系，也无法保证与业务事务原子提交。

### Option 3：所有业务通过一个统一远程审计 HTTP 服务

业务服务完成操作后调用独立审计服务。

优点是物理集中；缺点是在当前单体中引入分布式一致性问题，远程服务失败时容易产生业务成功而审计缺失，或诱发异步 fallback。

### Option 4：统一内部审计契约、只追加账本和领域证据适配器

领域服务在同一事务中显式提交标准事件，统一账本关联现有专业证据，并由统一查询、周期审查、WORM 和 CI 门禁治理。

优点是能同时保证领域真实性、事务原子性和统一治理；成本是需要逐模块盘点、接入和迁移。

## Decision

选择 Option 4。

1. 新建公共内部接口 `GxpAuditTrailService.append`，不新建供业务写入使用的远程 HTTP 审计服务。
2. 新建 `gxp_audit_event` 作为统一只追加审计账本，不继承包含更新/删除语义的通用 BaseDO。
3. 领域服务负责稳定对象身份、动作、原因、before/after 和专业证据；审计内核负责安全上下文身份、正式时间、规范化、序号、hash、策略和持久化。
4. 成功业务数据与成功审计事件必须在同一数据库事务提交；审计失败回滚业务。
5. 现有 eDHR、DCC、BPM 和 Showroom 专业证据继续保留，通过 `evidence_type + source_id + evidence_hash` 显式关联。
6. 账本禁止应用更新和删除，使用对象 hash 链、租户每日清单、WORM/Object Lock 和独立备份共同证明完整性。
7. 建设统一只读查询、导出、完整性验证和持久化周期审查，不提供审计补写、编辑或删除接口。
8. 建立机器可读 GxP 操作登记表；CI 阻止未登记、缺少策略或缺少测试的新增受控写入口。
9. 发布、Migration、接口版本和关键配置变化作为系统级 GxP 审计事件。
10. 正式操作时间和签名时间由受控服务器生成并关联可信时间证据，客户端时间只作为独立业务字段。
11. 每个事件的 before/after 使用显式状态信封；CREATE、UPDATE、DELETE、VOID/OBSOLETE 分别采用固定状态迁移，必需状态禁止使用 null 或 UNAVAILABLE。
12. `config/gxp-audit-policy.yaml` 是版本化操作登记权威源；编译期/CI 发现 Controller、领域服务、Job、消费者、导入、外部同步、Migration 和脚本写边界，并与登记表和测试双向核对。
13. 周期审查由持久化计划自动触发，按 `tenant + ruleVersion + periodCode` 唯一运行；停机恢复必须补扫，失败、漏期和逾期永久留痕。
14. 法规归档使用自包含归档包，至少保存规范事件、证据关联、签名、可信时间、必需领域证据、manifest 和 SHA256SUMS；每日清单只是归档包完整性组成部分。
15. 除应用账号最小权限外，必须接入数据库原生或经批准的等价特权审计，并将 DML、DDL、授权和关闭审计尝试外送至被审账号不可改写的独立保护存储。
16. 使用增量密封水位限制每日最终清单前的风险窗口；超过批准最大未封存时长时治理和发布状态失败。
17. 每次发布和回滚生成可重算系统变更清单，固定记录 commit、产物/镜像 digest、OpenAPI 前后 hash/diff、Migration 有序清单/hash、关键配置脱敏快照/diff、批准、原因、操作者、时间和结果。

## Consequences

正面影响：

- 检查清单 2.1 至 2.10 可以映射到统一控制和自动验证。
- 不牺牲 eDHR 字段级和 DCC 文件级专业证据。
- 审计失败无法被包装成业务成功。
- 新功能遗漏审计会在 CI 和发布门禁暴露。
- 查询、导出、周期审查、保存和恢复形成同一证据链。

负面影响和成本：

- 需要盘点大量 Controller、Job、消费者、同步和脚本，不能一次靠拦截器自动完成。
- 关键业务服务需要增加锁定 before、构造 after 和同事务 append。
- append-only 数据库权限、WORM、可信时间和独立恢复需要运维投入。
- 统一查询要处理多种历史专业证据和数据脱敏策略。
- 首次切换前必须完成业务范围和保存政策审批。
- 需要建设自包含归档包和隔离恢复工具，存储与恢复成本高于只保存每日 hash 清单。
- 需要引入全写边界发现、架构约束和批准例外生命周期，CI 复杂度增加。
- 数据库特权审计的具体产品与部署取决于正式环境能力，缺少经批准实现时发布保持阻塞。
- 自动周期审查需要处理跨期停机、时区、补扫、幂等和逾期升级。

## Rejected Options

- 拒绝 Option 1，因为它不能阻止未来格式和覆盖继续分裂。
- 拒绝 Option 2，因为访问日志不是完整审计追踪，无法证明真实数据变化。
- 拒绝 Option 3，因为当前架构下远程写入破坏业务与审计的本地事务原子性。
- 拒绝把 hash 链单独视为不可篡改，因为高权限删除整条链仍需每日清单和 WORM 证明。
- 拒绝只把每日 manifest/hash 写入 WORM，因为它无法在主数据库丢失后恢复可查阅的事件和签名证据。
- 拒绝只提供手工“创建审查批次”按钮，因为它不能证明企业实际按批准周期执行审查。
- 拒绝只扫描 Controller 注解，因为 Job、消费者、导入、Migration、脚本和绕过服务的 Mapper 写入仍会漏审。
- 拒绝长期双写和异步补记，因为会产生两个事实源或业务成功而审计缺失。

## Migration Path

1. 批准固定 schema 的 GxP 操作登记表、保存期限、周期审查、最大未封存时长、NTP、WORM 和特权审计参数。
2. 以 additive migration 部署统一表和最小权限，不立即切换业务。
3. 完成统一内核的真实事务、幂等、并发和完整性测试。
4. 先接入 eDHR、DCC 和电子签名，再接入权限、配置和基础数据。
5. 对既有专业记录生成只追加历史索引；无法唯一关联的记录保持阻塞。
6. 每个模块在维护窗口一次切换，切换后旧日志不再单独承担 GxP 成功证据。
7. 启用查询、自动周期审查、可信时间、增量密封、每日清单、完整法规归档包、特权审计外送和恢复验证。
8. 独立验证通过后再评估正式发布。

## Verification and Operational Impact

- schema 测试证明事件表没有更新/逻辑删除字段，数据库账号无 UPDATE/DELETE/TRUNCATE 权限。
- 真实事务测试注入审计失败，证明业务主表、子表和版本均回滚。
- hash 测试覆盖修改、删除、插入、换序和整条对象链删除。
- 状态信封测试覆盖 ABSENT、PRESENT、VOIDED、REDACTED 及 CREATE/UPDATE/DELETE/VOID 合法矩阵。
- 每个 GxP 动作覆盖原因、before/after、签名、幂等和并发测试。
- 覆盖发现测试逐类植入 Controller、Service、Job、消费者、Migration 和脚本未登记入口，证明 CI 失败。
- 周期审查覆盖连续周期、停机补扫、冻结快照、发现项、整改、质量签名、漏期/逾期和关闭阻断。
- 正式环境验证 chrony/NTP、数据库时间偏差、特权审计外送、未封存水位、WORM versionId/retainUntil/legal hold 和独立恢复。
- 归档验证先清空隔离恢复环境，再仅用自包含法规归档包恢复事件、证据、签名、时间及查询导出能力。
- 系统变更验证重算 OpenAPI、Migration 顺序、配置和产物/镜像 diff，缺少批准或前后基线时发布失败。
- E2E 仅在用户当轮明确授权后使用 Playwright 走真实页面，API/DB 只读核验。

## Revisit or Rollback Conditions

- 若系统拆分为独立数据库的微服务，需要重新决策跨库一致性协议，不能直接把本地 append 改成尽力 HTTP 调用。
- 若法规或质量政策要求全局单一序列、外部可信时间戳或独立第三方审计平台，应重新评审链分区和时间证据方案。
- 首条正式统一事件产生前可回退应用并保留未启用表；产生事件后不得用旧代码继续 GxP 写入，只能向前修复或从切换前完整备份恢复。
- WORM、可信时间或恢复验证失效时，受影响环境的合规放行状态必须转为阻塞。
