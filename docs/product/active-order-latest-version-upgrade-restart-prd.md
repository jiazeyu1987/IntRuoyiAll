# MES 活跃订单按最新版本升级重启 PRD

## Purpose and Scope

本文定义 MES 活跃订单在执行过程中因受控基础数据版本变化而需要重新执行时的产品需求。适用版本对象包括工艺路线、QA 检验规程、批记录模板、表单模板、表单槽位、工序开始配置、设备参数标准、物料规范、放行规则，以及未来纳入同类受控管理的版本对象。

最新需求口径采用单一路径：用户进入活跃订单，点击“升级”按钮，系统自动解析所有适用受控对象的最新正式版本，生成并冻结升级快照，然后提交独立版本升级审批。审批通过后，系统终止旧活跃执行和旧批次的继续执行资格，创建业务上下文相同的新活跃订单，并按照升级快照从头生成全部工序、物料、QA、批记录、表单和放行任务。

该流程处理的是“版本变化导致执行依据变化”，不是生产质量不合格。若同时存在真实质量问题、合规冻结或不合格冻结，必须按原质量或合规流程处理，版本升级不能绕过。

## Product Summary

活跃订单详情页提供“升级”按钮。用户点击后进入升级确认页，系统展示当前订单锁定的受控版本基线，并自动解析全部适用对象的最新正式版本。用户不选择版本、不删除对象、不补选依赖，只确认“按全部最新正式版本整单重启”的影响并提交审批。

审批提交后，旧活跃订单进入版本升级审批中，生产报工、PQC、批记录填写、批记录审批和上市放行写操作全部冻结。审批拒绝或撤回时，旧订单恢复原版本执行。审批通过时，系统以原子方式终止旧执行、作废旧 eDHR 批次的执行资格，并创建新的活跃订单执行修订版。

新订单复制的是业务上下文，例如生产工单、产品、生产批号、计划数量、组织、计划日期和来源关系；新订单不复制旧订单的执行事实，例如旧填写值、完成状态、QA 结果、签名、附件、审批结果或放行结论。用户若忘记旧订单填过什么，可以从新订单追溯到旧订单只读详情，查看旧版本下的原始填写内容。

## Target Users

- 一线生产员工：从活跃订单发起版本升级，审批通过后按新订单从头填写。
- 生产组长：确认旧执行被冻结或被替代，安排新订单重新执行。
- 工艺管理员：确认工艺路线和相关执行配置的新版本影响。
- QA/质量负责人：确认 QA 检验规程、检验项目、抽样标准和放行要求的新版本影响。
- DCC/文件管理员：确认受控文件、模板、规程和版本依赖均处于正式状态。
- 审批人：审核版本升级原因、影响范围和整单重启结论。
- 审计和批记录查看人员：追溯新旧订单关系、升级审批、旧填写事实和新执行事实。

## First Version Scope

1. 活跃订单详情页增加“升级”按钮。
2. 点击升级后进入版本升级确认页，页面展示当前订单锁定版本基线。
3. 系统自动解析全部适用受控对象的最新正式版本。
4. 系统在提交审批前生成完整升级快照，记录对象类型、对象 ID、版本 ID、版本号、正式状态、适用范围和快照 Hash。
5. 前端不提供逐项版本选择器，不允许只升级 QA、不允许只升级路线、不允许跳过其他受控对象。
6. 页面展示“当前版本到最新版本”的差异和影响摘要。
7. 若版本集合缺少正式版本、适用范围不匹配或依赖冲突，系统阻止提交并显示具体阻塞原因。
8. 用户填写升级原因并提交独立“版本升级重启”审批。
9. 审批期间旧订单冻结所有执行写操作，但允许只读查看。
10. 审批拒绝或撤回时旧订单恢复原版本执行。
11. 审批通过后系统原子终止旧活跃执行、终止旧批次执行资格、创建新活跃订单和新批次。
12. 新订单锁定审批申请中的升级快照，即使审批期间又发布了更新版本，也不自动替换。
13. 新订单按所有最新正式版本从头生成任务，不继承旧完成状态和旧填写结果。
14. 新旧订单、旧批次、新批次和升级申请之间建立双向追溯关系。
15. 旧订单在追溯中只读可查，能够查看用户之前填写的内容、签名、附件、审批和字段审计。

## Non-Goals

- 不在原活跃订单上直接改工艺路线版本、QA 版本或其他版本字段。
- 不提供按对象选择目标版本的流程。
- 不支持“只把 QA 从 5.0 升到 6.0，其他不变”这类局部升版。
- 不支持用户指定低于最新正式版本的目标版本。
- 不做跨版本字段自动映射、旧值带入、旧工序完成状态继承或一键复制旧填写。
- 不删除旧订单、旧批次、旧表单、旧签名、旧附件和旧审计。
- 不把版本升级审批当作不合格审批、偏差审批、CAPA、召回或报废流程。
- 不用当前最新模板或当前 ACTIVE 配置解释旧订单历史。
- 不默认创建外部 ERP 新生产工单；外部工单策略由独立集成需求决定。
- 不允许高权限绕过版本升级审批、冻结和追溯要求。

## Functional Requirements

### FR-01 活跃订单升级入口

- 活跃订单详情必须提供“升级”按钮。
- 只有具备版本升级发起权限且可访问该订单的用户可以使用该按钮。
- 已终止、已归档、已放行、已处于升级审批中或存在不可绕过冻结的订单，不能再次发起普通升级。
- 按钮不可用时，页面必须展示明确原因。

### FR-02 当前版本基线展示

- 升级确认页必须展示当前订单锁定的受控版本基线。
- 基线至少包括对象类型、对象名称、版本号、版本 ID、锁定时间、正式状态和来源快照。
- 当前基线来自订单锁定快照，不得由前端临时查询当前 ACTIVE 版本替代。
- 如果旧订单快照缺失，系统必须阻止升级或历史查看，并提示需要数据修复，不得用最新配置补齐。

### FR-03 全部最新正式版本解析

- 点击升级后，系统必须为订单执行所需的全部受控对象解析最新正式版本。
- 最新正式版本必须满足租户、产品、工艺路线、工序、组织、适用日期和文件状态要求。
- 草稿、待审批、撤回、作废、过期且禁止新执行的版本不能进入升级快照。
- 解析结果由后端返回并保存，前端不得自行推算“最新”。
- 若任一对象没有可用最新正式版本，提交审批必须被阻止。

### FR-04 不提供版本选择

- 前端不得展示逐项版本选择器。
- 用户不得只升级 QA、只升级工艺路线、只升级批记录模板或跳过任一适用受控对象。
- 用户不得把目标版本改成低于最新正式版本的历史版本。
- 若业务希望部分版本升级，应另立需求，不进入本功能第一版。

### FR-05 差异和影响预览

- 提交审批前必须展示当前版本与全部最新正式版本的差异摘要。
- 差异至少覆盖工序增删改、批记录物料变化、QA 检验项目变化、表单字段变化、表单槽位变化、设备参数变化、物料规范变化、放行规则变化和版本依赖变化。
- 差异预览必须明确提示：审批通过后整单从头执行，新订单不继承旧填写结果。
- 若工艺路线从清洗两个物料变为清洗三个物料，预览必须展示该结构变化。

### FR-06 升级审批申请

- 申请必须记录来源活跃订单、来源批次、当前版本集合、全部最新正式版本集合、申请人、申请时间、升级原因和升级快照 Hash。
- 申请原因类型必须为版本升级重启，不得伪装成质量不合格原因。
- 提交后生成独立版本升级审批实例，并展示审批编号、审批状态和冻结状态。
- 审批节点可由工艺、QA、DCC、生产负责人等角色参与，具体节点由正式审批配置决定。

### FR-07 审批期间冻结

- 升级申请处于审批中时，旧活跃订单必须禁止生产报工、PQC 提交、批记录填写、批记录审批、上市放行和再次升级。
- 页面必须显示“版本升级审批中，当前执行已冻结”及审批编号。
- 查询旧订单只能只读，不得触发任务补建、状态补偿或快照回填。
- 审批拒绝或撤回后，旧订单解除版本升级冻结并继续按原版本执行。

### FR-08 审批通过后的原子重启

- 审批通过后，系统必须在一个受控事务中完成旧执行终止、新执行创建和新旧关系建立。
- 旧活跃订单状态变为 `SUPERSEDED_BY_VERSION_UPGRADE`。
- 旧 eDHR 批次状态变为 `VOIDED_BY_VERSION_UPGRADE`。
- 旧订单所有未完成任务、待办、审批和放行动作必须终止或标记为被版本升级替代。
- 新订单必须生成新的活跃执行 ID、执行编号、eDHR 批次编号和任务集合。
- 新旧订单不能同时处于可生产、可提交、可审批批记录或可上市放行状态。

### FR-09 新订单复制边界

新订单可以复制：

- 原生产工单 ID 和编号。
- 产品、生产批号、计划数量、组织、计划日期和业务备注。
- 版本升级申请 ID、来源订单 ID 和来源批次 ID。

新订单不得复制：

- 旧工序完成状态、累计完成数量、损耗数量和不良明细。
- 旧物料填写值、批记录表单值、字段审计、签名和附件。
- 旧 PQC 任务、检验结果、逐件明细、QA 签名和放行结论。
- 旧审批待办、批记录审批结果、上市放行签名和关闭时间。

### FR-10 新版本任务重建

- 新订单必须按升级快照中的全部最新正式版本重新生成完整工序、物料、QA、批记录、表单、签名和放行任务。
- 工艺路线、QA 规程、批记录表单、表单槽位和工序开始配置必须分别读取各自正式来源，不得互相补齐。
- 如果新路线要求三个清洗物料，新订单必须生成三个空白物料执行项。
- 新订单所有执行入口从待开始或待填写状态开始，业务上视为从头执行。

### FR-11 旧订单追溯

- 新订单详情必须提供“版本历史”或等价入口，可进入旧订单只读详情。
- 旧订单详情必须按旧订单锁定快照和旧表单布局渲染。
- 旧订单必须展示原填写值、填写人、填写时间、签名、附件、字段审计、旧版本集合、作废原因和替代新订单。
- 历史页面只读，不提供编辑、重新提交、审批、放行或复制到新订单。

### FR-12 幂等和失败处理

- 同一来源订单只能存在一个进行中的版本升级申请。
- 重复点击升级、重复提交审批或重复应用审批结果，不得产生多个有效新活跃订单。
- 审批通过后应用失败时，不得出现旧订单已作废但新订单不可追溯，或新旧订单同时可执行的状态。
- 应用失败必须保留明确错误、冻结状态和处理入口。
- 审批期间若快照中的任一目标版本被撤销或不再适用，应用必须失败并要求重新发起，不得自动换成另一个版本。

## Business Rules

1. 活跃订单版本升级重启是执行依据变化，不是生产质量不合格。
2. 用户入口固定为活跃订单详情页的“升级”按钮。
3. 目标版本固定为点击升级时系统解析出的全部最新正式版本。
4. 本功能不支持逐项选择版本、局部升级或指定历史版本。
5. 升级申请提交前必须冻结目标版本快照；审批期间新发布版本不影响当前申请。
6. 审批通过后必须整单重启，不做旧执行数据迁移。
7. “创建一个一模一样的订单”只表示复制业务上下文，不表示复制执行事实。
8. 旧订单和旧批次的执行资格被终止，但历史事实不能删除、改写或用新模板重算。
9. 新订单所有工序、检验、批记录和放行任务从头开始。
10. 新旧订单必须有结构化关系，能够互相追溯。
11. 当前 ACTIVE 配置只用于解析本次升级目标，不得用于替代旧订单锁定快照。
12. 存在真实不合格、合规冻结或放行后变更时，版本升级不能绕过原流程。
13. 任一受控对象最新正式版本缺失、依赖冲突或适用范围不匹配时，必须阻塞提交。
14. 失败处理必须 fail fast，不能静默换用旧版本、低版本或模拟成功。

## States and Transitions

### 版本升级申请状态

| 状态 | 含义 | 可进入动作 |
| --- | --- | --- |
| `DRAFT` | 已生成全部最新正式版本升级快照，用户尚未提交 | 提交审批、放弃 |
| `PENDING_APPROVAL` | 审批中，旧订单已冻结 | 审批通过、审批拒绝、撤回 |
| `APPROVED` | 审批已通过，等待或正在应用 | 应用重启 |
| `APPLIED` | 旧执行已终止，新活跃订单已创建 | 查看新订单、查看旧追溯 |
| `REJECTED` | 审批拒绝 | 旧订单恢复原版本执行 |
| `WITHDRAWN` | 申请撤回 | 旧订单恢复原版本执行 |
| `APPLY_FAILED` | 审批通过但应用失败 | 受控重试或人工修复 |
| `CANCELLED` | 申请被系统或授权用户取消 | 只读留痕 |

### 旧活跃订单状态

| 状态 | 含义 |
| --- | --- |
| `ACTIVE` | 按原锁定版本正常执行 |
| `VERSION_UPGRADE_PENDING` | 版本升级审批中，禁止执行写操作 |
| `SUPERSEDED_BY_VERSION_UPGRADE` | 因版本升级被新订单替代，只读追溯 |
| `VERSION_UPGRADE_APPLY_FAILED` | 应用失败，保持冻结等待处理 |

### 旧批次状态

| 状态 | 含义 |
| --- | --- |
| `IN_PROGRESS` | 原批次仍可按旧版本执行 |
| `VOIDED_BY_VERSION_UPGRADE` | 因版本升级重启而终止执行资格，历史证据保留 |

### 新活跃订单状态

| 状态 | 含义 |
| --- | --- |
| `CREATING` | 正在按升级快照创建新执行 |
| `ACTIVE` | 已加入活跃订单，可以从头执行 |
| `CREATE_FAILED` | 创建失败，不得进入可生产状态 |

## Edge Cases

- 订单已卡在最后上市放行步骤：若原因是受控版本需要升级，仍从活跃订单点击升级，审批通过后旧放行任务终止，新订单按最新版本从头执行；若存在真实质量问题，则质量流程独立处理。
- 路线 V1 清洗两个物料，新路线 V2 清洗三个物料：旧订单保留两个物料填写历史，新订单生成三个空白物料执行项。
- QA 当前 5.0，最新正式版本为 7.0：本流程直接使用 QA 7.0，不提供选择 6.0 的入口。
- 只想升级 QA 但不想升级路线：本功能不支持；应另立局部版本变更需求并重新评审。
- 审批期间发布了更高版本：当前申请仍按提交前冻结的快照执行；若要用更高版本，撤回或拒绝后重新点击升级。
- 审批拒绝或撤回：旧订单恢复原版本执行，不创建新订单。
- 目标版本审批通过后被撤销：应用失败，不能自动改用另一个最新版本。
- 旧订单已有正式报工、QA 结果或批记录签名：全部保留在旧订单，只读可查，新订单不继承。
- 旧订单尚无填写数据：仍按同一升级审批和重启流程留痕。
- 旧订单历史快照缺失：不得用当前 ACTIVE 配置补齐历史，必须进入数据修复或审计处理。
- 订单已经放行或归档：普通活跃订单升级入口关闭，走放行后变更、CAPA、召回或其他正式流程。
- 多人重复点击升级：返回已有进行中申请或已应用结果，不创建第二个有效申请。

## Acceptance Criteria

### AC-01 活跃订单展示升级入口

Given 用户有版本升级发起权限且订单处于 `ACTIVE`  
When 用户打开活跃订单详情  
Then 页面显示“升级”按钮，并展示当前订单锁定版本基线。

### AC-02 自动使用全部最新正式版本

Given 当前订单锁定 QA 5.0 且最新正式 QA 为 7.0  
When 用户点击“升级”进入确认页  
Then 系统自动把 QA 7.0 和其他适用受控对象的最新正式版本写入升级快照，页面不展示逐项版本选择器。

### AC-03 阻塞不可用最新版本

Given 任一受控对象没有可用最新正式版本或存在依赖冲突  
When 用户尝试提交升级审批  
Then 系统阻止提交并显示具体对象、冲突原因和解除条件。

### AC-04 审批期间冻结旧订单

Given 升级申请处于 `PENDING_APPROVAL`  
When 用户尝试报工、PQC、批记录填写或上市放行  
Then 系统拒绝写操作，并显示版本升级审批冻结原因和审批编号。

### AC-05 审批拒绝恢复旧执行

Given 旧订单因版本升级申请被冻结  
When 审批被拒绝或撤回  
Then 旧订单恢复原版本执行状态，不创建新活跃订单。

### AC-06 审批通过重启

Given 升级审批通过且目标快照仍有效  
When 系统应用升级  
Then 旧订单变为 `SUPERSEDED_BY_VERSION_UPGRADE`，旧批次变为 `VOIDED_BY_VERSION_UPGRADE`，新订单加入活跃订单并从头开始。

### AC-07 不继承旧执行事实

Given 旧订单已经填写物料、QA、批记录和签名  
When 新订单创建成功  
Then 新订单不带入旧填写值、旧结果、旧签名或旧完成状态。

### AC-08 历史填写可追溯

Given 用户忘记旧订单曾填写的内容  
When 用户从新订单进入版本历史并打开旧订单  
Then 系统按旧订单快照只读展示原填写内容、签名、附件和审计，不使用当前最新模板补齐。

### AC-09 幂等防重复

Given 同一来源订单已有进行中的升级申请  
When 用户再次点击升级或重复提交  
Then 系统返回已有申请或明确冲突，不创建第二个有效申请或第二个新订单。

### AC-10 版本升级不等于不合格

Given 升级原因是工艺路线、QA 规程或其他受控版本变化且没有质量不合格  
When 用户提交升级申请  
Then 系统创建版本升级审批，不创建不合格审批；若另有质量冻结，版本升级不能解除该冻结。

## Open Questions

- 版本升级审批的具体节点、角色、电子签名要求和超时策略需由审批配置确认。
- 外部 ERP 是否要求新生产工单编号，需由 ERP 集成规则确认；本功能第一版只定义 MES 内部新活跃执行。
- 旧订单涉及的领料、库存占用、FIFO 分配和 WIP 数量是否需要冲销或释放，需由仓储和生产执行规则确认。
- 升级应用失败后的人工修复页面、重试权限和审计字段需在系统设计阶段细化。
- 旧订单历史可见范围、保留期限、脱敏策略和普通员工查看边界需由合规策略确认。

## Product Blockers

- 无法为全部受控对象生成最新正式版本快照时，不得提交升级审批。
- 无法证明最新版本适用范围和依赖关系完整时，不得应用新订单。
- 无法冻结旧订单执行写操作时，不得发起升级审批。
- 无法保证旧执行终止、新执行创建和关系建立具备事务性与幂等性时，不得上线升级按钮。
- 无法保留旧订单锁定快照、原填写值、签名、附件和字段审计时，不得作废旧执行。
- 旧订单存在真实不合格冻结、合规冻结或放行后正式变更场景时，不得通过普通活跃订单升级流程绕过。
