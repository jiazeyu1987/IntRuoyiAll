# PRD：DCC 第一阶段逻辑文件身份与 Windchill 版本内核

## Purpose and Scope

本文定义 DCC 第一阶段的正式产品需求。第一阶段以逻辑文件身份为基础，引入 Windchill 式 `Revision / Iteration` 版本机制，完成受控文件的初始建档、检出、检入、撤销检出、历史追溯、从指定小版本创建下一大版本，以及具体小版本与现有审批发布流程的受控衔接。当前实施和验收范围仅限测试环境，不包含生产发布。

第一阶段要解决的核心问题是：系统能够稳定判断“这是哪一份逻辑文件”“当前编辑到哪个小版本”“哪个具体版本正在审批”“普通用户当前应使用哪个正式版本”。

本文中的版本展示统一使用 `A/1`、`A/2`、`B/1`；其中字母是大版本，数字是小版本。版本号只表达版本身份，不直接表达审批或生效状态。

- `IntRuoyiBackend/docs/product/dcc-screenshot-requirements-prd.md` 及配套用户流程、验收标准。

## Product Summary

DCC 将一份受控文件分成三个层次：

1. 逻辑文件：由 `DCC 项目 + 分类叶子 + 文件编码` 唯一确定，代表长期不变的文件身份。
2. 大版本：使用字母表示一次需要正式审批和文控发布的修订代际，例如 A、B、C。
3. 小版本：使用数字表示同一大版本编制过程中的迭代，例如 A/1、A/2、A/3。

编制人员通过检出取得独占编辑权，通过检入自动形成下一小版本。小版本本身不发起审批，也不会自动替代普通用户正在使用的正式版本。文件责任人只能将当前工作大版本的最新小版本提交审批；审批和文控发布成功后，该具体小版本才成为当前正式版本。

已发布的大版本需要修改时，用户从当前大版本下明确选择一个小版本作为来源，创建下一大版本的 `/1` 小版本。例如从 A/2 创建 B/1。新大版本发布前，旧正式版本继续有效。

## Target Users

- 文件编制人员：创建文件、检出、修改、检入、撤销检出和查看自己的工作版本。
- 文件责任人：确认版本来源、选择送审小版本、发起下一大版本并说明变更原因。
- 审核人员：审核提交时锁定的具体小版本。
- 批准人员：批准或驳回提交时锁定的具体小版本。
- 文控人员：核对版本身份，发布已批准的具体小版本，维护版本历史的受控可见性。
- 普通阅读用户：只使用当前正式发布版本，不接触未发布工作版本。
- 审计人员：查询版本来源、检出检入、审批、发布、替代和失败记录。

## First Version Scope

1. 将逻辑文件唯一身份确定为 `DCC 项目 + 分类叶子 + 规范化文件编码`。
2. 为每个逻辑文件分别维护当前正式版本、当前工作大版本、最新工作小版本和当前送审小版本。
3. 新逻辑文件由系统自动创建 `A/1`，用户不能手工指定初始版本。
4. 支持对可编辑工作版本执行检出、检入和撤销检出。
5. 检入时由系统自动增加小版本数字，并永久保留上一小版本。
6. 小版本不单独审批，也不因检入而自动成为普通用户使用的正式版本。
7. 支持从当前大版本下明确选定一个历史小版本，创建下一大版本的 `/1` 版本，并永久记录来源。
8. 支持将当前工作大版本的最新小版本提交现有 DCC 审批流程；提交后锁定该小版本及其受控内容。
9. 支持审批驳回后基于被驳回版本继续检出、检入并形成新小版本，再次送审。
10. 支持已批准小版本经文控发布后成为当前正式版本，并在同一成功事务中替代原正式版本。
11. 普通用户始终只看到当前正式版本；授权编制、审批和文控人员按职责查看工作版本和历史版本。
12. 提供完整版本历史，显示版本号、来源版本、状态、创建人、创建时间、修改说明、审批发布结果和文件哈希。
13. 对现有 DCC 数据执行只读迁移预检并输出阻塞清单；未解决的身份或版本歧义不得自动迁移。
14. 大版本发布时形成可追溯的关联方范围和关联文件快照，供后续通知与影响评估阶段使用。
15. 建立项目访问规则，明确 OWNER、EDIT、VIEW 三个项目级别，并与类别动作权限、全局接口权限共同决定版本操作。

## Non-Goals

- 不在第一阶段建设项目目录模板、项目目录完整性统计或目录模板升级差异确认。
- 不在第一阶段建设受控文件内容模板、模板字段规则或通用附件模板规则。
- 不改变现有审核、批准、文控发布节点的业务分工；仅要求流程锁定并处理明确的具体小版本。
- 不在第一阶段完成关联方消息发送、关联文件影响评估任务和影响评估闭环。
- 不在第一阶段建设跨产品引用、同版本例外替换、代理交接或强制解锁流程。
- 不在第一阶段建设完整的权限申请审批平台；但所有版本动作必须执行现有项目访问和对应动作权限校验。
- 不在第一阶段改变培训、电子分发或纸质分发规则。
- 不在第一阶段处理环境隔离、CSV 全量验证、性能容量指标或普通上传断点续传。
- 不在第一阶段执行生产环境部署、生产安全评审、生产密钥治理、生产灾备或生产 Go/No-Go。
- 不允许通过兼容字符串、默认项目、默认分类叶子或自动猜测方式掩盖历史数据问题。

## Functional Requirements

### FR-P1-01 逻辑文件身份

1. 系统必须以 `dccProjectCodeId + fileTypeTaxonomyLeafId + normalizedFileNumber` 唯一识别逻辑文件。
2. `dccProjectCodeId` 必须指向有效的 DCC 项目；产品主档只作为关联信息，不参与逻辑文件唯一键。
3. 文件类型必须使用有效的分类叶子，非叶子分类不能用于创建逻辑文件。
4. 文件编码必须按统一规则去除首尾空白并进行大小写规范化后再判断唯一性。
5. 同一项目、同一分类叶子、同一规范化文件编码只能存在一个逻辑文件。
6. 相同文件编码可以在不同项目或不同分类叶子下重复使用。
7. 并发创建同一逻辑文件时只能成功一次，失败请求必须明确返回身份冲突。

### FR-P1-02 版本组成与自动编号

1. 完整版本由大版本字母和小版本正整数共同组成。
2. 新逻辑文件的初始版本由系统自动生成为 `A/1`。
3. 同一大版本内，检入按当前最大有效小版本自动递增，例如 `A/1 -> A/2`。
4. 大版本采用 Excel 式字母进位：A 至 Z，之后为 AA、AB，AZ 之后为 BA，并按相同规则继续。
5. 创建下一大版本时，大版本自动递增，小版本重置为 `1`，例如 `A/3 -> B/1`、`Z/2 -> AA/1`。
6. 用户不能手工输入或修改大版本字母、小版本数字和展示版本号。
7. 已形成的版本号及其逻辑文件归属不可修改。
8. 每个版本必须保存直接来源版本；新大版本还必须保存用户选定的修订来源版本。

### FR-P1-03 检出

1. 只有项目访问级别为 OWNER 或 EDIT，且具有检出接口权限和类别 EDIT 权限的用户可以检出文件。
2. 检出对象必须是当前工作大版本中最新且允许编辑的小版本。
3. 已正式发布且尚未创建下一工作大版本的版本不能直接检出，用户必须先执行“新建修订版”。
4. 同一逻辑文件同一时间只能存在一个有效检出锁。
5. 检出时用户必须填写修改原因。
6. 检出成功后，系统显示检出人、检出时间、修改原因和被检出的版本。
7. 检出不创建新小版本，也不改变普通用户当前看到的正式版本。

### FR-P1-04 检入

1. 只有当前检出人可以检入。
2. 检入必须包含以下至少一种真实变化：修改后的源文件，或允许修改的业务元数据差异；两者都没有时必须拒绝。
3. 系统必须根据当前工作大版本的最新小版本自动生成下一小版本。
4. 检入形成的新小版本状态为“工作中”，不自动提交审批。
5. 内容变更必须保存新文件和新哈希；仅元数据变更必须复制形成新的受控源文件记录、保持相同哈希，并保存结构化字段差异。
6. 项目、分类叶子和文件编码属于逻辑文件身份，不能通过元数据检入修改。
7. 检入必须保存来源版本、变更范围、前后哈希、字段差异、修改说明、操作人和操作时间。
8. 检入成功后释放检出锁。
9. 文件存储、复制、哈希计算或版本记录任一环节失败时，不得创建不完整版本，原检出锁继续保留。
10. 重复点击或重复请求不能创建两个相同小版本。

### FR-P1-05 撤销检出

1. 当前检出人可以撤销自己的检出；具备独立授权的文控处理不在第一阶段范围内。
2. 撤销检出必须填写原因。
3. 撤销检出只丢弃本次未检入的工作副本并释放锁。
4. 撤销检出不得创建新小版本，不得改变最后一个已检入版本。
5. 撤销检出必须保留操作审计记录。

### FR-P1-06 新建大版本

1. 新大版本只能在不存在其他开放大版本时创建。
2. 只有项目 OWNER 可以从当前大版本的版本历史中明确选择一个小版本作为来源。
3. 系统不得静默改用最新小版本。
4. 当选定来源不是当前正式版本时，用户必须填写选择该历史小版本的理由。
5. 新大版本自动使用下一大版本字母和小版本 `1`。
6. 新大版本必须复制选定来源的受控内容和允许继承的业务元数据，并保存来源快照。
7. 创建新大版本不自动发起审批，不影响当前正式版本。
8. 重复请求不得产生两个相同的开放大版本。

### FR-P1-07 送审版本锁定

1. 文件责任人只能提交当前工作大版本的最新小版本；存在更新小版本时不得提交旧小版本。
2. 提交审批时必须锁定逻辑文件身份、完整版本号、源文件、文件哈希、业务元数据、现有关联文件快照和审批路线快照。
3. 已送审的小版本不能继续编辑或被检出。
4. 审批页面必须明确显示正在审批的具体版本，例如 `B/3`，不能只显示“大版本 B”。
5. 同一逻辑文件同一时间只能存在一个未完成的送审版本。
6. 审批期间产生的后续工作版本不能替换审批对象。

### FR-P1-08 驳回与重新送审

1. 审批驳回后，原送审版本及全部审批记录必须永久保留。
2. 编制人员不得覆盖被驳回版本。
3. 编制人员可以基于被驳回版本检出修改，检入后形成同一大版本的下一小版本。
4. 重新送审必须选择新形成的具体小版本，并生成新的审批快照。
5. 原审批签名和批准结果不得沿用到新小版本。

### FR-P1-09 批准、发布与正式版本切换

1. 大版本审批通过后，具体送审小版本进入“已批准/待文控发布”。
2. 批准不能直接改变普通用户的当前正式版本。
3. 文控只能发布已批准且内容与审批快照一致的具体小版本。
4. 发布成功后，该版本成为当前正式版本。
5. 新正式版本生效与旧正式版本被替代必须作为一个不可分割的业务结果完成。
6. 发布失败时，新版本不得成为正式版本，旧正式版本继续有效。
7. 发布后同一逻辑文件只能存在一个当前正式版本。

### FR-P1-10 可见性与版本历史

1. 普通阅读用户默认只看到当前正式版本。
2. 未发布工作版本不能从普通阅读入口搜索、预览或下载。
3. 编制人员可以查看其有权参与的当前工作版本和版本历史。
4. 审核、批准和文控人员可以查看其当前任务所需的锁定版本。
5. 历史页面必须区分工作中、审批中、已驳回、已批准待发布、正式、已替代和已作废状态。
6. 每个新大版本必须显示其选定来源，例如“B/1 来源于 A/2”。
7. 历史记录必须明确标记当前正式版本和当前最新工作版本，两者可能不是同一个版本。

### FR-P1-11 审计与失败处理

1. 创建逻辑文件、创建版本、检出、检入、撤销检出、新建大版本、提交审批、驳回、批准、发布和替代必须记录审计事件。
2. 审计事件至少包含操作者、时间、逻辑文件、版本、来源版本、动作、原因、结果和文件哈希。
3. 身份冲突、重复请求、非本人检入、非法版本来源和发布失败等关键失败也必须记录。
4. 审计记录写入失败时，对应关键业务动作不得返回成功。

### FR-P1-12 现有数据迁移预检

1. 正式迁移前必须只读扫描现有逻辑文件、版本、项目、分类叶子、当前有效指针、审批、签名和文件记录。
2. 预检必须为每条现有版本给出目标逻辑文件身份和目标 `Revision / Iteration` 映射。
3. 缺少项目、缺少分类叶子、身份重复、版本顺序不明、多个当前有效版本、文件缺失或哈希不可读时，预检必须输出明确阻塞项。
4. 阻塞项必须由业务人员确认，系统不得通过默认项目、默认分类、文件名猜测或重新编号自动消除。
5. 迁移完成后，原有审批、签名、发布文件、时间、操作者和历史版本必须仍可追溯。
6. 旧测试数据只有在身份唯一、版本号唯一且可排序、无未完成审批、正式指针唯一时才允许确定性自动映射。
7. 确定性映射将每个旧业务版本视为一个大版本的 `/1`：单版本为 A/1，多版本依次为 A/1、B/1、C/1。
8. 不满足确定性条件的数据继续阻塞；测试环境也不得自动删除或猜测映射。

### FR-P1-13 后续通知与影响评估衔接

1. 大版本发布记录必须保存发布时具有查看资格的关联方范围快照。
2. 大版本发布记录必须保存发布时关联文件及其版本快照。
3. 第一阶段只保证这些快照可审计、可供后续流程消费，不宣称消息已经送达或关联文件已经完成影响评估。

## Business Rules

- BR-P1-01：逻辑文件身份一旦存在，不得通过普通元数据编辑把它移动到另一个项目、分类叶子或文件编码。
- BR-P1-02：版本号由系统生成；前端展示值不是权威输入。
- BR-P1-03：小版本是同一大版本内的不可变迭代记录，不是审批结论。
- BR-P1-04：检入生成小版本，但不会自动成为正式版本。
- BR-P1-04A：检入必须产生内容或允许元数据的真实差异；仅元数据变更也生成新小版本，空操作不生成版本。
- BR-P1-05：一个大版本可以有多个小版本，但只能由当前最新小版本进入审批；历史小版本只能用于追溯或作为下一大版本的明确来源。
- BR-P1-06：已送审小版本内容不可修改；修改必须形成下一小版本并重新送审。
- BR-P1-07：用户可以从当前大版本下选择任意历史小版本创建下一大版本，系统必须忠实使用所选来源。
- BR-P1-08：非当前正式版本作为大版本来源时必须说明理由，且选择记录不可修改。
- BR-P1-08A：选择历史小版本创建下一大版本只允许项目 OWNER；不增加独立预审批，来源和理由进入后续正式审批快照。
- BR-P1-09：一个逻辑文件最多有一个当前正式版本、一个开放大版本、一个未完成送审版本和一个有效检出锁。
- BR-P1-10：正式版本仍有效时，新的工作版本、审批版本或发布失败版本都不能替代其普通阅读入口。
- BR-P1-11：审批、发布和历史记录绑定到具体 `Revision / Iteration`，不能只绑定逻辑文件或大版本字母。
- BR-P1-12：已发布大版本不得通过普通检入继续增加小版本；再次正式修改必须创建下一大版本。
- BR-P1-13：历史版本不得删除；第一阶段仅允许撤销尚未检入的个人工作副本。
- BR-P1-14：关联文件在本阶段不会自动升版，大版本发布快照也不能被解释为影响评估已经完成。
- BR-P1-15：项目访问级别为 OWNER、EDIT、VIEW；OWNER 包含 EDIT 和 VIEW，EDIT 包含 VIEW。菜单权限、项目负责人文本和临时项目修正任务都不能代替正式项目访问规则。

## States and Transitions

版本生命周期状态与检出锁是两套不同状态。检出只表示编辑权被占用，不代表版本已进入审批或已经生效。

| 当前状态 | 用户动作或系统事件 | 下一状态 | 结果 |
|---|---|---|---|
| 不存在 | 创建新逻辑文件 | A/1 工作中 | 建立逻辑文件和初始小版本 |
| 工作中且未检出 | 检出 | 工作中 + 已检出 | 产生个人工作副本，不增加版本 |
| 工作中且已检出 | 检入 | 下一小版本工作中 | 保存新版本并释放检出锁 |
| 工作中且已检出 | 撤销检出 | 原版本工作中 | 丢弃工作副本，不增加版本 |
| 工作中 | 提交具体小版本 | 审批中 | 锁定送审版本和审批快照 |
| 审批中 | 驳回 | 已驳回 | 保留该版本和审批记录 |
| 已驳回 | 检出并检入 | 下一小版本工作中 | 形成新的返工版本 |
| 审批中 | 批准 | 已批准/待发布 | 普通用户正式版本不变 |
| 已批准/待发布 | 文控发布成功 | 正式 | 新版本成为当前正式版本 |
| 已批准/待发布 | 文控发布失败 | 发布失败 | 旧正式版本继续有效 |
| 正式 | 新建修订版 | 下一字母 `/1` 工作中 | 记录选定来源，旧正式版本不变 |
| 原正式版本 | 新版本发布成功 | 已替代 | 从普通入口移出，保留历史 |

## Edge Cases

1. 两个用户同时检出：只能有一个成功，失败方看到当前检出人和检出时间。
2. 同一用户重复点击检出：不得刷新检出时间或生成第二个工作副本。
3. 检入请求重复到达：只能生成一个下一小版本。
4. 文件上传成功但版本记录失败：不得形成新版本，检出锁继续保留并明确报错。
5. 未上传新文件且元数据没有变化：拒绝检入，不增加小版本。
6. 仅元数据变化：生成新小版本，源文件内容哈希不变，但新小版本拥有独立受控文件记录和字段差异。
7. 检出期间账号停用：第一阶段不提供管理员直接解锁，必须作为后续交接/强制解锁流程阻塞处理。
8. 用户选择非当前正式小版本创建新大版本：必须展示当前正式版本与选定来源的差异，并要求填写理由。
9. 已存在开放大版本时再次创建下一大版本：请求必须失败并指向现有开放大版本。
10. 已送审版本尝试检出或修改：请求必须失败，不能修改审批对象。
11. 审批期间产生重复回调：不得重复改变状态、重复发布或产生多个正式版本。
12. 当前正式版本发布文件缺失：不得创建下一大版本或执行迁移，必须报告文件完整性阻塞。
13. 现有版本号无法按确定性规则映射：不得自动转换。
14. 分类节点后来增加子节点：已经使用该节点作为文件类型的历史身份不能被静默改变。
15. 项目停用：不得创建、检出、检入或新建大版本，但历史和当前正式版本仍按权限可追溯。

## Acceptance Criteria

- AC-P1-01：Given 两个请求使用相同项目、分类叶子和规范化文件编码，When 并发创建逻辑文件，Then 只能创建一个逻辑文件，另一个请求明确返回身份冲突。
- AC-P1-02：Given 文件编码相同但项目或分类叶子不同，When 分别创建逻辑文件，Then 两份逻辑文件均可合法存在。
- AC-P1-03：Given 用户创建新逻辑文件，When 创建成功，Then 系统自动生成 A/1，且页面不允许用户编辑版本号。
- AC-P1-04：Given A/1 未被检出，When 授权用户检出，Then A/1 显示检出人和时间，但不会生成 A/2。
- AC-P1-05：Given A/1 已由当前用户检出，When 用户上传修改文件并检入，Then 系统生成 A/2、保留 A/1 并释放检出锁。
- AC-P1-06：Given 用户已检出 A/2，When 撤销检出，Then 不生成 A/3，A/2 保持不变并保留撤销审计。
- AC-P1-07：Given A/1、A/2、A/3 均存在，When 用户选择 A/2 创建下一大版本，Then 系统创建 B/1 并显示“来源于 A/2”，不得改用 A/3。
- AC-P1-08：Given A/3 是当前正式版本且用户选择 A/2 作为 B/1 来源，When 未填写选择理由，Then 系统拒绝创建 B/1。
- AC-P1-09：Given B/1、B/2、B/3 均存在且 B/3 是最新工作小版本，When 文件责任人提交审批，Then 系统只允许提交 B/3 并锁定其文件哈希；提交 B/1 或 B/2 必须被拒绝。
- AC-P1-10：Given B/3 正在审批，When 任意用户尝试修改或检出 B/3，Then 系统拒绝且审批对象保持不变。
- AC-P1-11：Given B/3 被驳回，When 编制人员修改并检入，Then 系统生成 B/4，B/3 和原审批记录继续保留。
- AC-P1-12：Given B/4 审批通过但尚未发布，When 普通用户打开文件，Then 仍看到原正式版本 A/x。
- AC-P1-13：Given B/4 发布成功，When 普通用户再次打开文件，Then 只看到 B/4 为当前正式版本，原 A/x 标记为已替代。
- AC-P1-14：Given B/4 发布失败，When 查询当前正式版本，Then 原 A/x 仍然有效且 B/4 不进入普通阅读入口。
- AC-P1-15：Given 历史数据缺少项目或分类叶子，When 执行迁移预检，Then 输出明确阻塞项且不修改该数据。
- AC-P1-16：Given 大版本发布完成，When 审计人员查看发布记录，Then 可以看到发布时关联方范围和关联文件版本快照，但系统不将其标记为已通知或已完成影响评估。
- AC-P1-17：Given 当前 Revision 为 Z，When 项目 OWNER 创建下一大版本，Then 系统自动创建 AA/1；Given 当前为 AZ，Then 下一大版本为 BA/1。
- AC-P1-18：Given 用户只修改允许的业务元数据，When 检入，Then 系统创建下一小版本、保留相同内容哈希并记录字段差异。
- AC-P1-19：Given 用户未上传新文件且没有元数据差异，When 检入，Then 系统拒绝且不增加小版本。
- AC-P1-20：Given 用户只有项目 VIEW，When 尝试检出或创建 Revision，Then 系统拒绝；Given 用户为项目 OWNER，When 选择非当前正式小版本并填写理由，Then 可以创建下一 Revision。

完整验收集合见 `docs/product/dcc-windchill-version-phase1-acceptance-criteria.md`。

- 未完成现有 DCC 主档和版本数据只读盘点前，不得批准正式迁移方案。
- 任何现有文件缺少 `dccProjectCodeId`、有效分类叶子或唯一文件编码时，必须先完成业务确认，不能自动补默认值。
