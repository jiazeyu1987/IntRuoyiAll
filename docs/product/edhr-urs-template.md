## 11. 需求书写规则

正式需求应符合以下规则：

- 每条需求只描述一个可验证要求。
- 每条需求使用唯一编号。
- 每条需求使用“系统应……”或“系统不得……”表述。
- 每条需求应避免写实现方案，除非该实现方式本身是法规、质量或业务强制要求。
- 每条需求应能追踪到来源、风险、设计、测试和验证结论。
- 不应使用“完善”“友好”“强大”“尽量”“支持相关功能”等无法客观验收的表述。

推荐语言：

- 系统应在 `[触发条件]` 时 `[执行动作]`，并 `[可观察结果或验收标准]`。
- 系统不得在 `[禁止条件]` 下 `[禁止动作]`。
- 当 `[异常条件]` 发生时，系统应 `[阻止 / 提示 / 记录 / 通知 / 进入指定状态]`。

示例：

| 不推荐写法 | 推荐写法 |
| --- | --- |
| 系统应具有完善的审计功能。 | 系统应记录关键数据修改的修改前值、修改后值、操作人、操作时间和修改原因。 |
| 系统应支持电子签名。 | 系统应在记录提交时要求签名人重新输入身份凭证，并将签名人、签署时间、签署含义和被签记录绑定保存。 |
| 系统应保证数据安全。 | 系统应禁止无放行权限的用户执行批记录最终放行操作。 |

## 15. 验收准则

系统满足本 URS 的最低条件如下：

- 所有 `必须` 需求均已完成设计评审，并在 RTM 中追踪到测试证据。
- 所有 GxP / 质量影响为 `是` 的需求均已完成风险评估。
- 所有高风险需求均已有 OQ、PQ、SEC、DI 或 RT 测试证据。
- 所有测试偏差均已关闭，或已有经质量批准的处理结论。
- 未完成需求已列入批准的限制清单、开放问题或后续版本计划，不得冒充已验证完成。

## 19. 附录 A：验证方式定义

| 缩写 | 名称 | 说明 |
| --- | --- | --- |
| DR | Design Review | 通过设计、配置或文件评审确认 |
| IQ | Installation Qualification | 确认系统安装、环境、版本和配置 |
| OQ | Operational Qualification | 确认系统功能、边界、权限、异常处理 |
| PQ | Performance Qualification | 使用真实或代表性业务流程确认系统适合预定用途 |
| UAT | User Acceptance Testing | 用户验收测试 |
| SEC | Security Test | 权限、账号、职责分离和安全控制测试 |
| DI | Data Integrity Test | 数据完整性、审计追踪、记录绑定和只读控制测试 |
| RT | Recovery Test | 备份、恢复、灾备和补录演练 |
| RTM | Requirements Traceability Matrix | 需求追踪矩阵 |
