# 生产一线简化报工、工序池与资源分配项目简述

## Purpose and Scope

本文件记录本次线程中形成的业务构想：在现有批记录系统被业务认可的基础上，以现有生产报工为一线主入口，在报工提交时同步采集与批记录相关的简化事实数据。它的目标不是推翻现有批记录或报工系统，而是把一线报工、PQC 过程检验记录、批记录相关数据采集、工序池归集、生产工单先进先出消耗、审核副本生成和正式批记录追溯之间的关系说明清楚。

本文件只沉淀本次线程的用户说明和当前理解，不代表已经完成设计、开发或验收。

## Problem Statement

当前批记录系统能够承载正式记录和审核归档，但一线员工在实际滚动生产中只需要按自己当前工序记录少量事实数据。业务希望一线填写不要被完整工艺路线强制限制，也不要要求员工填写与当前工序无关的复杂信息。

同时，业务仍需要保留原始记录、记录修改日志，并在审核时形成一份接近业务限制的副本，用于后续审核、归档和正式批记录链路。

最新业务口径明确：生产一线员工实际做的是报工，但这个入口同时也是记录本入口。系统是在员工报工时要求补充批记录相关内容；一线员工点击确定提交后，系统应在同一次提交中完成报工，并把批记录相关原始内容写入记录本。这里不是两个割裂入口，也不是记录本反向生成报工，而是“报工 + 记录本”结合在一起的组合入口。

最新补充强调：最主要的是“工序池”概念。所有员工的报工、记录本原始数据和 PQC 过程检验记录不是直接散落到订单上，而是先按工序汇入对应工序池。生产工单再从各工序池按数量取用或满足，工序是否完成也通过该生产工单在对应工序池中的累计完成数量判断；PQC 过程检验记录作为工序池的质量过程明细，影响质量状态、可分配数量和后续审核追溯。

提交到工序池的统一对象建议命名为“工序池提交事件”。不管来源模板是报工、记录本字段、损耗单还是 PQC 过程检验，每次确定提交都形成一条工序池提交事件。该事件有两个所有模板共通的强锚点：唯一电子签名和唯一提交时间。基于提交时间，工序池可以形成时间甘特图，展示每天谁在什么时间提交了什么内容。

最新设备口径明确：生产现场设备数量有限，设备上登录的是一个可操作账号，不是每个员工都切换系统账号。该账号绑定 `X` 个工艺路线，且 `X >= 1`；在该账号内可以切换这些工艺路线对应的所有工序。实际填写时，员工是在这个已登录账号里切换到自己，系统根据“账号可用工艺路线/工序 + 当前选择员工”加载该员工对应的固定 UI 模板。员工填写完成后进行电子签名并结束本次工序池提交事件。

## Target Users

- 生产一线员工：按当前工序填写简单生产事实。
- PQC 人员：记录过程检验结果；第一版录入可以简化为成功或失败，但过程检验记录要进入对应工序池。
- 审核人员：查看原始记录和按规则调整后的审核副本。
- 生产管理人员：查看工序池、资源消耗和 FIFO 满足情况。
- 系统管理员或工艺管理员：维护账号可切换工序、工序绑定员工和固定 UI 模板。
- 设备端共享账号管理员：维护设备上登录账号可切换的工艺路线、工序范围和可选员工范围。

## Core Scenarios

1. 有限设备上先登录一个可操作账号；该账号绑定 `X` 个工艺路线，且 `X >= 1`。
2. 员工在该账号内切换账号已绑定工艺路线对应的工序；这里切换的是工艺路线和工序，不是切换系统登录账号。
3. 员工选择某个工序后，只能切换绑定到该工序的员工。
4. 实际填写人切换到自己后，系统根据该员工和当前工序加载对应的固定 UI 模板。
5. 员工在报工页面或一线报工模式中填写上一个工序的输入数量、设备参数、输出数量、损耗数量等简化字段。
6. 同一工序的数据可能由一个人一次填完，也可能拆成多个人、多个字段或多次报工分片填写。
7. 系统从同一组页面数据中拆分报工信息和批记录相关信息：输出、损耗等进入报工链路；上一个工序输入数量、设备、设备参数等进入记录本和批记录审核链路。
8. 系统将员工点击确定提交的服务端时间作为默认事件时间，不要求员工手动填写报工时间或记录时间。
9. 员工点击确定提交时，系统在同一业务事务中保存或提交报工，并保存批记录相关原始数据、来源关联和事件日志；同时形成一条“工序池提交事件”。
10. 员工对本次工序池提交事件进行电子签名，签名主体是实际填写员工，不是设备端共享登录账号。
11. PQC 人员记录该工序的过程检验记录；第一版可以简化录入成功或失败，但必须作为工序池质量过程明细保存。
12. 工艺流程仍可设置路线，但实际填报不按前后置路线强制限制，因为实际生产是并行滚动的。
13. 报工形成的当前工序产出先进入对应工序池，形成可追溯的工序池流水。
14. 同一生产工单同一工序的多次报工数量需要在对应工序池中累计，工序是否完成通过累计完成数量是否达到工单或任务要求数量判断，而不是通过路线顺序或某一张记录是否填完判断。
15. 生产工单从各工序池消耗或满足数量，按生产工单计划开工时间排序，先计划开工的生产工单优先满足。
16. 工序池可基于工序池提交事件的唯一提交时间生成时间甘特图，展示每天谁提交了什么模板内容、数量、设备参数或 PQC 过程检验记录。
17. 审核时系统基于限制规则生成审核副本；例如范围为 `20~40` 的字段，原始输入 `50` 时副本调整为 `40`，原始输入 `10` 时副本调整为 `20`。
18. 原始数据和调整后的审核副本都需要保留。
19. 原始记录提交后允许修改，但必须保留修改日志。

## First Version Goal

第一版建议聚焦在可验证的最小闭环：

- 固定几类生产一线填报模板。
- 固定几类 PQC 简化模板。
- 以报工确定提交为主入口的一次提交双提取：报工信息进入生产报工，批记录相关信息进入记录本、字段审计和审核副本链路。
- 支持同一生产工单同一工序由一个人或多个人分片填写，并按报工数量累计判断工序完成。
- 工序池记录 PQC 过程检验记录，并把检验结果纳入质量状态、待检/可分配数量和审核追溯。
- 统一“工序池提交事件”对象，所有模板提交都带唯一电子签名和唯一提交时间。
- 基于工序池提交事件生成按时间展示的工序池甘特图。
- 支持有限设备上的共享登录账号：账号绑定一个或多个工艺路线，员工在账号内切换工序和实际填写人。
- 账号到工序的授权限制。
- 工序到员工的绑定与切换限制。
- 原始记录保存、修改和修改日志。
- 提交时间自动记录。
- 审核副本生成与超限值按边界调整。
- 工序池流水记录。
- 订单按生产工单计划开工时间 FIFO 消耗各工序池数量的基础分配明细。

这 12 个里程碑也可以合并成 4 个大阶段：M0-M1 是需求和模型基础；M2-M4 是一线填报闭环；M5-M7 是工序池、PQC 和 FIFO 数量闭环；M8-M12 是审计、审核、看板、集成和上线验收。

## Existing System Integration Approach

总体策略是复用现有 eDHR、记录本、生产报工、资源池、生产工单、字段审计和权限候选能力，在它们之间补齐少量桥接字段与规则，不新增一套孤立的一线生产系统。当前业务口径明确不考虑排产系统，订单只考虑生产工单；一线入口同时承担报工入口和记录本入口职责，批记录相关内容随报工一起提交并写入记录本；所有一线提交先进入对应工序池，再由生产工单按数量满足。设备端登录账号应理解为有限设备上的操作入口账号，实际填写人与电子签名仍按员工身份记录。

### Process Pool Model

工序池是本方案的核心聚合层。它不是一个全局大池，也不是某个员工的临时草稿，而是按工序维度组织的生产事实池。每个工序池收集该工序下所有一线员工的组合提交，包括输入数量、设备参数、输出数量、损耗数量、报工来源、记录本来源和 PQC 过程检验记录。

| 工序池要素 | 含义 |
| --- | --- |
| 池维度 | 至少包含生产工单、生产任务、工序、路线工序、产品/物料、批号或批次、质量状态；是否包含设备、班次、日期需要后续确认。 |
| 入池来源 | 一线员工点击提交后的组合记录：一条工序池提交事件，关联一条报工明细、一条或多条记录本原始条目，必要时关联 PQC 过程检验记录。 |
| 统一事件 | 建议统一命名为“工序池提交事件”；每条事件必须有唯一电子签名、唯一提交时间、登录账号、实际填写员工、模板类型、工序池上下文和原始 payload。 |
| 池内明细 | 保留每个人、每次提交、每台设备、每组参数、每次数量、损耗原因和 PQC 过程检验记录，不覆盖原始分片。 |
| 质量过程 | PQC 过程检验记录作为工序池质量过程明细，记录检测结论、检验来源和质量状态变化。 |
| 数量口径 | 输入数量、完成数量、合格数量、不合格/损耗数量、待检数量、PQC 通过数量、PQC 失败数量、可分配数量需要分别留痕。 |
| 出池/满足 | 生产工单按计划开始时间 FIFO，从对应工序池取数量或被对应工序池数量满足。 |
| 完成判断 | 某生产工单的某工序累计完成数量达到该工序要求数量时，才判断该工序完成。 |
| 时间视图 | 以工序池提交事件的提交时间为横轴，电子签名/提交人和模板内容为明细，可生成每天谁提交了什么内容的时间甘特图。 |

因此，“资源池”和本方案的“工序池”不是同一个概念。当前方案需要新增正式工序池，用来承载工序池提交事件、记录本原始事实、PQC 过程检验、审核副本来源、实际填写员工、电子签名和生产工单 FIFO 满足关系；现有报工余量池只能作为参考或下游可分配余量表，不能直接等同于工序池。

当前系统已存在一个资源池能力：`mes_pro_feedback_surplus_pool`，代码对象是 `MesProFeedbackSurplusPoolDO`，配套分配流水是 `mes_pro_feedback_surplus_allocation` / `MesProFeedbackSurplusAllocationDO`。它的现有定位是“MES 报工工序余量池”，主要用于报工超产余量、系统外其他订单和按 `processId` 查询可用余量。它不是本方案需要的完整工序池。

现有余量池与本方案工序池之间的差距包括：现有表仍包含排产工单字段和预留目标排产字段，缺少生产工单 FIFO 的正式目标字段；它按基础 `processId` 组织，不足以表达路线工序、设备、登录账号、实际填写员工、电子签名、提交时间、记录本条目、PQC 过程检验记录、审核副本和工序池提交事件。后续设计必须新增工序池，现有余量池只允许作为工序池之后的下游余量承载或兼容既有报工余量逻辑。

### Split Fill And Quantity Completion Model

同一个生产工单下的同一个工序，可以有两种填写方式：

### Minimal New Or Adjusted Scope

- 记录本条目需要补齐可检索的生产上下文字段：批次执行、生产工单、路线工序、工序、实际填写员工、设备或工作站等；如果现有标签只能展示不能稳定查询，则需要正式字段，不用标签替代正式关联。
- 一线记录模板需要把“输入结构校验”和“审核限制规则”分开。当前记录本字段支持 `min/max`，但一线原始记录不能因此拦截 `10` 或 `50` 这类超限值；第一版审核副本规则只处理上下限。
- 报工和记录本条目需要能双向追溯。优先在组合提交结果中保存 `feedbackId` 与 `recordbookEntryId` 的正式关联，资源池继续通过 `sourceFeedbackId` 追溯报工来源；必要时在报工或资源池侧增加 `sourceRecordbookEntryId`，避免只靠备注或文本匹配。
- 多人分片填写时，原始记录本条目不互相覆盖；审核副本可以按生产工单、工序和字段规则聚合生成。
- 工序完成状态需要明确“应完成数量”的来源，优先使用生产任务或工单中已存在的目标数量字段；若某工序存在损耗或返工，完成数量、合格数量和可进入资源池数量要分别定义。
- 工序池需要新增正式工序池主表、事件表和分配明细，现有报工余量池不能作为工序池主表。
- 工序池需要有正式 PQC 过程检验记录维度，至少能追溯检验记录来源、检验结果、关联报工/记录本、质量状态变化和对可分配数量的影响。
- 工序池提交事件需要正式表或正式事件对象承载，至少包含电子签名编号、提交时间、提交人、员工、工序池上下文、模板类型、来源单据和原始 payload。
- 设备端共享账号需要正式表达“登录账号绑定工艺路线集合”“工艺路线投影可切换工序集合”“工序绑定可选员工集合”“员工绑定 UI 模板集合”。实际填写员工和登录账号必须同时留痕，不能只保存其中一个。
- 工序池分配逻辑需要按生产工单 `plannedStartTime` 排序，并落正式 `targetWorkOrderId` / `targetWorkOrderCode`；已经 FIFO 分配给生产工单的原始记录不得再修改。
- 前端建议在现有报工表单上增加“一线报工模式”，或新增一个更简化的报工变体入口；底层仍使用报工、记录本、工序任务候选和新增工序池接口，不另起新应用。
- 后端建议新增组合提交服务或扩展报工保存/提交请求，明确承载批记录相关 payload，并把报工保存、记录本保存、事件日志和来源关联放在同一事务内。

### Boundary Rules

- 一线报工不使用 eDHR 批次任务的路线前后置 `available/canOpenTask` 作为提交门禁；路线只作为工序上下文和后续正式批记录追溯依据。
- 一线入口既是报工入口，也是记录本入口；点击提交后同一事务既完成报工，也写入记录本。
- 一线入口不是“先记录本、再报工”或“先报工、再人工补记录本”的割裂流程；同一次提交中的报工数据和记录本数据必须建立正式来源关联。
- 一线分片填写不等于工序完成；工序完成只能由累计数量达成规则判断。
- 工序池是数量完成和 FIFO 满足的核心依据；不能只从单条报工、单条记录本或全局资源池推断工序完成。
- PQC 过程检验记录必须归入对应工序池，不能成为与工序池脱节的独立质检记录。
- 所有进入工序池的数据必须通过工序池提交事件归档；不能绕过唯一电子签名和唯一提交时间直接改池内汇总数。
- 设备端账号只是现场设备上的系统入口；实际填写员工、电子签名员工和工序池提交事件责任主体必须是员工本人。
- 切换用户不是切换账号；系统登录态可以保持设备端账号，员工在账号内切换到自己时不需要额外身份验证，电子签名即代表本次提交身份。
- 一线模式不得信任前端手填报工时间；报工时间和记录本提交时间应由后端在确定提交时生成。
- 工序池与现有报工余量池是两个概念；不能用现有 `mes_pro_feedback_surplus_pool` 替代新增工序池。
- 审核副本第一版只处理上下限规则，不处理设备参数、损耗比例、PQC 状态等复杂规则。
- 原始记录修改必须重新电子签名；已经 FIFO 分配给生产工单的原始记录不能修改。
- 正式批记录表单仍从工序设置里的逐工序批记录表单绑定读取，不能由记录本模板、表单槽位 `formBindings` 或工序开始配置推断。
- 记录本保存事实，批记录保存审核后的正式表达；两者通过字段审计和审核副本关联，不互相覆盖。
- 缺少模板、员工授权、生产工单计划开工时间、新增工序池维度或正式批记录绑定时必须阻塞，不用默认模板、空工序池或模拟成功掩盖。

## Non-Goals

- 不在第一版推翻或替换现有正式批记录系统。
- 不新增一套与 eDHR、记录本、报工、生产工单和资源池脱离的独立系统。
- 不把一线入口设计成脱离报工的独立记录本提交入口，也不把记录本写入排除在报工提交之外。
- 不把表单槽位 `formBindings` 当作正式“批记录表单”的来源。
- 不把“工序开始”上传人、附件负责人等配置当作批记录表单或一线填报模板。
- 不在一线填报时强制执行完整工艺路线前后置限制。
- 不把所有工序产出混入一个无工序维度的全局资源池。
- 不把现有报工工序余量池当作本方案新增工序池。
- 不用默认值、模拟成功或静默降级掩盖缺少的正式绑定、模板、员工授权或资源池规则。

## Constraints

- 生产一线填写必须简化，只要求当前工序相关事实数据。
- 一线员工点击确定提交应同时完成报工和记录本写入，且两者需要正式来源关联。
- 同一生产工单同一工序允许多人、多次分片填写，但最终必须能按工单和工序汇总数量。
- 工序完成判断以数量达成为准，不以路线流转顺序、字段填写人数量或单条记录是否完成为准。
- 一线提交必须进入明确的工序池，工序池必须保留工序、生产工单、数量和来源记录的正式关联。
- PQC 过程检验记录必须进入对应工序池，并与质量状态、待检数量、PQC 通过/失败数量和可分配数量建立关系。
- 不管模板类型如何，每次提交必须形成唯一的工序池提交事件，并带唯一电子签名和唯一提交时间。
- 设备数量有限，设备端允许使用共享登录账号；该账号绑定至少一个工艺路线，并只能切换这些工艺路线对应的工序。
- 员工在设备端账号内切换到本人后填写；UI 必须跟随实际员工和当前工序切换。
- 电子签名和工序池提交事件责任主体必须绑定实际员工，不能只绑定设备登录账号。
- 员工在设备端账号内切换到自己时不做额外身份验证，电子签名代表身份。
- 工艺路线可以继续配置，但填报时不得因为路线顺序阻断并行滚动生产。
- FIFO 订单排序依据为计划开始时间。
- 审核副本允许调整超出限制的值，但原始数据必须保留。
- 审核副本第一版只处理上下限。
- 原始记录允许修改，但必须保留完整修改日志并重新电子签名。
- 已经 FIFO 分配给生产工单的原始记录不能修改。
- 员工 UI 使用固定几类模板，不采用无限自由配置作为当前已确认需求。
- 项目术语必须遵守现有边界：“批记录表单”“表单槽位”“工序开始”是不同配置入口，不能互相替代。
- 一线原始记录的超限值不能在提交时被 `min/max` 阻断；限制规则应在审核副本生成时执行并留痕。

## Success Criteria

- 一线员工能在授权工序内快速完成简化填报。
- 有限设备上的共享登录账号能按绑定工艺路线切换工序，员工能在账号内切换到本人并看到对应 UI。
- 一线员工通过组合入口一次点击提交后，系统能同时完成生产报工和记录本原始内容写入。
- 一个工序由多人拆分填写时，系统能保留各自原始记录，并正确汇总该工序的完成数量。
- 工序池能按工序展示输入、完成、合格、不合格、损耗、待检和可分配数量。
- 工序池能通过工序池提交事件生成时间甘特图，展示每天谁提交了什么内容。
- 工序完成状态能通过生产工单或任务的累计完成数量判断。
- PQC 能以过程检验记录形式进入对应工序池；第一版可用成功/失败简化录入。
- 提交时间由系统自动记录，不依赖员工手填。
- 原始记录、修改日志、审核副本可以同时追溯。
- 审核副本能按字段限制规则生成边界值调整结果。
- 工序池能记录一线产出和生产工单消耗的来源。
- 订单消耗顺序能按生产工单计划开工时间满足 FIFO 原则。
- 正式批记录链路和一线原始记录链路边界清楚。
- 方案复用现有 eDHR、记录本、报工和生产工单数据链路，并新增正式工序池；新增范围可解释、可追溯。

## Assumptions

- 现有批记录系统继续作为正式审核归档和追溯能力的一部分。
- 现有生产报工和记录本共同构成一线组合入口的两个落点。
- 现有记录本模板、条目和事件可以作为组合入口中批记录相关原始内容的主要承载。
- 固定 UI 模板数量有限，可以通过记录本模板类型、模板编码或枚举进行维护。
- 现有报工余量池和分配表不是工序池；新增工序池可以在必要时向现有余量池同步可分配余量，但不能复用其作为工序池主模型。
- 工序池需要使用流水、质量过程记录和分配明细，而不是只保存一个当前数量。
- 审核副本的调整规则第一版只处理上下限。
- 设备端共享登录账号可通过现有账号、工作站/设备、工艺路线权限和填写候选能力组合实现；员工切换到自己时不做额外验证，电子签名代表身份。

- PQC 过程检验记录的字段清单、记录模板、与正式 IPQC/过程检验单的关系需要确认。
- PQC 过程检验记录是否由 PQC 人员在一线组合入口录入，还是从现有质量模块同步到工序池，需要确认。
- 原始记录修改是否必须填写修改原因，是否需要审批。
- 审核副本生成后是否允许人工二次修改，以及修改日志如何保存。
- 固定 UI 模板的第一批模板类型和字段清单需要业务确认。

- 记录本条目上下文字段、报工来源字段和工序池来源/目标字段是否已经足够，不足部分需要正式 schema 设计。
- `工序是否报工` 为 `/` 但会形成批记录的工序，组合入口应只写记录本还是也要补齐 MES 报工，需要逐工序确认。
