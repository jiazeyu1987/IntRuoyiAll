# 生产一线简化填报与资源池分配项目简述

## Purpose and Scope

本文件记录本次线程中形成的业务构想：在现有批记录系统被业务认可的基础上，以现有生产报工为一线主入口，在报工提交时同步采集与批记录相关的简化事实数据。它的目标不是推翻现有批记录或报工系统，而是把一线报工、批记录相关数据采集、资源池归集、生产工单先进先出消耗、审核副本生成和正式批记录追溯之间的关系说明清楚。

本文件只沉淀本次线程的用户说明和当前理解，不代表已经完成设计、开发或验收。

## Problem Statement

当前批记录系统能够承载正式记录和审核归档，但一线员工在实际滚动生产中只需要按自己当前工序记录少量事实数据。业务希望一线填写不要被完整工艺路线强制限制，也不要要求员工填写与当前工序无关的复杂信息。

同时，业务仍需要保留原始记录、记录修改日志，并在审核时形成一份接近业务限制的副本，用于后续审核、归档和正式批记录链路。

最新业务口径明确：生产一线员工实际做的是报工；系统是在员工报工时要求补充批记录相关内容。因此一线员工点击确定提交时，系统应能从同一次提交中提取报工信息和批记录相关信息，而不是让员工先单独填写记录本、再由记录本反向生成报工。

## Target Users

- 生产一线员工：按当前工序填写简单生产事实。
- PQC 人员：按简化方式记录检测成功或失败。
- 审核人员：查看原始记录和按规则调整后的审核副本。
- 生产管理人员：查看资源池、订单消耗和 FIFO 满足情况。
- 系统管理员或工艺管理员：维护账号可切换工序、工序绑定员工和固定 UI 模板。

## Core Scenarios

1. 生产员工进入填报页面后，只能在账号授权的工序范围内切换工序。
2. 员工选择某个工序后，只能切换绑定到该工序的员工。
3. 切换员工后，系统根据该员工和工序加载对应的固定 UI 模板。
4. 员工在报工页面或一线报工模式中填写上一个工序的输入数量、设备参数、输出数量、损耗数量等简化字段。
5. 系统从同一组页面数据中拆分报工信息和批记录相关信息：输出、损耗等进入报工链路；上一个工序输入数量、设备、设备参数等进入记录本和批记录审核链路。
6. 系统将员工点击确定提交的服务端时间作为默认事件时间，不要求员工手动填写报工时间或记录时间。
7. 员工点击确定提交时，系统在同一业务事务中保存或提交报工，并保存批记录相关原始数据、来源关联和事件日志。
8. PQC 人员只记录检测成功或失败。
9. 工艺流程仍可设置路线，但实际填报不按前后置路线强制限制，因为实际生产是并行滚动的。
10. 报工形成的产出进入资源池，形成可追溯的资源流水。
11. 订单从资源池消耗数量，按生产工单计划开工时间排序，先计划开工的生产工单优先满足。
12. 审核时系统基于限制规则生成审核副本；例如范围为 `20~40` 的字段，原始输入 `50` 时副本调整为 `40`，原始输入 `10` 时副本调整为 `20`。
13. 原始数据和调整后的审核副本都需要保留。
14. 原始记录提交后允许修改，但必须保留修改日志。

## First Version Goal

第一版建议聚焦在可验证的最小闭环：

- 固定几类生产一线填报模板。
- 固定几类 PQC 简化模板。
- 以报工确定提交为主入口的一次提交双提取：报工信息进入生产报工，批记录相关信息进入记录本、字段审计和审核副本链路。
- 账号到工序的授权限制。
- 工序到员工的绑定与切换限制。
- 原始记录保存、修改和修改日志。
- 提交时间自动记录。
- 审核副本生成与超限值按边界调整。
- 资源池流水记录。
- 订单按生产工单计划开工时间 FIFO 消耗资源的基础分配明细。

## Existing System Integration Approach

总体策略是复用现有 eDHR、记录本、生产报工、资源池、生产工单、字段审计和权限候选能力，在它们之间补齐少量桥接字段与规则，不新增一套孤立的一线生产系统。当前业务口径明确不考虑排产系统，订单只考虑生产工单；一线员工的主动作是报工，批记录相关内容嵌入报工提交过程。

### Feedback-Centered Submission Model

一线入口应理解为“报工 + 批记录相关字段”的组合提交：

| 提交内容 | 归属链路 | 说明 |
| --- | --- | --- |
| 生产工单、生产任务、工序、工作站、报工人、输出数量、合格/不合格/待检数量、损耗数量 | 现有生产报工 | 进入 `mes_pro_feedback` 及后续报工审批、产出、消耗和资源池链路。 |
| 上一个工序输入数量、设备参数、固定模板内的批记录相关字段 | eDHR 记录本与批记录审核链路 | 作为原始事实保存到记录本条目，后续生成审核副本和字段审计。 |
| 员工点击确定提交的时间 | 报工时间与记录本提交时间 | 一线模式不让员工手填；后端以服务端提交时间写入，避免前端时间被当作可信来源。 |
| PQC 成功/失败 | 简化 PQC 记录与质量状态 | 第一版先保存成功/失败事实；是否同步到正式 IPQC、待检数量或不良数量，需要后续规则确认。 |

提交处理建议是一个正式的组合接口，或在现有报工保存/提交请求中增加明确的 `recordbookPayload` / `batchRecordPayload`。无论采用哪种接口形态，都应在同一事务中完成：校验报工上下文、校验员工和工序权限、校验模板存在、保存或提交报工、保存记录本原始内容、写入记录本事件、建立报工与记录本条目的来源关联。任一前置条件缺失时应整体失败，不做报工成功但批记录丢失的部分成功。

### Reuse Existing Capabilities

| 业务需求 | 优先复用的现有能力 | 结合方式 |
| --- | --- | --- |
| 一线报工内嵌批记录填写 | 现有生产报工 UI/API、eDHR 记录本模板与条目 | 报工是主入口；使用现有报工上下文承载生产工单、任务、工序、工作站和数量字段，使用 `mes_pro_edhr_recordbook_template.entry_schema_json` 表达固定几类批记录相关字段，使用 `mes_pro_edhr_recordbook_entry.entry_content_json` 保存原始填写内容。 |
| 原始记录修改日志 | eDHR 记录本事件 | 复用 `mes_pro_edhr_recordbook_event` 记录提交、修改、失败等事件；修改事件需要保存修改前、修改后、字段差异、修改人和修改时间。 |
| 员工默认填写时间 | 记录本条目提交时间、报工时间 | 一线模式前端不暴露手填时间；后端以提交事务时间写入 `submittedAt` / `feedbackTime`。当前通用报工表单仍存在报工时间控件，后续实现一线模式时需要收敛为服务端确定时间。 |
| 账号限制工序、员工切换 | eDHR 工序任务、候选人快照、填写人规则 | 复用 `routeProcessId`、`candidateUserSnapshot`、`fillableUsers`、过程表单填写人规则，生成账号可切换工序和工序可选员工。 |
| 固定几类 UI 模板 | 记录本模板类型与前端固定组件 | 按 `recordbookType` 或模板编码加载固定 Vue 组件；模板 schema 用来约束字段身份，不用它生成无限自由表单。 |
| PQC 简化输入 | 现有 QC/IPQC 领域和工序 `checkFlag` | 第一版可用记录本的 `PQC_SIMPLE` 模板保存成功/失败；需要进入正式质检链路时再同步到现有 IPQC 结果，而不是让一线填完整检验单。 |
| 输出、损耗、报工 | 现有生产报工 | 报工链路直接接收输出数量、合格数量、待检/不合格数量和损耗字段；上一个工序输入数量、设备参数等不硬塞进报工表，而是和同一报工建立记录本/批记录来源关联。 |
| 资源池 | 现有报工剩余资源池 | 复用 `mes_pro_feedback_surplus_pool` 和 `mes_pro_feedback_surplus_allocation`，从已确认的报工产出产生入池流水，并记录生产工单消耗明细。 |
| FIFO 订单消耗 | 现有生产工单计划开工时间 | 使用 `mes_pro_work_order.planned_start_time` 作为 FIFO 排序依据。 |
| 审核副本 | 批记录执行与字段审计 | 将审核副本落到正式批记录执行草稿或审核态数据中；复用字段审计里的 `recordbookValueJson` / `batchRecordValueJson` 保存原始值与调整后值。 |

### Minimal New Or Adjusted Scope

- 记录本条目需要补齐可检索的生产上下文字段：批次执行、生产工单、路线工序、工序、实际填写员工、设备或工作站等；如果现有标签只能展示不能稳定查询，则需要正式字段，不用标签替代正式关联。
- 一线记录模板需要把“输入结构校验”和“审核限制规则”分开。当前记录本字段支持 `min/max`，但一线原始记录不能因此拦截 `10` 或 `50` 这类超限值；范围限制应进入审核副本规则。
- 报工和记录本条目需要能双向追溯。优先在组合提交结果中保存 `feedbackId` 与 `recordbookEntryId` 的正式关联，资源池继续通过 `sourceFeedbackId` 追溯报工来源；必要时在报工或资源池侧增加 `sourceRecordbookEntryId`，避免只靠备注或文本匹配。
- 资源池分配逻辑需要按生产工单 `plannedStartTime` 排序；如果现有资源池分配表只有排产目标字段或文本标签，则需要补齐正式 `targetWorkOrderId` / `targetWorkOrderCode`，不能用文本标签替代生产工单关联。
- 前端建议在现有报工表单上增加“一线报工模式”，或新增一个更简化的报工变体入口；底层仍使用报工、记录本、工序任务候选和资源池接口，不另起新应用。
- 后端建议新增组合提交服务或扩展报工保存/提交请求，明确承载批记录相关 payload，并把报工保存、记录本保存、事件日志和来源关联放在同一事务内。

### Boundary Rules

- 一线报工不使用 eDHR 批次任务的路线前后置 `available/canOpenTask` 作为提交门禁；路线只作为工序上下文和后续正式批记录追溯依据。
- 一线入口不是“记录本先提交、再生成报工”；报工确定提交是主事务，批记录相关数据从同一次提交中提取并落到记录本和审核副本链路。
- 一线模式不得信任前端手填报工时间；报工时间和记录本提交时间应由后端在确定提交时生成。
- 正式批记录表单仍从工序设置里的逐工序批记录表单绑定读取，不能由记录本模板、表单槽位 `formBindings` 或工序开始配置推断。
- 记录本保存事实，批记录保存审核后的正式表达；两者通过字段审计和审核副本关联，不互相覆盖。
- 缺少模板、员工授权、生产工单计划开工时间、资源池维度或正式批记录绑定时必须阻塞，不用默认模板、空资源池或模拟成功掩盖。

## Non-Goals

- 不在第一版推翻或替换现有正式批记录系统。
- 不新增一套与 eDHR、记录本、报工、生产工单和资源池脱离的独立系统。
- 不把一线入口设计成脱离报工的独立记录本提交入口。
- 不把表单槽位 `formBindings` 当作正式“批记录表单”的来源。
- 不把“工序开始”上传人、附件负责人等配置当作批记录表单或一线填报模板。
- 不在一线填报时强制执行完整工艺路线前后置限制。
- 不用默认值、模拟成功或静默降级掩盖缺少的正式绑定、模板、员工授权或资源池规则。

## Constraints

- 生产一线填写必须简化，只要求当前工序相关事实数据。
- 一线员工点击确定提交应同时提取报工信息与批记录相关信息，且两者需要正式来源关联。
- 工艺路线可以继续配置，但填报时不得因为路线顺序阻断并行滚动生产。
- FIFO 订单排序依据为计划开始时间。
- 审核副本允许调整超出限制的值，但原始数据必须保留。
- 原始记录允许修改，但必须保留完整修改日志。
- 员工 UI 使用固定几类模板，不采用无限自由配置作为当前已确认需求。
- 项目术语必须遵守现有边界：“批记录表单”“表单槽位”“工序开始”是不同配置入口，不能互相替代。
- 一线原始记录的超限值不能在提交时被 `min/max` 阻断；限制规则应在审核副本生成时执行并留痕。

## Success Criteria

- 一线员工能在授权工序内快速完成简化填报。
- 一线员工通过报工入口一次点击提交后，系统能同时保存报工信息和批记录相关原始信息。
- PQC 能以成功或失败完成简化检测记录。
- 提交时间由系统自动记录，不依赖员工手填。
- 原始记录、修改日志、审核副本可以同时追溯。
- 审核副本能按字段限制规则生成边界值调整结果。
- 资源池能记录一线产出和订单消耗的来源。
- 订单消耗顺序能按生产工单计划开工时间满足 FIFO 原则。
- 正式批记录链路和一线原始记录链路边界清楚。
- 方案复用现有 eDHR、记录本、报工、资源池和生产工单数据链路，新增范围可解释、可追溯。

## Assumptions

- 现有批记录系统继续作为正式审核归档和追溯能力的一部分。
- 现有生产报工继续作为一线员工的主要业务入口。
- 现有记录本模板、条目和事件可以作为报工过程中批记录相关原始内容的主要承载。
- 固定 UI 模板数量有限，可以通过记录本模板类型、模板编码或枚举进行维护。
- 现有报工剩余资源池和分配表可以作为资源池与订单消耗的基础。
- 资源池需要使用流水和分配明细，而不是只保存一个当前数量。
- 审核副本的调整规则优先处理范围类限制；其它复杂限制尚未定义。

## Open Questions

- 资源池归集维度具体包括哪些字段：物料、产品、规格、批号、工序、设备、班次、日期、质量状态等是否都需要参与。
- 报工组合提交采用新增接口，还是扩展现有报工保存/提交请求；提交前保存草稿、确定提交和修改日志之间的状态机需要确认。
- 页面字段到报工字段、记录本字段和批记录字段的精确映射需要确认。
- 订单计划开始时间来自哪个正式字段，是否允许人工调整排序。
- 资源池分配是否需要区分合格、待检、失败、返工等质量状态。
- PQC 检测失败后，对资源池入池、订单消耗和审核副本的影响规则是什么。
- 原始记录修改是否必须填写修改原因，是否需要电子签名或审批。
- 审核副本生成后是否允许人工二次修改，以及修改日志如何保存。
- 固定 UI 模板的第一批模板类型和字段清单需要业务确认。
- 一线填报和现有记录本功能之间的数据边界、菜单入口和权限边界需要进一步确认。
- 生产工单 `plannedStartTime` 为空时如何处理，是否禁止进入 FIFO 分配。
- 记录本条目上下文字段、报工来源字段和资源池来源/目标字段是否已经足够，不足部分需要正式 schema 设计。

## Blockers

- 未确认资源池归集维度前，不能进入资源池数据模型最终设计。
- 未确认固定 UI 模板类型前，不能进入前端页面和后端模板模型开发。
- 未确认报工组合提交契约前，不能进入报工与批记录一体化接口开发。
- 未确认 PQC 失败对资源池和订单消耗的影响前，不能完成 FIFO 分配规则。
- 未确认原始记录修改日志字段和审批要求前，不能完成审计链路设计。
- 未把记录本提交校验和审核限制规则分离前，不能直接用带 `min/max` 的记录本模板承载一线超限原始输入。
- 若现有资源池分配表不能正式关联生产工单，只能记录文本标签或排产目标字段，则不能进入生产工单 FIFO 分配实现。

## Evidence Reviewed

- 本次线程用户消息：业务认可当前批记录系统，并提出生产一线简化填报、并行滚动生产、资源池、FIFO、审核副本、账号工序限制和员工切换等建议。
- 本次线程用户澄清：一线输入字段包括上一个工序输入数量、设备参数、输出数量、损耗数量；PQC 只判定成功或失败；FIFO 按计划开始时间排序；审核副本调整超限值；原始和调整后数据都保留；原始记录可修改但要记录修改日志；员工 UI 固定几类模板。
- 本次线程用户澄清：文档记录范围是本次线程对话，不是所有对话。
- 本次线程用户追问：如何与现有系统结合，尽量利用现有系统，少开发新的系统。
