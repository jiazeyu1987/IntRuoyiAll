## Confirmed Facts

- 业务同事认可当前批记录系统，但希望增加或调整一线简化填报能力。
- 生产一线员工只根据自己当前工序填写简单数据。
- 一线填写内容包括上一个工序的输入数量、设备参数、输出数量、损耗数量。
- PQC 第一版可采用简化输入，但工序池需要记录 PQC 的过程检验记录。
- 员工填写时间使用系统默认事件时间，不由员工手动填写。
- 工艺路线可以设置路线，但实际填写时不按路线顺序限制。
- 所有工序实际是并行、滚动生产。
- 员工填写内容汇入资源池。
- 订单从资源池取数量。
- FIFO 的订单排序依据为计划开始时间。
- 当前业务口径不考虑排产系统，订单只考虑生产工单。
- 当前业务口径要求结合现有报工系统，一线入口既是报工入口，也是记录本入口。
- 一线员工在报工时需要填写批记录相关内容。
- 一线员工点击确定提交时，系统需要从同一次提交中完成报工并写入记录本。
- 同一个生产工单、同一个工序的填写内容可能由一个人完成，也可能拆分给几个人完成。
- 工序是否完成通过数量判断，不通过路线顺序或单张记录是否填写完成判断。
- 工序池是当前业务模型的核心概念。
- 所有员工在某个工序的组合提交先进入对应工序池，再由生产工单按数量消耗或满足。
- 工序池需要保留输入数量、完成数量、合格数量、不合格/损耗数量、待检数量、可分配数量和来源记录。
- 工序池还需要记录 PQC 的过程检验记录，并把检验结果纳入质量状态和数量可用性判断。
- 所有模板的每次提交都有两个共通锚点：唯一电子签名和唯一提交时间。
- 提交到工序池的统一对象建议命名为“工序池提交事件”。
- 工序池可以基于提交时间生成时间甘特图，展示每天谁提交了什么内容。
- `批记录压力泵.doc` 中多数工序都包含 `生产数量/pcs`、`自检合格数量/pcs` 或 `合格数量/pcs`、`不合格数量/pcs`。
- `批记录压力泵.doc` 中清洗类、光固类、硅化Ⅰ、单包装等工序存在明确设备参数；清洁、硅化Ⅱ、组装Ⅱ、中包装、大包装未抽取到独立设备参数。
- `损耗单.doc` 中损耗相关字段包括生产数量、不合格日期、工序名称、不合格数量、不合格原因、处置方式、生产人员/日期、检验人员确认/日期、批准人/日期。
- 生产工单对象已有 `plannedStartTime` 字段，可作为生产工单 FIFO 的计划开工时间候选字段。
- 员工填写时不做强限制，保留原始记录数据。
- 审核时可以生成一份接近限制的副本。
- 审核副本允许修改超出限制的值，例如范围 `20~40` 时，输入 `50` 调整为 `40`，输入 `10` 调整为 `20`。
- 原始数据和修改之后的数据都要保留。
- 原始记录提交之后可以修改。
- 原始记录修改必须有日志记录。
- 员工 UI 固定几类模板。
- 一个账号可以限制可操作工序数量，只能切换对应工序。
- 员工可以切换，但只能切换绑定当前工序的员工。
- 切换员工时，对应 UI 也切换。
- 生产现场设备数量有限，设备上登录的是一个可操作账号，员工填写时是在该账号内切换用户，不是切换系统账号。
- 设备端登录账号绑定 `X` 个工艺路线，且 `X >= 1`。
- 设备端登录账号内可以切换这 `X` 个工艺路线对应的所有工序。
- 员工在设备端账号内切换到自己后，UI 切换为该员工对应的固定 UI 模板。
- 员工填写完成后需要进行电子签名，结束本次提交。
- 登录账号、实际填写员工、电子签名员工需要区分；工序池提交事件责任主体应是实际填写员工。
- 现有系统已经存在 eDHR 记录本模板、记录本条目、记录本事件、批次任务、填写候选人、字段审计、生产报工、报工余量池、余量分配和生产工单计划开工时间字段。
- 现有系统确实有资源池相关能力，主要是 `mes_pro_feedback_surplus_pool` 报工工序余量池和 `mes_pro_feedback_surplus_allocation` 余量分配流水。
- 现有报工工序余量池不是本方案要求的完整工序池；它当前更像报工余量/超产余量的池化与分配能力。
- 现有报工工序余量池和本方案新增工序池不是一个概念；本方案需要新增正式工序池。
- 现有余量池已有来源报工、来源导入记录、基础工序、产品、总数量、已分配数量、可用数量和状态字段。
- 现有余量池仍包含来源排产工单和目标排产工单字段，不符合本方案“不考虑排产系统、订单只考虑生产工单”的最终口径。
- 现有余量池缺少工序池提交事件、唯一电子签名、唯一提交时间、设备端登录账号、实际填写员工、记录本条目、PQC 过程检验记录和审核副本等关键维度。
- 现有记录本字段定义支持 `min/max` 范围，但一线原始记录不能在提交时用该范围阻断超限值。
- 员工在设备账号内切换到自己时，不需要额外身份验证；本次提交的电子签名代表实际员工身份。
- 审核副本规则第一版只处理上下限，不处理设备参数、损耗比例、PQC 状态等复杂规则。
- 原始记录修改必须重新电子签名。
- 已经 FIFO 分配给生产工单的原始记录不能修改。
- 实施顺序建议先冻结需求和工序池模型，再完成设备账号/员工/模板权限、一线报工组合提交、工序池数量汇总、PQC 入池、生产工单 FIFO 分配、原始记录修改与重签名、审核副本、时间甘特图、现有系统集成和试点验收。
- `压力泵工序.xlsx` 的 `工序名称` 是展示给一线员工的 MES 工序名称。
- `压力泵工序.xlsx` 的 `批记录工序名称` 是最终对外批记录使用的正式工序名称。
- MES 工序与批记录工序不是固定一对一关系，可以一对一、多道 MES 工序合并为一道批记录工序，也可以存在 MES 报工但不独立形成批记录的工序。
- `设备编码` 是实际设备身份；用户明确 `B09032/G01160` 表示两台机器。
- 设备名称是可选展示信息；没有设备名称时仍需保留设备编码。
- MES 工序编码和 10.5 小时日产能是可选主数据，并非每道 MES 工序都有。
- 当前压力泵工序分析只使用 `二代压力泵` 工作表；`一代压力泵`、`Sheet2` 和 `Sheet3` 不纳入本次需求。

## Assumptions

- “当前的记录本功能”可作为报工过程中批记录相关原始内容的承载；前端入口应把报工和记录本合在一个一线组合入口里。
- “批记录”继续承担正式记录、审核归档或追溯职责，但具体生成方式需要后续设计确认。
- 工序池需要新增正式主模型；现有报工剩余余量池只能作为参考或下游余量承载，不能作为工序池主模型。
- PQC 过程检验记录可先作为工序池质量过程明细保存；是否同步到正式 IPQC/过程检验单需要后续设计确认。
- “工序池提交事件”可以作为工序池的统一事实对象，关联报工、记录本、损耗单、PQC 过程检验记录和原始 payload。
- 固定 UI 模板可以通过记录本模板类型、模板编码或枚举项维护，具体实现方式尚未确认。
- 多人分片填写可以用多条报工记录和多条记录本条目保存原始事实，再按生产工单、任务、工序聚合。
- 设备端共享登录账号可优先复用现有账号、工作站/设备、工艺路线权限和填写候选能力组合实现；员工切换到自己时不做额外验证，电子签名代表身份。

## Decisions

- 本次文档只记录当前线程对话，不汇总其它项目历史对话。
- 初步方向是保留现有批记录系统，并以生产报工为一线主入口，在报工过程中嵌入批记录相关事实采集、工序池、FIFO 分配和审核副本链路。
- FIFO 排序依据确认为订单计划开始时间。
- 审核副本的范围类超限值按边界值调整，同时保留原始值。
- 原始记录允许修改，但必须保留修改日志。
- 员工 UI 使用固定几类模板。
- 结合现有系统的优先方向是：报工承载一线主提交和数量结果，记录本承载报工过程中采集的批记录相关原始事实，工序池承载每个工序的输入、产出、损耗和可分配数量聚合，生产工单计划开工时间承载 FIFO 排序，批记录执行和字段审计承载审核副本与原始/修正值对照。
- 一线入口应是现有报工表单的一线模式或简化报工变体，同时也是记录本入口；底层应复用 eDHR 记录本、工序任务候选和报工接口，并新增正式工序池接口。
- 员工点击确定提交时应在同一事务中保存/提交报工、写入记录本原始内容、写入记录本事件，并建立报工与记录本条目的来源关联；任一正式前置条件缺失时整体失败。
- 一线填报不使用路线前后置门禁作为提交限制；路线仅作为上下文和正式追溯依据。
- 正式批记录表单仍按逐工序批记录表单绑定读取，不能由记录本模板、表单槽位或工序开始配置替代。
- 基于 `批记录压力泵.doc` 的第一版一线字段可以按四类组织：上一个工序输入数量、设备参数、输出数量、损耗数量。
- `损耗单.doc` 可作为有损耗时的补充记录来源；一线基础模板只建议纳入工序名称、生产数量、不合格数量、损耗/不合格原因、处置方式、生产人员，检验确认和批准字段不放入一线基础模板。
- 一线填写支持一个人填完或多个人拆分填写，原始记录应保留分片明细。
- 工序完成判断以生产工单或生产任务下该工序累计完成数量为准；记录本填写完整性用于审核和追溯，不替代数量完成判断。
- 工序池是数量聚合、工序完成判断和生产工单 FIFO 满足的核心层；不能把所有工序混入一个无工序维度的全局资源池。

- 提交到工序池的统一对象建议命名为“工序池提交事件”；UI 上可显示为“提交记录”，但模型术语以“事件”表达不可篡改、可追溯、可上时间轴。
- 有限设备上的一线入口应支持“一个设备登录账号 + 多工艺路线 + 多工序 + 多员工切换”的现场操作方式；切换员工时 UI 跟随实际员工切换，提交时以实际员工完成电子签名。
- 现有系统有“报工工序余量池”，但它和本次方案的“工序池”不是一个概念；本方案需要新增正式工序池，现有余量池只能作为参考或下游余量表。

- 审核副本规则第一版只处理上下限。
