## Confirmed Facts

- 业务同事认可当前批记录系统，但希望增加或调整一线简化填报能力。
- 生产一线员工只根据自己当前工序填写简单数据。
- 一线填写内容包括上一个工序的输入数量、设备参数、输出数量、损耗数量。
- PQC 也采用简化输入，只判定检测成功或失败。
- 员工填写时间使用系统默认事件时间，不由员工手动填写。
- 工艺路线可以设置路线，但实际填写时不按路线顺序限制。
- 所有工序实际是并行、滚动生产。
- 员工填写内容汇入资源池。
- 订单从资源池取数量。
- FIFO 的订单排序依据为计划开始时间。
- 当前业务口径不考虑排产系统，订单只考虑生产工单。
- 当前业务口径要求结合现有报工系统，一线员工的主动作是报工。
- 一线员工在报工时需要填写批记录相关内容。
- 一线员工点击确定提交时，系统需要从同一次提交中提取批记录信息和报工信息。
- 生产工单对象已有 `plannedStartTime` 字段，可作为生产工单 FIFO 的计划开工时间候选字段。
- 员工填写时不做强限制，保留原始记录数据。
- 审核时可以生成一份接近限制的副本。
- 审核副本允许修改超出限制的值，例如范围 `20~40` 时，输入 `50` 调整为 `40`，输入 `10` 调整为 `20`。
- 原始数据和修改之后的数据都要保留。
- 原始记录提交之后可以修改。
- 原始记录修改必须有日志记录。
- 员工 UI 固定几类模板。
- 一个账号可以限制可操作工序数量，只能切换对应工序。
- 员工可以切换，但只能切换绑定当前工序的员工。
- 切换员工时，对应 UI 也切换。
- 现有系统已经存在 eDHR 记录本模板、记录本条目、记录本事件、批次任务、填写候选人、字段审计、生产报工、报工剩余资源池、资源分配和生产工单计划开工时间字段。
- 现有记录本字段定义支持 `min/max` 范围，但一线原始记录不能在提交时用该范围阻断超限值。

## Assumptions

- “当前的记录本功能”可作为报工过程中批记录相关原始内容的承载，但前端主入口和业务动作应以生产报工为中心。
- “批记录”继续承担正式记录、审核归档或追溯职责，但具体生成方式需要后续设计确认。
- 资源池建议优先复用现有报工剩余资源池和订单分配明细，但分配目标必须改为或补齐正式生产工单关联。
- 固定 UI 模板可以通过记录本模板类型、模板编码或枚举项维护，具体实现方式尚未确认。

## Open Questions

- 资源池按照哪些维度归集和消耗。
- 报工与批记录相关内容的组合提交采用新增接口，还是扩展现有 `createFeedback/updateFeedback/submitFeedback` 请求。
- 报工字段、记录本字段、批记录字段之间的精确映射规则是什么。
- PQC 失败记录是否进入资源池，或进入不可消耗资源状态。
- 订单计划开始时间字段来源和排序冲突处理方式。
- 审核副本是否只处理数值上下限，还是还包括设备参数、损耗比例、PQC 状态等其它规则。
- 原始记录修改日志是否需要记录修改原因、电子签名、审核人或审批流程。
- 固定 UI 模板具体分几类，每类字段和校验规则是什么。
- 员工和工序绑定关系由哪个模块维护，是否与现有用户、角色、岗位或工序配置复用。
- 生产工单 `plannedStartTime` 为空时是否允许进入 FIFO 分配。
- 记录本条目到报工、资源池、批记录审核副本之间的正式关联字段是否需要补充。
- 审核副本规则是否作为记录本模板的一部分、批记录字段规则的一部分，还是单独的审核规则配置。

## Blockers

- 缺少资源池维度定义，无法完成资源池模型设计。
- 缺少固定 UI 模板清单，无法完成一线填报页面和模板接口设计。
- 缺少报工组合提交契约，无法完成一线报工与批记录相关数据的一体化落库。
- 缺少 PQC 失败后的资源处理规则，无法完成资源池可用量和订单消耗规则。
- 缺少原始记录修改日志字段和审批要求，无法完成审计合规设计。
- 如果继续把 `min/max` 放在记录本提交校验中，一线超限原始值会被拦截，无法满足“原始记录不限制、审核副本调整”的业务要求。
- 如果现有资源池分配表不能正式关联生产工单，只能记录文本标签或排产目标字段，则不能实现生产工单维度 FIFO。

## Decisions

- 本次文档只记录当前线程对话，不汇总其它项目历史对话。
- 初步方向是保留现有批记录系统，并以生产报工为一线主入口，在报工过程中嵌入批记录相关事实采集、资源池、FIFO 分配和审核副本链路。
- FIFO 排序依据确认为订单计划开始时间。
- 审核副本的范围类超限值按边界值调整，同时保留原始值。
- 原始记录允许修改，但必须保留修改日志。
- 员工 UI 使用固定几类模板。
- 结合现有系统的优先方向是：报工承载一线主提交和数量结果，记录本承载报工过程中采集的批记录相关原始事实，现有剩余资源池承载资源入池和消耗，生产工单计划开工时间承载 FIFO 排序，批记录执行和字段审计承载审核副本与原始/修正值对照。
- 一线入口应是现有报工表单的一线模式或简化报工变体，而不是脱离报工的独立记录本系统；底层应复用 eDHR 记录本、工序任务候选、报工和资源池接口。
- 员工点击确定提交时应在同一事务中保存/提交报工、保存批记录相关原始内容、写入记录本事件，并建立报工与记录本条目的来源关联；任一正式前置条件缺失时整体失败。
- 一线填报不使用路线前后置门禁作为提交限制；路线仅作为上下文和正式追溯依据。
- 正式批记录表单仍按逐工序批记录表单绑定读取，不能由记录本模板、表单槽位或工序开始配置替代。
