# DCC项目代码与产品目录联合新建审批开发文档

## 1. 文档目的

本文定义“从 DCC 产品目录发起，联合新建 DCC 项目代码和 DCC 产品目录产品，并经审批后正式落库”的开发合同。

本文是开发设计文档，不代表功能已经实现、数据库已经迁移、审批已经配置或页面已经验收。后续实现必须先按本文的 BDD 场景写 RED，再实现 GREEN，最后完成相邻回归。

## 2. 需求范围

### 2.1 入口

- 入口位于“基础数据 / DCC 产品目录”页面。
- 入口名称建议为“新建项目代码及产品”。
- “基础数据 / DCC 项目代码”页面删除“新增项目代码”入口。
- DCC 项目代码仍可查询、查看和执行已有维护动作，但不能从该页面直接新建项目代码。
- 本需求不替换已有“产品建档申请”语义。现有产品建档申请面向 MDM 产品主数据；本需求面向 DCC 产品目录和 DCC 项目代码的联合正式数据。

### 2.2 一对一关系

一次申请只包含一组项目和产品：

```text
一个 DCC 项目代码 <-> 一个 DCC 产品目录产品
```

- 一个项目代码不得在本申请中关联多个产品。
- 一个产品不得在本申请中关联多个项目代码。
- 项目代码和产品必须作为同一申请的两个正式落库对象处理。
- 关联关系必须保存稳定的项目代码 ID、产品目录 ID 和申请 ID，不能只保存项目名称、项目代码或产品名称文本。

### 2.3 新建页面字段

页面只显示以下业务字段：

| 字段 | 必填 | 控件 | 规则 |
|---|---:|---|---|
| 项目名称 | 是 | 文本输入 | 去除首尾空白后不能为空 |
| 项目代码 | 是 | 文本输入 | 去除首尾空白后不能为空，不能重复 |
| 项目负责人 | 是 | 文本输入 | 去除首尾空白后不能为空；本需求保存现有文本语义，不扩展人员选择器 |
| 产品编码 | 是 | 文本输入 | 去除首尾空白后不能为空，不能重复 |
| 产品名称 | 是 | 文本输入 | 去除首尾空白后不能为空，不能重复 |
| 分类 | 是 | 下拉选择 | 只能选择“一类”“二类”“三类” |
| 备注 | 否 | 多行文本 | 可为空，保存原始业务说明 |

页面不得追加文控、型号规格、产品英文名、注册证、日期、项目工程师、存放位置、优先级或其它未确认字段。

## 3. 业务流程

```text
DCC产品目录
  -> 填写联合新建申请
  -> 提交
  -> 待审核
  -> admin审核
  -> 待批准
  -> admin批准
  -> 事务化写入项目代码、产品目录和关联关系
  -> 已完成
```

驳回流程：

```text
待审核或待批准
  -> admin驳回并填写原因
  -> 已驳回
  -> 申请人修改
  -> 重新提交
  -> 待审核
```

写入失败流程：

```text
批准通过
  -> 写入中
  -> 任一步失败
  -> 回滚全部正式数据
  -> 写入失败
```

写入失败不是成功状态，也不能通过前端刷新、重复点击或默认提示伪装为已完成。

## 4. 审批规则

### 4.1 审批节点

审批必须保留两个独立节点：

1. 审核节点：固定候选人为 `admin`。
2. 批准节点：固定候选人为 `admin`。

同一个 `admin` 账号可以完成两个节点，但系统必须分别保存审核动作和批准动作，不能把一次操作同时记为审核和批准。

### 4.2 审批意见

- 审核通过和批准通过都必须有操作记录。
- 驳回必须填写非空驳回原因。
- 审批记录至少保存申请 ID、节点、操作者、动作、意见、时间和结果。
- 审批记录不可被申请人编辑或删除。
- 审批中的正式目标数据只存在申请快照中，不得提前写入正式 DCC 项目代码或 DCC 产品目录。

### 4.3 申请状态

建议状态枚举：

| 状态 | 含义 |
|---|---|
| `DRAFT` | 草稿，尚未提交 |
| `PENDING_REVIEW` | 待 admin 审核 |
| `PENDING_APPROVAL` | 审核通过，待 admin 批准 |
| `REJECTED` | 审核或批准被驳回 |
| `WRITING` | 批准通过，正在写入正式数据 |
| `COMPLETED` | 项目代码、产品和关联关系均已写入 |
| `WRITE_FAILED` | 正式写入失败，已回滚并保存失败原因 |

申请状态、审批节点状态和正式数据状态必须分开表达，不能使用“审批通过”代替“正式写入完成”。

## 5. 数据设计

### 5.1 联合新建申请

建议新增独立申请主表，例如 `dcc_project_product_create_request`。正式表名、字段类型和租户基类须在实施前按实际 schema 复核后确定。

申请快照至少包含：

| 字段 | 说明 |
|---|---|
| `id` | 申请 ID |
| `tenant_id` | 租户范围 |
| `project_name` | 项目名称快照 |
| `project_code` | 项目代码快照 |
| `project_leader` | 项目负责人快照 |
| `product_code` | 产品编码快照 |
| `product_name` | 产品名称快照 |
| `classification` | 一类/二类/三类 |
| `remark` | 备注快照 |
| `status` | 申请状态 |
| `applicant_user_id` | 申请人 |
| `reviewer_user_id` | 实际审核人，必须为 admin |
| `approver_user_id` | 实际批准人，必须为 admin |
| `review_reason` | 审核意见 |
| `approval_reason` | 批准意见 |
| `reject_reason` | 驳回原因 |
| `write_error_code` | 写入失败码 |
| `write_error_message` | 脱敏后的失败原因 |
| `generated_project_code_id` | 成功后生成的项目代码 ID |
| `generated_product_catalog_id` | 成功后生成的产品目录 ID |
| `association_id` | 成功后生成的关联关系 ID |
| `created_at/updated_at` | 审计时间 |

申请表保存用户提交的业务快照，不能在批准时重新从前端参数读取字段，也不能用当前页面列表数据补齐缺失字段。

### 5.2 正式对象

审批通过后的正式写入目标为：

1. `dcc_project_code`：保存项目名称、项目代码、项目负责人及正式状态。
2. `dcc_product_catalog`：保存产品编码、产品名称、分类、项目名称、项目代码及备注。
3. 现有或新增的正式关联关系表：保存项目代码 ID、产品目录 ID、申请 ID，并保证一对一有效关联。

项目负责人当前需求是文本字段。若后续要改为系统用户 ID，必须另开需求，不能在本任务中默默替换数据语义。

### 5.3 与现有 MDM 产品建档的边界

- 本申请的产品名称、产品编码和分类直接形成 DCC 产品目录快照。
- 不得因为“产品”一词自动创建或选择 MDM 产品主数据。
- 不得把 `productMasterId` 当作本申请的隐含必填字段。
- 若后续要求 DCC 产品目录产品必须同步 MDM 产品主数据，必须增加明确的同步来源、状态机、失败补偿和独立验收，不属于本文默认范围。

## 6. 唯一性和重复校验

### 6.1 业务唯一性

以下字段在同一租户的有效正式数据中必须唯一：

- 项目代码；
- 产品编码；
- 产品名称。

规范化至少执行首尾空白去除；大小写是否敏感必须按现有数据库排序规则和业务合同确认，不能由前端自行决定。

### 6.2 提交时校验

提交申请时依次校验：

1. 必填字段和分类枚举；
2. 正式 DCC 项目代码中是否已有相同项目代码；
3. 正式 DCC 产品目录中是否已有相同产品编码；
4. 正式 DCC 产品目录中是否已有相同产品名称；
5. 其它未完成申请中是否已占用相同项目代码、产品编码或产品名称；
6. 当前申请是否已经提交，防止重复点击生成两笔申请。

重复时必须返回明确字段级错误，例如“项目代码已存在”“产品编码已存在”“产品名称已有待审批申请”。

### 6.3 批准写入前校验

批准动作开始时必须在事务内重新校验全部唯一性，并锁定相关申请和正式目标身份。提交后到批准前，其他用户可能已经创建相同数据，因此不能只依赖提交时校验。

数据库必须使用租户范围的唯一约束或等价的有效数据唯一机制兜底。唯一冲突必须转成可见的业务失败，不得捕获后返回成功。

## 7. 事务与失败处理

### 7.1 正式写入事务

批准通过后的正式写入必须由一个本地事务完成：

1. 锁定申请并确认当前状态为可批准；
2. 再次校验项目代码、产品编码、产品名称；
3. 将申请标记为 `WRITING`；
4. 新增 DCC 项目代码；
5. 新增 DCC 产品目录；
6. 新增项目代码与产品目录的一对一关联；
7. 保存生成对象 ID；
8. 将申请更新为 `COMPLETED`。

### 7.2 任一步失败

如果项目代码、产品目录、关联关系或申请状态任一步写入失败：

- 回滚本事务中已经写入的项目代码；
- 回滚本事务中已经写入的产品目录；
- 回滚本事务中已经写入的关联关系；
- 不保留半成品正式数据；
- 在可独立提交的失败记录机制中保存 `WRITE_FAILED`、错误码和脱敏原因；
- 页面显示“写入失败”，不能显示“已完成”；
- 提供明确的重新处理入口，并在重试前重新校验唯一性。

失败原因不得吞掉、截断成无意义的“系统异常”或使用默认成功文案。若失败记录本身无法保存，应将原始异常准确暴露给调用方和日志，并保持正式数据事务回滚。

### 7.3 重试规则

- 只有 `WRITE_FAILED` 申请可以进入重新处理。
- 重新处理必须重新锁定申请并重新读取申请快照。
- 若项目代码、产品编码或产品名称已被其它正式数据占用，重试必须失败并要求修改申请，不得覆盖既有数据。
- 重试不得重复创建已提交成功的正式对象。
- `COMPLETED` 申请不能再次执行写入。

## 8. 页面和操作

### 8.1 DCC 产品目录页面

新增：

- “新建项目代码及产品”按钮；
- 联合新建表单；
- 我的申请/申请记录入口；
- 申请详情、审批节点、审批意见和写入失败原因；
- 驳回后编辑并重新提交；
- 写入失败后的重新处理。

联合新建表单不得与现有“产品目录维护”表单混用，避免用户误以为点击保存就能绕过审批。

### 8.2 DCC 项目代码页面

- 删除“新增项目代码”按钮及其直接新建动作。
- 保留列表、详情和已有查询能力。
- 不能通过隐藏按钮、直接 URL、前端伪造权限或旧接口继续绕过联合审批新建。
- 后端也必须拒绝未经联合申请审批的直接新建路径；只删除按钮不构成完成。

### 8.3 审批中心

审批详情需要展示：

- 申请编号；
- 项目名称、项目代码、项目负责人；
- 产品编码、产品名称、分类、备注；
- 当前节点；
- 申请人和提交时间；
- 审核记录、批准记录；
- 驳回原因或写入失败原因；
- 项目代码与产品的一对一关系预览。

审批页的通过、驳回按钮必须由后端按当前节点和当前操作者再次授权。

## 9. 接口设计建议

接口路径仅为开发建议，正式路径需遵循当前 DCC Controller 组织方式。

| 方法 | 建议路径 | 用途 |
|---|---|---|
| `POST` | `/dcc/project-product-requests` | 创建草稿或提交申请 |
| `GET` | `/dcc/project-product-requests/page` | 查询申请记录 |
| `GET` | `/dcc/project-product-requests/{id}` | 查看申请详情 |
| `POST` | `/dcc/project-product-requests/{id}/submit` | 提交草稿 |
| `POST` | `/dcc/project-product-requests/{id}/review` | admin审核通过或驳回 |
| `POST` | `/dcc/project-product-requests/{id}/approve` | admin批准或驳回 |
| `POST` | `/dcc/project-product-requests/{id}/retry-write` | 处理写入失败申请 |

接口合同要求：

- 所有写接口必须校验租户、权限、状态和幂等键。
- 审核和批准接口不能由前端传入任意操作者 ID；操作者必须从当前登录上下文解析。
- 申请详情返回申请快照和审批记录，不通过当前正式列表反推历史申请内容。
- 唯一性错误返回稳定业务错误码和具体字段，不返回默认成功。

## 10. BDD 验收场景

### BDD-01 入口位置

Given 用户具备联合新建权限\
When 用户进入 DCC 产品目录页面\
Then 页面显示“新建项目代码及产品”入口\
And DCC 项目代码页面不显示直接新增项目代码入口

### BDD-02 表单字段边界

Given 用户打开联合新建表单\
When 页面完成渲染\
Then 只显示项目名称、项目代码、项目负责人、产品编码、产品名称、分类和备注\
And 分类选项只有一类、二类、三类

### BDD-03 提交必填校验

Given 用户缺少任一必填字段\
When 用户提交申请\
Then 提交被拒绝\
And 页面指出具体缺失字段\
And 不创建申请或正式数据

### BDD-04 一对一申请

Given 用户填写一组项目和产品\
When 用户提交申请\
Then 申请只保存一个项目代码和一个产品\
And 申请快照保存项目代码与产品的稳定关联身份

### BDD-05 提交进入审核

Given 表单字段合法且无重复\
When 用户提交申请\
Then 申请状态为 `PENDING_REVIEW`\
And 审核待办候选人为 `admin`\
And DCC 项目代码和 DCC 产品目录正式表没有新增数据

### BDD-06 审核通过进入批准

Given 申请处于 `PENDING_REVIEW`\
When `admin` 审核通过\
Then 保存审核人、审核时间和审核意见\
And 申请状态为 `PENDING_APPROVAL`\
And 生成批准节点给 `admin`

### BDD-07 审核驳回

Given 申请处于 `PENDING_REVIEW`\
When `admin` 以非空原因驳回\
Then 申请状态为 `REJECTED`\
And 正式项目代码、正式产品和关联关系均不存在新增数据\
And 申请人可以修改后重新提交

### BDD-08 批准写入完成

Given 申请已审核通过且处于 `PENDING_APPROVAL`\
When `admin` 批准\
Then 系统在一个事务中新增 DCC 项目代码、DCC 产品目录和一对一关联\
And 申请状态为 `COMPLETED`\
And 三个正式对象都能通过稳定 ID 查询

### BDD-09 批准驳回

Given 申请处于 `PENDING_APPROVAL`\
When `admin` 以非空原因驳回\
Then 申请状态为 `REJECTED`\
And 不新增正式项目代码、产品目录或关联关系

### BDD-10 重复项目代码

Given 正式数据或其它待审批申请已占用项目代码\
When 用户提交或 admin 批准当前申请\
Then 系统明确返回项目代码重复\
And 不创建重复正式数据

### BDD-11 重复产品编码

Given 正式数据或其它待审批申请已占用产品编码\
When 用户提交或 admin 批准当前申请\
Then 系统明确返回产品编码重复\
And 不创建重复正式数据

### BDD-12 重复产品名称

Given 正式数据或其它待审批申请已占用产品名称\
When 用户提交或 admin 批准当前申请\
Then 系统明确返回产品名称重复\
And 不创建重复正式数据

### BDD-13 写入中途失败

Given 批准后项目代码已经尝试写入但产品目录或关联写入失败\
When 事务结束\
Then 项目代码、产品目录和关联关系全部回滚\
And 申请状态为 `WRITE_FAILED`\
And 保存具体失败原因

### BDD-14 写入失败重试

Given 申请处于 `WRITE_FAILED`\
When 用户执行重新处理\
Then 系统重新读取申请快照并重新校验唯一性\
And 成功时只生成一套正式项目代码、产品目录和关联关系\
And 失败时仍保持失败状态并保存新失败原因

### BDD-15 审批操作者和节点隔离

Given 当前申请处于审核节点或批准节点\
When 非当前节点处理人或错误节点重复操作\
Then 后端拒绝该操作\
And 不改变申请状态或正式数据

### BDD-16 直接绕过入口

Given 用户绕过页面直接调用旧项目代码新建接口\
When 请求不携带有效联合申请审批上下文\
Then 后端拒绝新建\
And 不新增 DCC 项目代码

## 11. TDD 实施顺序

后续代码开发必须按以下顺序执行：

1. RED：申请状态、字段、唯一校验、分类枚举和状态迁移测试。
2. RED：提交前和批准前重复校验测试。
3. RED：审批节点 admin 候选人、审核/批准分离和驳回原因测试。
4. RED：正式写入事务回滚测试，覆盖项目代码已写入后产品目录失败、关联失败和申请状态更新失败。
5. GREEN：新增申请、审批、正式写入和失败状态服务。
6. GREEN：产品目录入口、联合表单、申请记录和审批详情页面。
7. GREEN：删除项目代码直接新建入口，并在后端关闭绕过路径。
8. REGRESSION：现有 DCC 产品目录查询、DCC 项目代码查询、既有产品建档申请和审批中心回归。

本轮不执行上述测试；它们是后续实现的完成门禁。

## 12. 非目标和禁止行为

- 不把 DCC 产品目录新建申请改造成 MDM 产品建档申请。
- 不在审批提交时提前插入正式项目代码或产品目录。
- 不允许只写入项目代码或只写入产品目录后返回成功。
- 不用当前日期、默认分类、默认项目或空字段补齐用户未提交的数据。
- 不吞异常、不捕获唯一冲突后返回成功、不用前端禁用按钮代替后端权限。
- 不通过删除项目代码页面按钮来掩盖旧接口仍可直接新建的问题。
- 不扩展到多产品、多项目、批量导入或复杂流程配置。

## 13. 实施前必须确认

以下事项不阻塞本文档交付，但在代码实现前必须由开发依据实际 schema 和产品规则确认：

1. DCC 产品目录的“产品名称”正式对应 `dcc_product_catalog.product` 还是另有权威字段。
2. DCC 产品目录的“分类”正式落在 `classification`，还是需要同时维护产品类别 I/II。
3. 现有 DCC 项目代码和产品目录的租户范围、数据来源和唯一约束是否允许直接新增。
4. 项目负责人保存为文本还是应绑定系统用户；本文暂按当前用户确认的界面文本字段设计。
5. 现有 BPM 审批中心能否固定创建两个节点且允许同一个 `admin` 连续办理。
6. 旧项目代码直接新建接口的正式下线方式和历史数据兼容边界。
