# DCC项目代码与产品目录联合新建审批开发文档 Review

## 1. Review 结论

结论：**开发文档已保存，需求主流程可进入开发设计评审；代码实现前有 6 项必须确认事项，均已写入正式文档，不将未确认内容伪装成已确定事实。**

文档已覆盖：

- DCC 产品目录入口；
- DCC 项目代码页面移除直接新建；
- 7 个页面字段及分类枚举；
- 项目代码与产品一对一关联；
- admin 审核和 admin 批准两个节点；
- 审批通过后正式写入；
- 写入失败全量回滚并标记失败；
- 项目代码、产品编码、产品名称重复校验；
- 驳回、重新提交和写入失败重试；
- 后端禁止绕过审批直接新建。

## 2. 已确认并锁定的设计

### R01 入口边界

**结论：通过。**

入口只放在 DCC 产品目录；DCC 项目代码页面删除新建入口。文档同时要求关闭后端绕过路径，避免只隐藏前端按钮。

### R02 页面字段边界

**结论：通过。**

表单严格限制为项目名称、项目代码、项目负责人、产品编码、产品名称、分类、备注。没有把现有产品建档申请中的文控、产品英文名、型号规格、项目工程师等字段带入本需求。

### R03 业务对象边界

**结论：通过。**

本文将本需求定义为 DCC 项目代码和 DCC 产品目录的联合新建申请，不直接复用 MDM 产品建档申请。这样可以避免：

- 把 MDM `productMasterId` 误当成用户必填字段；
- 把 MDM 产品创建成功误判成 DCC 产品目录写入成功；
- 把现有项目代码页上的“产品建档申请”误当成新的产品目录入口。

### R04 审批节点

**结论：通过，保留业务风险提示。**

审核人和批准人都固定为 `admin`，但文档保留两个独立节点和两条审批记录。这样符合用户当前确认的业务规则，同时不把一次 admin 操作同时记为审核和批准。

### R05 原子写入

**结论：通过。**

批准后的项目代码、产品目录、关联关系和申请完成状态均纳入一个事务。任何一步失败都必须回滚正式对象，并保存 `WRITE_FAILED` 和具体失败原因。

### R06 重复校验

**结论：通过。**

文档要求提交时校验、批准写入前再次校验、数据库唯一约束兜底，覆盖项目代码、产品编码、产品名称和待审批申请占用。并发唯一冲突不得被吞掉。

## 3. Review 发现与处理

| 编号 | 发现 | 风险 | 文档处理 |
|---|---|---|---|
| F01 | 现有产品建档申请在 DCC 项目代码页，面向 MDM 产品 | 直接复用会把两条业务链路混为一谈 | 新增独立申请边界和独立数据快照 |
| F02 | 现有产品目录可直接维护，项目代码也有直接新增入口 | 仅新增弹窗会留下审批绕过路径 | 同时要求删除前端入口和关闭后端直接新建 |
| F03 | 用户要求一个项目代码对应一个产品 | 只在页面展示关联而不保存稳定 ID 会出现错配 | 要求申请 ID、项目代码 ID、产品目录 ID 的正式关联 |
| F04 | 用户要求写入失败整笔回滚并标记失败 | 同一事务内直接把失败状态更新也回滚会丢失失败状态 | 文档要求正式数据事务回滚，并采用可独立提交的失败记录边界；实现时需明确事务传播或失败状态落库方案 |
| F05 | 项目代码、产品编码、产品名称都不能重复 | 只在提交时校验无法防止审批等待期间的并发占用 | 增加批准前重校验和数据库唯一约束 |
| F06 | admin 同时是审核人和批准人 | 可能与组织分权政策冲突，但用户已明确指定 | 按用户需求实现两个节点；若合规规则不允许同人连续办理，需在实施前改需求，不得静默改变 |
| F07 | 当前 DCC 产品目录存在“产品”“产品编码”“分类/类别 I/II”等多个字段 | 直接猜字段会造成数据落错列 | 文档把正式字段映射列为实施前确认项 |
| F08 | 项目负责人当前项目代码模型有多个负责人文本字段 | 直接猜 `projectLeader` 或 `projectEngineer` 会改变业务语义 | 本文按用户确认保留一个文本字段，并要求实施前确认正式归属 |

## 4. 开发前阻塞确认

以下不是本文档缺陷，但如果不确认，不能安全进入生产代码实现：

1. “产品名称”是否正式写入 `dcc_product_catalog.product`。
2. “分类（一类、二类、三类）”是否正式写入 `dcc_product_catalog.classification`，以及是否不维护 `categoryLevel1/categoryLevel2`。
3. 项目负责人是否保存文本；如果必须关联系统用户，需要新增用户 ID 字段和人员选择规则。
4. DCC 产品目录和 DCC 项目代码的唯一性是否按租户维度生效，现有历史重复数据如何处理。
5. 现有 BPM 是否支持 `admin` 连续完成审核和批准两个节点。
6. 直接新建项目代码旧接口是物理删除、权限关闭，还是保留给历史/系统内部调用；必须由后端合同明确。

## 5. 验收门槛

开发完成前至少应证明：

- 页面入口位置和字段边界正确；
- DCC 项目代码页无直接新建入口；
- 提交后正式两张目标表零写入；
- admin 审核和批准节点分离；
- 三类重复数据在提交和批准两个时间点均被拦截；
- 批准成功生成项目、产品和一对一关联；
- 任一写入步骤失败时正式数据零残留，申请可见为 `WRITE_FAILED`；
- 驳回原因、写入失败原因和审批时间线可查询；
- 旧产品建档申请功能没有被错误改写；
- 非当前节点操作者和绕过旧接口均被后端拒绝。

## 6. 证据边界

本 review 只验证需求、现状代码边界和开发文档完整性，不代表：

- 业务代码已经修改；
- 数据库迁移已经执行；
- BPM 模型已经配置；
- 页面已经实现；
- 单元测试、构建或 E2E 已通过；
- 生产租户已有数据已经清理或迁移。

后续代码任务必须新建自己的任务目录，并按本文 BDD 先执行 RED，再实现 GREEN 和 REGRESSION。
