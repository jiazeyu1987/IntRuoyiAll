# 用户管理分阶段实施与放行计划

基线与目标见 [架构](architecture.md)。本轮只设计、静态审查与结构验证。设计通过只表示可以作为后续开发依据，不等于代码、数据、业务或 E2E 已通过，也不授权提交、迁移或发布。

## 阶段顺序与范围

| 阶段 | 交付与边界 | 前置和单独授权 |
| --- | --- | --- |
| D0 本轮设计 | 七份设计文档；主 Agent 按 G1—G4 review，退回修订后才能放行 | 用户已授权文档设计和 review；不改代码/环境 |
| D1 下一开发：UM-03 | 用户列表有限摘要、查询部门上下文、无管理权限耦合/逐行角色请求、等价数据库分页排序及对应页面 | 独立开发授权；OQ-Q1/Q2/F2 确认，真实验证前置明确；表头排序现状已静态确认禁用 |
| D2 写职责与数据唯一源 | 先清单和小范围职责抽取，再任职唯一源迁移；明确用例、内聚规则与可恢复性 | 独立方案、全调用清单、现场 schema/差异证据、数据写入授权；不能打包成 D1 |
| D3 安全职责抽取 | 统一主体锁/资格端口，改密/生命周期/会话编排与循环依赖治理 | 独立授权，OQ-S1/S2确认；保留 UM-05/S-01及正式授权审计 |
| D4 历史身份：UM-01 | MES 历史姓名与正式新签名冻结身份；稳定 API，迁移内部 DO/Service 引用 | 独立授权，可信历史来源与签名/哈希/幂等合同确认；保留已有员工档案与提交冻结身份 |
| Deferred UM-02 | 未来导入复用正式生命周期规则 | 用户明确暂缓；不是下一项，也不是 D1/D3/D4 前置；重启需独立授权 |
| Later UM-06/UM-10等 | 解锁原因入口、更多筛选/候选/有效锁体验 | 不捆绑 D1；独立取舍和验收 |

D2 的来源切换必须纳入尚存导入写调用者，如果届时仍未获处理授权，只阻断该“来源切换”子阶段，不强迫先做 UM-02，也不阻断其他独立阶段。此计划顺序是推荐，后续每阶段启动前以当轮授权与风险重新选定。

## D1 明确实施包

### 目标与允许改动

仅修列表的读取架构：`index.vue`、用户 API 类型/读取函数、用户查询专用树（可新增局部组件）、UserController 的查询入口、UserQueryService/投影转换与批量 Mapper、自定义查询 SQL、相应定向测试。共用 DeptTreeSelect 若调整必须只引入纯数据输入能力并保持所有其他默认调用者合同，优先用用户页局部组件避免扩大范围。

page保留现有公开字段和条件，增量roles/posts/isDeptLeader；page SQL内部投影同时携带原始post_ids字符串，纯解析后批量对账，不以已转换Set代替原文。Q2是proposed最小user:query组织上下文接口。正式query DTO不带密码或原始JSON。批量关系只用已经通过租户/数据范围过滤的页内用户，相关主数据读取仅包含这些关系所需ID。路由定位因目标部门停用而不在可选树时明确拒绝并提示，是本阶段必须记录和验证的边界变化，禁止自动去掉筛选。

### 明确不做

不改任职双写/Schema/唯一源，不拆 UserForm 保存，不改角色分配/临时授权/高权限规则，不改密码/会话/生命周期/导入，不新增 nickname/postId/loginLockActive 筛选、角色岗位候选页或更多列体验，不修改 MES/DCC/BPM，不扩大权限种子、不新增管理员账号，不清理其他任务资产。角色筛选后端已经存在，保留；页面本轮不增加筛选 UI。

### M1 开发前核对

1. 确认届时 HEAD、并行改动与目标文件所有者；读适用项目文档，建独立开发任务和用户要求的隔离 worktree。
2. 核对实际数据库方言/隔离级别、数据权限拦截对派生查询的效果和真实菜单路由；只读记录，不输出凭据。
3. 确认 Q2 的允许部门范围与森林方案；真实受限测试角色要能进入用户页且仅有 user:query。测试账号/组织/角色数据需由任务自有、正式前端建立，任何准备写入遵守当轮授权，不能直接写 DB。
4. 全仓枚举 page 调用者、表头排序 handler 与 utils 调用者；确定增量响应不会改变导出、选择器和编辑合同。

缺上述必要前提则准确报告影响；不切换备用库、mock 或不完整成功路径。

### M2 后端有限查询

按后端 Q1/Q2 实现授权先行、批量摘要、只读一致快照和对账。deptId 分支由数据库执行等价分组排序再分页，不取全量用户到应用。排序验证以当前 E04 的结果为对照，不比较局部几行顺序。

必须验证选定部门优先、其他部门按已过滤可见用户 MAX(id) DESC、组内负责人优先/id DESC、负责人被过滤不额外插入、跨页连续、空页 total、roleId永久关系和租户/范围条件在 count/aggregate/page 三处一致。SQL数量为7+H以内且不随本页人数增加；鉴权基础设施成本单列。

### M3 前端读取改造

page 与 Q2 单独管理状态；本页移除岗位/角色管理分页与逐行 list-user-roles 读取；server 顺序原样显示。保留现有筛选、列配置、负责人样式、路由定位、成功刷新与组织管理明确操作。只有明确点击角色分配时才调用其授权接口。

测试不得只检查字符串移除；应运行真实 getList handler 或组件行为，验证协议错误不变成空角色、旧请求不覆盖新筛选，停用岗位/角色关系仍显示、普通查询权限可完成加载。

### M4 定向验证与主 Agent 放行

未来实现必须具备相应测试改动和与风险相符的验证；是否采用先失败测试由当轮用户与项目现行规则决定，本轮不强加已取消的 RED/GREEN门禁。

- 静态业务链：入口→Controller权限→范围→查询过滤/排序→关系/主数据→DTO→页面，所有失败和下游消费者逐节点复核。
- 后端：查询服务规则、真实 MySQL 的派生排序/分页/计数/权限、只读快照并发、无 N+1、DTO无敏感字段。SQL替身测试不能声称数据库隔离或拦截已通过。
- 前端：只查询权限、停用关系、快筛/分页/树、响应协议失败、请求竞态、路由定位、真实 handler；lint与定向类型/构建验证按当轮任务范围。
- 保留合同：定向回归 UM-04 与 UM-05/S-01；不重跑无关全系统用例作为新增完成门禁，也不能跳过唯一能证明受影响安全行为的回归。
- 若当轮用户明确要求 E2E：Playwright走真实用户页，使用真实受限账户及任务数据；创建/赋权/编辑等被验收动作只能前端完成；API/DB仅只读核验，不用 fetch/apiGet 替代。缺真实受限入口不得仅用 admin 宣称权限隔离通过。

主 Agent 独立复核测试范围、证据和 G1—G4；未通过则退回明确范围修订，不能开发者自批。

### M5 集成与收尾

实现和定向验证通过后先 ready_for_closeout，按当前规则仅清理任务自有资产。Git提交/推送、主分支融合、数据库写入与发布必须以该开发轮的明确授权为准；本轮文档放行不自动取得这些权限。保留静态结论、实际运行结果与阻塞，不把旧历史报告抄成新 PASS。

## 后续阶段门禁

D2 先完成全部关系读写清单、真实异常和恢复方案，后做唯一源切换；D3 先完成完整锁图与代理事务证据，后抽接口；D4 先确认每种事实的当时身份来源与证据绑定，后改历史读取与新签名写入。每次小范围改动单独放行，不用“架构升级”绕过业务验收或扩大范围。

## 本轮与未来证据区分

本轮可以记录文档标题/链接/方法锚点结构检查和静态设计 review。所有验收矩阵的运行验证标为未来待执行；UM-04/UM-05历史已通过只是回归合同来源。尚未确认的问题对应哪个阶段写清，不把未知政策当已通过，也不把暂缓 UM-02 改写为当前阻塞。
