# Change Request: 活跃订单 QA 锁定时点冲突

## Request Summary And Source

- 已批准的 14 任务设计要求：生产组长加入活跃订单时，在同一事务锁定 DCC 项目代码、QA 规程、QA 发布版本，并按 QA 自有工序生成 PQC 任务。
- 后续任务 `20260813-add-admin-pressure-pump-orders` 记录了用户的明确决定：允许先加入活跃订单，加入事务只锁生产路线和生产工序快照，QA/PQC 在后续独立流程处理。
- 两项决定不能同时成立；VAL13 不能自行选择业务规则。

## Current Baseline Reviewed

- 14 任务权威基线：`doc/tasks/20260811-frontline-pqc-dcc-qa-agent-design/`，其中 C00、DF02、DF06、DF07、DF10、INT12 和 VAL13 均依赖订单锁定的 DCC/QA 三项快照。
- 原 DF06 提交曾实现加入时锁定三项快照、生成四类规则任务、重新激活时保留并验证旧快照。
- 后续提交 `333029852` 删除了上述加入时行为，并增加“快照列保持可空”的测试，但漏提交对应 SQL 和两个 DCC 候选接口 DTO。
- 当前正式一线读取仍要求三项快照完整；生产代码中不存在加入后补写三项快照和创建 PQC 任务的正式入口。
- 因此当前“后续再锁”实现只能让订单进入活跃池，不能让该订单完成正式 PQC 查看与提交。

## Classification

需求变更兼发布阻断：变更活跃订单与 QA/PQC 的事务边界、快照生命周期和 PQC 任务创建时点。

## Impact Analysis

- 产品：决定无有效 QA 时订单能否加入活跃池，以及何时可进入一线 PQC。
- 设计：若保留原合同，只需修复后续回归；若采用后续锁定，必须新增明确的锁定命令和失败恢复流程，禁止在读取接口中隐式写入。
- 数据：影响三个快照列的 NULL/NOT NULL 最终约束、既有空快照订单、removed 订单重新激活和历史任务回填。
- API：后续锁定方案需要正式写接口或明确业务命令、权限、幂等、并发和错误合同；当前没有该接口。
- 测试：至少影响 C00、DF02、DF06、DF07、DF10、INT12、VAL13 的 BDD/TDD 与冻结测试；不能只修改一个 schema 测试。
- 发布：INT12 合并和 VAL13 独立验收均停止；不得以补漏 SQL或删除 Mockito 桩制造绿色。
- 运维：当前不修改共享业务数据、不重启服务、不部署；四张已存在空快照活跃订单的后续处理必须在方案批准后单独设计。
- 依赖：无论选择哪套合同，提交 `333029852` 漏掉的两个 DCC 候选 DTO 都必须通过独立窄修复纳入版本控制，才能从干净 worktree 构建。

## Decision

ACCEPT A：用户于 2026-08-14 明确回复 `A + 授权补 DTO`。恢复原 14 任务合同：加入活跃订单时必须锁定 DCC/QA 并生成 PQC 任务；QA 无效时加入失败。

方案 B 不进入当前实现范围；后续“先加入、再锁 QA”如需重新提出，必须作为新的正式变更重新设计，不能覆盖本次验收基线。

## Required Approvals

- 已满足：用户选择方案 A。
- 已满足：用户授权将两个漏提交的 DCC 候选 DTO 作为独立窄修复纳入 `int_main`；不得带入同目录其它未提交改动。
- 未授权且不执行：方案 B 的设计扩展、push、部署、远程操作和共享业务数据修改。

## Downstream Skill Reruns

- 使用 backend-api-delivery 修复两个遗漏 DTO，并从干净 worktree 执行 DCC 编译和相关回归。
- 使用 bug-regression-fix-loop 恢复 DF06 合同，随后重跑 DF06、INT12 和独立 VAL13。
- 不运行方案 B 的 PRD/系统设计扩展。

## Blockers And Next Action

- 业务合同阻塞已解除。
- 当前前置：通过独立窄提交补齐两个 DTO，恢复干净构建后再修复 C00/DF06 回归。
