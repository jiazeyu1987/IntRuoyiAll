# 生产报工超量冲突处理变更

## Request Summary And Source

来源：用户在当前任务中确认，生产工单同一工序允许多员工提交；若累计数量超过工单生产数量，不能阻止提交，而应整组标红并交由组长纠错。

## Current Baseline Reviewed

- 生产报工确认分配服务会在超量时直接抛错。
- 活跃订单详情只汇总提交数量，没有返回工序级冲突字段。
- 分配弹窗已有局部 `overageQuantity / needsAdjustment` 概念，但活跃订单列表和详情没有统一使用。
- 放行按钮主要按生产进度、检验进度和异常状态判断，没有显式阻断数量冲突。

## Classification

需求变更 / 业务规则调整。

## Impact

- Product: 员工提交不中断；组长只处理超量冲突，正常提交不额外确认。
- Design: 活跃订单、工序提交详情、报工分配区域需要展示红色冲突状态。
- Data: 不新增表；基于现有分配、工序快照和目标数量实时计算冲突。
- API: 活跃订单列表和详情响应增加冲突字段；分配/纠错后刷新相关状态。
- Test: 增加后端和前端聚焦合同，覆盖超量形成、展示和放行阻塞。
- Release: 行为变更影响生产组长工作台和报工纠错链路，需定向验证。
- Operations: 无新增配置或迁移。

## Decision

Accept. 该规则符合用户确认的业务口径，且能避免多数正常提交被组长逐条确认。

## Required Approvals

当前用户已明确要求“按照这个进行实现”。

## Downstream Skill Reruns

- backend-api-delivery
- frontend-feature-delivery

## Blockers And Next Action

无实现阻塞，变更已完成：超量允许保存并形成正式冲突状态，活跃订单和同工序全部提交明细标红，生产进度封顶目标数量，未解决冲突阻止放行，组长纠错后自动重算并恢复正确回填。

聚焦后端回归 36 个测试通过；前端类型检查、ESLint、数量冲突及相邻静态合同通过。真实写入浏览器 E2E 仍需使用确认的测试租户、账号和专用生产工单执行。
