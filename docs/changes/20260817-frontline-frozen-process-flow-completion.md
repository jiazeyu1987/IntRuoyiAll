# 一线生产活跃订单冻结工序链路补全

## Request Summary

- 来源：用户要求补全一线生产的活跃订单冻结工序链路，并在全部实现后统一验证。
- 明确边界：本次是补全数据来源和页面联动，不新增提交前“活跃订单 + 冻结工序 + 工序编号 + 生产系数 + 目标数量”五项强校验。
- 原有报工、初始分配、完成量、进度和 PQC 业务逻辑保持不变。

## Current Baseline Reviewed

- 活跃订单加入时已经保存路线版本和逐工序目标快照。
- 当前一线生产页面仍可能按当前发布路线加载工序，导致旧订单选到新版 `routeProcessId`。
- 当前 MVP 已明确允许在 `processId` 唯一时读取订单已有目标快照，保证旧订单暂时能够继续提交。
- 当前运行配置请求未完整以活跃订单冻结工序身份作为数据边界。
- 原冻结工艺任务因 MVP 范围调整暂停，现由用户明确恢复其中的数据链路补全部分。

## Classification

- 缺陷修复与产品链路补全：修正一线生产工序候选和运行配置的数据来源，避免新旧路线工序串单。

## Impact

- 产品：旧活跃订单展示旧版冻结工序，新活跃订单展示新版冻结工序；切换订单不保留上一订单上下文。
- 设计：新增或补全活跃订单冻结工序读取接口；一线生产必须先选订单，再加载该订单工序。
- 数据：只读取既有活跃订单和工序目标快照，不迁移、不覆盖、不自动升级历史订单。
- API：冻结工序查询以 `activeOrderId` 为必要输入；运行配置请求增加 `activeOrderId`。
- 前端：切换活跃订单时清空工序、员工、模板和运行配置，并阻止迟到响应回写旧订单状态。
- 后端：运行配置按订单冻结 `routeProcessId` 读取正式设备、工作站和参数；正式缺失时返回明确错误，不套用新版配置。
- 测试：集中覆盖旧订单旧工序、新订单新工序、切单清理、运行配置订单边界及相邻提交回归。
- 发布与运维：不涉及数据库迁移；不增加自动路线升级操作。

## Decision

- ACCEPT：补全活跃订单冻结工序查询、页面联动和运行配置链路。
- DEFER：提交前五项强校验和“活跃订单工艺升级”操作不在本次 MVP 范围。
- KEEP：现有 MVP 初始分配兼容行为以及原有完成量、进度、PQC 链路保持不变。
