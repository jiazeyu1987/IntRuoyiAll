# 注册证到期提醒正确分支 E2E 验证文档

## Scope

本文档用于指导 Codex 在本机 `int_main` 环境，通过 Playwright 操作真实前端页面，验证注册证到期提醒正确分支。

- 注册部经理在“注册证管理 / 注册证 / 通知设置”中，为 `T_30`、`T_8`、`T_2`、`T_1` 四个提醒节点分别配置接收账号。
- 每日任务到达对应节点后，只通知该节点中已经配置的账号。
- E2E 口径是“配置谁，谁收到通知”。
- “子公司负责人、集团管代、总经办”不是系统自动推导对象；如果业务要验证这些人收到通知，就把对应真实账号配置到对应节点后验证该账号收到。

不覆盖填错、缺字段、权限不足、网络失败等失败分支。

## Current Logic

- 提醒节点固定为 `T_30`、`T_8`、`T_2`、`T_1`。
- 节点时间按注册证有效期至向前推算 30 / 8 / 2 / 1 个月。
- 通知接收人来自“通知设置”保存的 `thresholdRecipientUserIds`。
- 业务岗位或组织身份不直接决定收件人；只有被配置到目标节点的账号才应收到该节点通知。
- 注册证列表页“通知设置”是提醒接收人维护入口。
- 个人中心“配置 / 注册证配置”只验证提醒启用、每日运行时间和接收规则说明，不作为选择接收人的主入口。
- 若当前前端没有可点击的每日任务或业务日期模拟入口，真实 E2E 必须记为 `BLOCKED`；不得直接调用后端接口冒充前端 E2E 通过。

## Code Evidence To Recheck Before Running

- 前端列表页：`IntRuoyiFronted/src/views/dcc/registration-certificate/index/index.vue` 中“通知设置”按钮受 `dcc:registration-certificate:config:query` 控制。
- 前端通知弹框：`ReminderConfigDialog.vue` 使用 `UserSelectV2` 维护 `thresholdRecipientUserIds.T_30/T_8/T_2/T_1`，保存按钮受 `dcc:registration-certificate:config:update` 控制。
- 前端配置页：`Profile/components/RegistrationCertificateConfig.vue` 展示“提醒收件人由注册部经理在注册证页面的‘通知设置’中维护”，保存启停和运行时间时必须保留已存在的 `thresholdRecipientUserIds`。
- 后端配置服务：`DccRegistrationCertificateConfigService.update()` 校验四个阈值 key、保存 `threshold_recipient_user_ids_json`，并同步接收人权益。
- 后端每日任务：`DccRegistrationCertificateReminderDailyJob.createDeliveries()` 调用 `configService.getRecipientUserIds(config, occurrence.thresholdLevel())`，按每个 occurrence 的阈值取配置账号生成发送记录。
- 后端阈值计算：`DccRegistrationCertificateReminderService` 使用 `dueDate.minusMonths(30/8/2/1)`，颜色口径为 `T_30=NORMAL`、`T_8=LIGHT`、`T_2/T_1=BRIGHT`。

## E2E-1 注册部经理配置四个节点接收人

### Operation

1. 使用注册部经理 `chudongqian` 登录“芋道源码”租户。
2. 进入“注册证管理 / 注册证”页。
3. 点击“通知设置”。
4. 在 `到期前 30 个月` 中选择 `chudongqian` 和接收人 A。
5. 在 `到期前 8 个月` 中选择 `chudongqian` 和接收人 A。
6. 在 `到期前 2 个月` 中选择 `chudongqian` 和接收人 B。
7. 在 `到期前 1 个月` 中选择 `chudongqian` 和接收人 C。
8. 点击“保存”。
9. 刷新页面后重新打开“通知设置”，核对四个节点的接收人回显。

### Expected Result

- 页面显示“通知设置已保存”或等价中文成功结果。
- 四个节点均保留本次配置的接收人。
- 保存请求中的 `thresholdRecipientUserIds` 包含 `T_30`、`T_8`、`T_2`、`T_1` 四个 key。
- 每个 key 对应的用户 ID 与页面选择结果一致。
- 未配置到某节点的用户不应出现在该节点回显标签中。

### Evidence

- 记录自然触发保存请求 URL、HTTP 状态、业务码、rowVersion 和四个节点的用户 ID 数量。

## E2E-7 更新通知设置后按新账号发送

### Operation

1. 使用 `chudongqian` 打开“通知设置”。
2. 将 `T_30` 接收人 A 调整为接收人 B，同时保留 `chudongqian`。

4. 准备另一张有效期至为业务日期 + 30 个月的任务自有 CURRENT 注册证。

- 接收人 A 不再收到新的 T_30 提醒。
- 该 E2E 证明接收对象跟随最新配置变化，而不是跟随固定人员、固定部门或固定角色动态推断。

## Execution Notes For Codex

- 所有业务动作必须由 Playwright 在真实页面完成。
- API 或数据库只允许做只读核验，不能承担通知设置保存、每日任务执行、文件上传、审批、状态修改或权限绕过。
- 如果需要临时配置接收人，必须通过“通知设置”页面完成；不得直接更新 `threshold_recipient_user_ids_json`。
- 如果需要推进业务日期，必须使用真实前端里的产品认可业务日期模拟入口或每日任务正式入口，并记录入口、操作人和具体时间；当前只发现后端模拟接口而没有页面入口时，真实 E2E 必须记为 `BLOCKED`。
- 消息验证必须登录对应接收人账号，在真实消息中心或站内信页面查看。
- 接收人 A/B/C 只是被配置账号；如果业务需要把它们解释为子公司负责人、集团管代、总经办，执行前需在测试记录中写明对应账号名和业务身份，但系统通过标准仍是“该账号被配置后收到通知”。
- 每次写入型 E2E 必须创建任务自有注册证数据，编号包含唯一标识，并记录清理策略。
- E2E 完成后，记录通知设置版本、四个节点接收人、业务日期、注册证编号、提醒阶段、消息状态、颜色状态、受理单校验状态和延续新证状态。
