# DCC项目代码与产品目录联合新建审批实现任务

## Goal

实现 `docs/dcc-project-product-approval/README.md` 定义的联合新建审批链路：从 DCC 产品目录发起申请，经过 `admin` 审核和批准后，在同一事务中新增 DCC 项目代码、DCC 产品目录和一对一关联；重复数据阻断，写入失败回滚并标记失败。

## Milestones

1. 读取现有 DCC schema、Controller、Service、Mapper、前端页面和审批基础设施，确认改造边界。
2. RED：补齐后端申请状态、字段、唯一性、审批节点、事务回滚和直接绕过拒绝测试；补齐前端静态合同。
3. GREEN：实现后端申请/审批/写入链路、数据库迁移、前端产品目录入口和表单，移除项目代码直接新建入口。
4. REGRESSION：运行 DCC 定向 Maven 测试、SQL 静态/迁移合同和前端 TypeScript/静态测试。
5. 进入 `ready_for_closeout`，执行收尾 preview/apply，按仓库 Git 规则记录授权边界。

## Expected Verification

- 后端 DCC 模块定向测试覆盖成功、驳回、重复、回滚、写入失败、重试和绕过拒绝。
- SQL 迁移静态合同覆盖新申请表、唯一索引、状态/失败字段和菜单入口调整。
- 前端静态合同覆盖产品目录入口、字段边界、项目代码入口移除和审批状态展示。
- 运行受影响模块编译/测试，不执行本轮未明确要求的真实页面 E2E。

completed

## 设计约束检查

- 只处理本任务资产，不回滚工作区中其它任务已有改动。
- 入口在 DCC 产品目录；DCC 项目代码删除直接新建入口。
- 一次申请只包含一个项目代码和一个产品，并保存稳定的一对一关联。
- 页面只保留项目名称、项目代码、项目负责人、产品编码、产品名称、分类、备注。
- 分类只允许一类、二类、三类。
- 审核人和批准人均为 `admin`，但保留两个独立审批节点和记录。
- 审批前不写正式项目代码、产品目录或关联。
- 批准写入使用本地事务；任一步失败时正式数据回滚，并在独立失败更新边界中标记 `WRITE_FAILED`。
- 项目代码、产品编码、产品名称在提交和批准前均校验，并由数据库唯一约束兜底。
- 不复用 MDM 产品建档申请作为本需求申请对象。
- 不使用 fallback、吞异常、默认成功、直接 SQL 业务写入或 mock 成功。
