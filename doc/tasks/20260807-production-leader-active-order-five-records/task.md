# 生产组长活跃订单池增加 5 条合格数据

## Task Goal

在本机 `int_main` 的已确认业务租户内创建 5 条可追踪、满足正式候选资格的数据，并通过生产组长真实页面将其加入当前生产组长活跃订单池。不得绕过候选资格、直接写活跃订单表或用 API-only 冒充页面成功。

## Milestones

- [x] M1：识别活跃订单正式资格链路、运行环境和数据边界
- [x] M2：核对真实 schema、当前生产组长身份及可复用的完整 QA 规程组合
- [x] M3：记录 RED 并创建 5 条任务自有前置数据
- [ ] M4：通过真实生产组长页面逐条加入 5 条活跃订单
- [ ] M5：完成只读 DB/API/UI 复核、证据校验、cleanup、提交与推送

## Expected Verification

- 写入前只读查询证明任务前缀对应的合格候选和活跃订单数量为 0。
- 真实 schema 核对覆盖生产工单、排产工单、排产工序、QA 规程、规程版本、规程项目、活跃订单、工序快照和 PQC 任务。
- 候选接口对 5 个任务订单均返回 `eligible=true`，但接口仅作为页面写入前的只读支持证据。
- Playwright 通过 `http://127.0.0.1:8081` 的生产组长页面逐条选择远程候选并执行“加入活跃订单”，5 次写请求均为 HTTP 200 且业务码 0。
- 写入后页面显示 5 条任务订单；只读 DB 复核 5 条 ACTIVE 活跃订单、对应工序快照及 PQC 任务完整存在且归属同一生产组长/租户。
- `database-schema-evidence.md` validator、`git diff --check`、task-closeout-cleanup preview/apply、提交与 `git push origin int_main` 通过。

## 设计约束检查

- `是否引入 fallback/降级/吞异常`：否；任何资格前置缺失均停止，不直接写活跃订单、快照或 PQC 任务表。
- `是否从根因和长期维护角度解决`：是；前置数据按正式 schema 和服务资格合同创建，最终加入动作走真实页面与正式后端事务。
- `是否存在临时补丁或绕过`：否；任务自有 fixture 是用户要求的 5 条数据本体，不伪造接口成功，不修改产品代码。

## Experience Gate

- `docs/experience-index.md` 存在并已读取。
- 适用 `docs/e2e-rules.md#写入型 E2E 任务自有模拟环境门禁`：本机、任务自有前缀、正式 schema、真实账号/权限、可追踪写入。

## Rollback Scope

- 仅允许回滚本任务前缀对应的 5 条生产工单及其任务自有排产、排产工序、活跃订单、工序快照、PQC 任务和审计记录。
- 不修改或删除被复用的正式产品、路线、路线版本、工序、QA 规程、规程版本和规程项目。
