# DCC 发布通知与关联文件影响评估 PRD

## Purpose and Scope

本 PRD 定义新文件采用 Windchill 版本机制后，大版本正式发布产生的后续动作：冻结“谁能看见”的范围，向明确关联方发送站内通知，为正向关联和反向引用文件创建影响评估任务，并跟踪“无需升版”或“需要升版”的处理结果。

第一版只处理本功能上线后新发生的 DCC 发布，不扫描、补建或重放历史文件。通知送达和影响评估完成不影响新版已经生效的事实。

## Evidence Reviewed

- 用户确认：大版本升级需要审批；批准后由文控独立发布；发布后通知关联方并判断关联文件是否需要升级。
- 一阶段 PRD 的 FR-P1-13、BR-P1-14、AC-P1-28：发布时保留关联方范围和关联文件快照，但不得把快照存在解释为通知或评估已经完成。
- 当前 `DccControlledFileRelatedFileServiceImpl`、`dcc_controlled_file_related_file`、`DccControlledFileFinalizationServiceImpl`、`DccControlledFileMessageDeliveryService`。
- 当前 DCC 浏览页、详情页、工作台和个人工作台真实入口。
- 已完成的新文件生命周期验收：B/1 ACTIVE、A/1 SUPERSEDED、A/2 WORKING，Master 指向 B/1。

## Product Summary

文控发布成功后，系统形成一个“发布后续批次”。它包含三类互相独立的事实：

1. 可见范围快照：记录发布当时哪些项目、分类、目录、部门、角色或用户规则允许查看，并冻结当时解析出的用户清单，回答“谁能看到”。
2. 通知收件人：只包含当前文件责任人、正式分发对象和关联文件影响负责人，回答“必须通知谁”。
3. 影响评估任务：针对与新版有正向关联或反向引用的每个相关 Master 生成一项任务，回答“相关文件是否需要升版”。

实际消息发送和人工评估在文件生效之后执行。消息失败会留下失败记录并可重试；评估未完成会留在工作台，但两者都不会把 ACTIVE 文件退回或隐藏。

## Target Users

- 文控人员：查看一次发布的可见范围、通知结果、影响任务和异常，并转派未分配任务、重试失败消息。
- 当前文件责任人：收到新版发布通知，查看发布版本和替代关系。
- 正式分发对象：收到自己需要使用的新版本通知，但通知本身不额外授予查看权限。
- 关联文件负责人：处理影响评估，决定无需升版或需要升版，并在需要时启动现有大版本流程。
- 项目 OWNER：查看本项目影响任务；在关联文件需要升版时按现有权限创建大版本。
- 审计人员：查看发布时快照、发送结果、评估结论、升版关联和完整时间线。

## First Version Scope

1. 每个首次发布或后续大版本发布生成唯一发布后续批次；小版本检入不生成。
2. 发布事务必须保存后续批次和冻结快照，实际通知发送与影响处理保持 `PENDING`；这些后续动作不阻塞 ACTIVE 生效。
3. 可见范围快照保存发布当时的正式 VIEW 规则来源、解析出的用户 ID 及用户/部门名称快照，不因后续权限调整而改写。
4. 通知收件人由当前文件责任人、正式电子/纸质分发对象及关联文件影响负责人合并去重，并保留每个人的收件原因。
5. 不向所有具有 VIEW 权限的人群自动群发；详情页仍可查看完整可见范围。
6. 关联影响范围同时包含新版明确关联的文件，以及当前正式版本反向引用新版 Master 的文件；按相关 Master 去重并冻结方向和版本。
7. 每个相关 Master 生成一个影响评估任务，默认分配给其当前正式版本责任人；责任人缺失或停用时任务进入“待文控分配”。
8. 评估结论只有“无需升版”和“需要升版”；两种结论都必须填写原因并保存操作者和时间。
9. “需要升版”不会自动创建版本。负责人通过任务入口打开现有大版本创建流程；已有开放大版本时只能确认关联现有版本，不能再创建一条。
10. 需要升版的任务持续显示“未开始、已关联修订、已解决”；所关联大版本正式发布后自动标记已解决。
11. 消息按发布批次和收件人幂等发送；失败记录显示原因并允许文控重试，已发送记录不可重复发送。
12. DCC 工作台增加“我的影响评估”，详情页增加“发布后续”区域；文控可查看全部任务和失败通知。
13. 所有 ID 按字符串在前端传递和比较。
14. 所有关键动作写入审计时间线，不修改历史发布、关系或决定记录。

## Non-Goals

- 不处理或补建历史文件的通知和影响任务。
- 不发送邮件、短信、企业微信或其他外部渠道，只使用现有站内通知。
- 不自动创建、送审、批准或发布关联文件新版本。
- 不把通知已读、培训完成或分发签收作为文件生效条件。
- 不改变现有 OWNER/EDIT/VIEW、审批、发布、培训或分发规则。
- 不支持跨 DCC 项目建立新关系；沿用当前同项目关联约束。
- 不设置超时天数、自动催办、自动升级或绩效统计。
- 不在本阶段实现目录模板版本化或历史文件治理。

## Functional Requirements

### FR-01 发布后续批次

- 仅当具体大版本从待发布状态成功变为 ACTIVE 时创建批次。
- 批次唯一绑定 `tenant + publishedControlledFileId`；重复发布回调返回已有批次，不重复生成收件人或任务。
- ACTIVE 状态、旧版 SUPERSEDED、Master 指针、批次和快照在同一发布事务内提交；实际消息发送在提交后执行。
- 无关联文件时批次仍存在，影响评估摘要显示“无需评估”。

### FR-02 可见范围与收件人

- 可见范围按发布时正式项目访问、分类、目录、产品组和分发规则冻结来源摘要与解析用户清单；用户清单使用结构化明细行并支持分页，不能只保存不可查询的大 JSON。快照只用于审计，不成为新的授权源。
- 通知收件人集合为：当前文件责任人、正式分发收件人、每个影响任务负责人。
- 同一用户命中多个来源时只产生一条发送记录，但展示全部收件原因。
- 用户收到通知后仍按当前权限访问文件；权限已撤销时明确提示无权，不因消息获得旁路。

### FR-03 关联影响范围

- 正向关系：发布版本在 `dcc_controlled_file_related_file` 中明确关联的 Master。
- 反向关系：其他 Master 的当前正式版本引用了本次发布 Master。
- 同一相关 Master 被多条关系或双向关系命中时只创建一项任务，任务保存全部关系方向。
- 任务冻结发布版本、相关 Master、相关当前正式版本、文件编号、名称、版本号、关系来源和生成时间。
- 后续关系编辑、相关文件升版或权限变化不改写冻结快照。

### FR-04 任务分配与决定

- 当前文件责任人统一取新发布版本的 `requesterId`；相关文件影响负责人统一取相关 Master 当前正式版本的 `requesterId`。
- 责任人不存在、停用或无法解析时，任务为 `UNASSIGNED` 并进入文控异常列表；不得静默跳过。
- 仅当前负责人可以提交结论；文控可以在决定前转派并填写原因。
- “无需升版”和“需要升版”都必须填写非空理由；提交后结论不可直接覆盖。
- 文控更正必须先重新打开任务并填写原因，旧决定作为审计历史保留。

### FR-05 升版跟踪

- “需要升版”完成后形成待执行跟踪，不自动改变相关文件。
- 负责人具有相关项目 OWNER 权限时可从任务打开大版本创建页，选择来源并填写升版理由。
- 已存在开放大版本时页面提示并允许将任务关联到该版本；不得创建第二个开放大版本。
- 关联大版本发布成功后跟踪状态为 `RESOLVED`；驳回、撤回或发布失败时保持未解决并展示原因。

### FR-06 通知发送

- 每个收件人保存 `PENDING / SENT / FAILED` 状态、尝试次数、发送时间和脱敏错误摘要。
- 发送使用系统现有幂等站内通知接口，幂等键由发布批次和收件人确定。
- 一个收件人发送失败不影响其他收件人，也不回滚文件 ACTIVE 状态。
- 文控只能重试 PENDING 或 FAILED；SENT 不能重放。

### FR-07 页面与查询

- DCC 详情页展示发布批次、可见范围、收件人发送摘要、相关任务状态与关联升版。
- DCC 工作台提供“我的影响评估”，默认只显示当前用户未完成任务。
- 文控管理入口可按文件编号、发布版本、任务状态、负责人和通知状态筛选。
- 审计时间线至少展示批次创建、消息发送/失败/重试、转派、决定、重新打开、关联修订和解决。

## Business Rules

- BR-01：文件正式生效不等待消息送达、阅读确认、评估决定或关联文件升版完成。
- BR-02：发布事务必须可靠记录后续批次；若连后续账本都无法保存，发布事务失败，旧正式版本继续有效。
- BR-03：可见范围是权限事实，通知收件人是工作责任，两者不得互相替代。
- BR-04：通知不能授予文件查看权限。
- BR-05：关联影响按 Master 去重，版本只作为发布时快照和后续修订链接。
- BR-06：正向关联与反向引用都进入影响范围；自身 Master 永不生成任务。
- BR-07：评估结论不等于升版动作；系统不能自动生成版本。
- BR-08：需要升版只允许复用现有 major-revision 权限和规则，不开新的绕过入口。
- BR-09：任务转派、更正、重试都必须写原因和审计。
- BR-10：历史快照、已发送记录和已提交决定不可物理删除。
- BR-11：小版本检入不产生发布通知或影响任务。
- BR-12：前端 Snowflake ID 不得经过 JavaScript Number。

## States and Transitions

### 发布后续批次

| Current | Event | Next | Observable Result |
| --- | --- | --- | --- |
| none | 大版本发布事务成功 | PENDING | 文件 ACTIVE，后续账本和快照已存在 |
| PENDING | 收件人和任务物化完成 | PROCESSING | 通知开始发送，任务可查询 |
| PROCESSING | 全部通知成功且任务已创建 | READY | 等待人工评估，不阻塞文件 |
| PROCESSING/READY | 存在通知失败 | PARTIAL_FAILED | 文件仍 ACTIVE，文控可重试 |
| READY/PARTIAL_FAILED | 所有影响跟踪解决 | COMPLETED | 后续闭环完成 |

### 通知发送

`PENDING -> SENT`；发送异常为 `PENDING -> FAILED`；人工重试为 `FAILED -> SENT/FAILED`。`SENT` 不允许重放。

### 影响评估

`PENDING` 或 `UNASSIGNED` -> `IN_REVIEW` -> `COMPLETED`。结论为 `NO_REVISION_REQUIRED` 或 `REVISION_REQUIRED`。需要升版时跟踪状态为 `NOT_STARTED -> REVISION_LINKED -> RESOLVED`；无需升版时跟踪状态为 `NOT_APPLICABLE`。

## Edge Cases

1. 发布回调重复：只能存在一个批次、一条用户通知和一个相关 Master 任务。
2. 文件无任何关联：不创建影响任务，仍通知文件责任人和正式分发对象。
3. 正反向同时命中同一 Master：只创建一项任务，显示两个方向。
4. 关联记录指向已替代版本：通过 Master 冻结发布时当前正式版本，不把旧 ID 当现行版。
5. 相关 Master 没有正式版本：任务进入待文控处理并显示“缺少当前正式版本”，不自动选择工作版本。
6. 负责人停用：任务 UNASSIGNED，消息不发给停用账号，文件继续有效。
7. 收件人后续失去 VIEW：消息仍保留，点击详情被当前权限拒绝。
8. 通知服务部分失败：成功用户不重复发送，失败用户可独立重试。
9. 两人同时提交同一评估：只有第一个版本匹配的请求成功，另一请求看到已处理结果。
10. 判断需要升版但没有 OWNER 权限：保留决定，提示联系项目 OWNER，不自动提升权限。
11. 已有开放大版本：只能关联该版本，不能创建第二条。
12. 关联修订被驳回或发布失败：任务保持未解决，显示关联版本状态。
13. 权限规则在发布后改变：历史可见范围快照保持不变，当前打开权限按新规则判断。
14. 重放 P4 发布或定时恢复任务：唯一键阻止重复批次和重复通知。

## BDD Scenarios

- BDD-01: Given B/1 待发布且关联关系有效，When 文控发布成功，Then B/1 立即 ACTIVE，并在同一事务保存唯一发布后续批次和快照。
- BDD-02: Given 批次包含多个收件来源，When 系统生成通知，Then 同一用户只有一条消息且保留全部原因。
- BDD-03: Given X 正向关联 Y 且 Z 反向引用 X，When X 发布，Then Y、Z 各生成一个按 Master 去重的影响任务。
- BDD-04: Given 相关文件责任人有效，When 打开我的影响评估并选择无需升版，Then 必填原因后任务完成且文件版本不变。
- BDD-05: Given 负责人选择需要升版，When 点击开始升版，Then 进入现有大版本流程，不自动建版；目标大版本发布后任务解决。
- BDD-06: Given 一个通知发送失败，When 发布事务已经提交，Then文件保持 ACTIVE，失败记录可见且只重试该收件人。
- BDD-07: Given 通知收件人失去 VIEW，When 从消息打开文件，Then 当前权限拒绝访问且消息不授予权限。
- BDD-08: Given 同一发布事件重复处理，When 物化任务和通知，Then 数据数量不增加并返回已有结果。

## Acceptance Criteria

- AC-01：发布成功后文件立即 ACTIVE，发布批次与快照存在，通知和评估仍可为待处理。
- AC-02：批次创建失败时发布整体失败，旧正式版继续有效；消息发送失败不回滚已提交发布。
- AC-03：详情页可查看发布时完整可见范围来源，且快照不随权限变化改写。
- AC-04：通知只发送给文件责任人、正式分发对象和影响负责人；同一用户合并去重并显示全部原因。
- AC-05：通知不授予 VIEW；当前无权限用户不能从消息旁路访问。
- AC-06：正向关联和反向引用都产生影响任务，同一相关 Master 只生成一项。
- AC-07：影响任务冻结发布版本、相关 Master、相关正式版本、关系方向和文件身份。
- AC-08：责任人缺失或停用时任务为 UNASSIGNED 并进入文控列表，不静默丢失。
- AC-09：只有负责人可提交结论；文控转派必须填写原因。
- AC-10：两类结论均必填原因；并发处理只有一个成功，历史决定不可覆盖。
- AC-11：无需升版完成任务且不改变相关文件任何版本状态。
- AC-12：需要升版不会自动建版；从任务只能进入或关联现有受控大版本流程。
- AC-13：已有关联大版本时禁止第二个开放大版本；关联版本发布后任务 RESOLVED。
- AC-14：通知按发布批次和用户幂等；FAILED 可重试，SENT 不可重放。
- AC-15：单个通知失败不影响其他收件人、不影响 ACTIVE 文件，错误原因可见。
- AC-16：小版本检入不创建发布批次、通知或影响任务。
- AC-17：工作台、详情页和文控管理页展示的批次、通知、任务、结论与数据库只读事实一致。
- AC-18：真实 Playwright 从大版本发布完成到负责人处理评估、开始/关联升版，全程只通过前端完成业务动作。

## Open Questions

- 第一版不设置截止时间、催办频率或外部消息渠道；这些内容需要新的业务规则后另立阶段。
- 跨项目关系仍被当前上传关联规则禁止，因此本阶段不定义跨项目负责人和权限处理。

## Product Blockers

- 实施前必须确认现有发布最终化事务中插入后续账本的位置，不得通过捕获异常后继续发布来伪造可靠性。
- 第一版责任人正式来源已固定为对应正式版本的 `requesterId`；未来若引入 Master 级责任人，必须另立迁移和产品规则，不能静默切换。
- 真实 E2E 需要至少两个同项目新文件、有效关联关系、文控账号和关联文件负责人账号；缺少时验收 BLOCKED。
