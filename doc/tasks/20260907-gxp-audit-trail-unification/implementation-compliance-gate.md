# 统一 GxP 审计追踪实施合规门禁

## Purpose

本文档回答两个问题：

1. 按现有文档开发完成后，是否足以支撑检查清单 2.1 至 2.10。
2. 后续新增模块、接口、Job、导入、Migration 或运维脚本时，如何持续满足同一审查要求。

结论口径：必须统一审计写入契约、统一账本、统一查询和统一覆盖门禁；不应把所有业务接口改造成同一个远程业务接口。业务仍保留各自领域 API，所有 GxP 成功写入必须在同一事务内调用统一内部审计服务，并通过机器可读策略登记和 CI 门禁证明没有遗漏。

## Non-Negotiable Implementation Contract

- 统一写入入口：所有 GxP 成功写操作必须调用 `GxpAuditTrailService.append`；禁止业务成功后异步补记、日志替代、默认成功或 silent fallback。
- 统一事实账本：所有正式审计事件进入 `gxp_audit_event` 只追加账本；领域专业证据通过稳定引用和 hash 关联，不复制、猜测或改写原证据。
- 统一策略登记：`config/gxp-audit-policy.yaml` 是 GxP 操作登记权威源，固定 schema、版本化、带批准引用、hash 冻结。
- 统一发现门禁：CI 必须双向比对登记表与实际写入口，覆盖 Controller、领域服务、Job、消费者、导入、外部同步、Migration 和运维脚本。
- 统一查询导出：审查员只通过统一只读审计中心查看标准字段、签名、时间、差异、状态信封、证据链接、完整性和导出包。
- 统一失败关闭：缺少原因、签名、before/after、可信时间、策略、保存、WORM、特权审计、覆盖登记或测试证据时，相关动作、治理状态或发布门禁必须失败。

## Definition of Done for Development

开发完成不得只理解为“代码能跑”。下列条件全部满足，才能进入正式合规放行评审：

1. 所有设计 blockers 已关闭，保存期限、审查周期、GxP 范围、NTP、WORM、最大未封存时长和特权审计目标均已批准。
2. 统一审计内核、只追加账本、状态信封、规范 hash、幂等、并发、事务回滚和完整性校验测试通过。
3. 首批纳入范围的 eDHR、DCC、BPM、Showroom、权限、配置、基础数据和系统变更写入口全部接入统一审计。
4. 每个受控动作均有 BDD、RED、GREEN、回归测试和覆盖登记映射，且测试 ID 写入策略登记。
5. 周期审查由持久化计划自动执行，至少完成批准要求的连续周期、停机补扫、失败/逾期和整改关闭验证。
6. 法规归档包自包含事件、证据、签名、领域证据、可信时间、manifest 和 `SHA256SUMS`，并完成清空隔离环境后的仅包恢复演练。
7. 正式环境完成数据库最小权限、特权审计外送、WORM 主副本、NTP/chrony、备份恢复和长期可读性证据采集。
8. 审查员通过真实页面完成抽样查询、差异阅读、签名追溯、完整性验证和导出包重算。
9. 质量/法规、系统、数据库/安全、运维和业务领域负责人完成签署确认。

只完成第 2 至第 4 项可说明“软件主体能力完成”，但不能在检查清单 2.1 至 2.10 勾选“未发现”；第 5 至第 9 项是正式合规结论的必需证据。

## Continuous Compliance Controls

后续为了“新增后仍然满足”，必须把统一接口和统一门禁纳入开发流水线：

- 新增写路径前，先在 `config/gxp-audit-policy.yaml` 登记 operationId、对象、动作、原因策略、签名策略、状态策略、保存类别、owner 和测试 ID。
- 新增 Controller、Service、Job、消费者、导入、同步、Migration 或脚本时，CI 自动发现实际写入口；未登记、重复 operationId、缺少测试或例外过期即失败。
- 所有受控业务写入只允许在领域服务中构造真实 before/after 并同事务 append；Controller 拦截器、API 访问日志和前端自报不得承担正式审计证据。
- 每次发布都生成系统变更清单并进入统一审计；OpenAPI、Migration、配置或产物变化缺少批准和原因时发布失败。
- 周期审查、归档、密封水位、特权审计外送、NTP 证据和恢复演练必须持续产生运行记录；缺失时治理状态不得显示 PASS。
- 不适用项必须有批准人、理由、范围和有效期；过期后自动回到阻塞，不能永久豁免。

## Reviewer Decision Rule

按本文档和关联设计开发完成后，审查结论应按以下规则给出：

- `PASS FOR DESIGN`：文档覆盖 2.1 至 2.10，且每项有实施控制和验证设计。
- `PASS FOR SOFTWARE`：代码、schema、测试、策略登记和 CI 覆盖已完成，但正式运行/SOP 证据尚未全部取得。
- `PASS FOR OPERATIONAL COMPLIANCE`：软件证据、正式环境证据、周期执行记录、归档恢复、SOP/培训和负责人签署全部通过。
- `BLOCKED/FAIL`：任一必需证据缺失、未批准、不可重算、不可恢复、不可独立验证，或存在业务成功但审计缺失路径。

当前任务只能给出 `PASS FOR DESIGN`；后续实现任务必须用本门禁升级到 `PASS FOR SOFTWARE`，再由正式运行与质量体系证据升级到 `PASS FOR OPERATIONAL COMPLIANCE`。
