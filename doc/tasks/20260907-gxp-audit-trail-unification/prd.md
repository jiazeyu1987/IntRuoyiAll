# 统一 GxP 审计追踪产品需求

## 1. Purpose

建立覆盖关键业务数据、基础数据、权限、配置、电子签名和系统变更的统一审计追踪能力，使授权审查人员能够回答谁、何时、对什么对象、执行了什么动作、为什么执行、发生了什么变化、使用了什么签名，以及证据是否完整且未被篡改。

本需求对应 `resource/相关文档/计算机化系统检查清单.md` 第二章 2.1 至 2.10。

## 2. Scope

### 2.1 In Scope

- 统一审计事件契约和只追加账本。
- eDHR、DCC、BPM、Showroom 现有专业证据关联。
- 用户、角色、菜单、数据范围、临时授权和签名授权变更。
- GxP 基础数据和业务记录的新增、修改、删除/作废、提交、复核、批准、发布和替代。
- 系统配置、发布、数据库 Migration、接口版本和关键调度配置变更。
- 统一查询、详情、导出、完整性校验和周期审查。
- 可信时间证据、备份、长期留存和 WORM 回执关联。
- 新增写操作的持续覆盖登记和 CI 门禁。

### 2.2 Out of Scope

- 用审计中心替代业务审批、电子签名或领域版本管理。
- 自动把所有普通查询和无 GxP 影响的技术日志纳入法规审计。
- 仅凭 HTTP 请求参数推断数据库真实变化。
- 本阶段直接确定法规保存年限、企业 NTP 地址或正式对象存储供应商。
- 本文档任务中的生产部署、数据迁移和运行态验收。

## 3. Roles

- 业务操作人：执行受控业务动作并提供强制变更原因。
- 复核/批准人：使用本人凭据完成电子签名并承担签名含义。
- 质量审查员：查询、导出、执行周期审查和确认整改。
- 审计管理员：维护审计策略和查看完整性状态，但无权修改历史事件。
- 系统管理员：维护系统运行，不得删除或改写审计证据。
- 运维/安全负责人：维护可信时间、备份、WORM 和恢复证据。

## 4. Functional Requirements

- FR-01：所有登记为 GxP 的成功写操作必须生成一条标准审计事件；失败操作按策略记录失败事件，但不得伪造业务成功。
- FR-02：标准事件必须保存主体、对象、动作、原因、前后值或字段差异、服务器时间、来源、请求关联和策略版本。
- FR-03：要求电子签名的动作必须绑定不可歧义的签名记录、签名含义、签名人和签署时间。
- FR-04：业务写入与成功审计事件必须处于同一事务；审计写入失败时业务写入回滚。
- FR-05：审计账本不得通过应用接口更新或删除，完整性校验必须发现修改、删除、插入和换序。
- FR-06：授权用户可以按租户、模块、对象、动作、操作人、结果、时间和签名筛选并查看标准化详情。
- FR-07：导出必须包含查询条件、策略版本、事件、证据引用、完整性结论、生成时间和清单哈希；缺失证据时导出必须标红并失败关闭。
- FR-08：系统必须建立持久化周期审查批次、冻结范围、审查签名、发现项、整改和关闭证据。
- FR-09：审计事件及关联证据必须按批准的保存策略备份并归档到可验证的 WORM/Object Lock 存储。
- FR-10：发布、Migration、接口版本和关键配置变更必须产生系统级审计事件。
- FR-11：正式审计时间和签名时间只能由受控服务器生成；客户端业务时间必须独立保存。
- FR-12：每个新增写入口必须进入 GxP 覆盖登记；未登记或缺少测试的受控操作不得通过发布门禁。
- FR-13：法规归档必须保存可独立恢复和查阅的完整审计包，包含规范事件、证据关联、签名证据、必需领域证据、可信时间证据、manifest 和校验清单；只保存 hash 或每日清单不视为完成归档。
- FR-14：系统必须依据持久化且已批准的周期规则自动创建审查批次，记录计划时间、实际运行、覆盖水位、补扫、漏期、逾期、告警和关闭状态；手工创建能力不能替代定期执行证据。
- FR-15：GxP 操作登记表必须使用固定、版本化、可校验的 schema，覆盖 Controller、领域服务、Job、消息消费者、导入、外部同步、Migration 和运维脚本；所有写边界均须声明稳定 operationId 或具有已批准的不适用决定。
- FR-16：数据库/schema 特权操作、审计表 DML/DDL、授权变更、审计配置变更和清单/归档操作必须由独立审计来源采集并外送至受保护存储；每日最终清单生成前的未封存窗口必须有批准上限、水位监控和超时阻断。
- FR-17：事件前后状态必须使用显式状态信封区分对象不存在、存在、已脱敏和未采集；必需状态不得以 `null` 或 `UNAVAILABLE` 代替。CREATE 为 ABSENT -> PRESENT，DELETE/VOID 为 PRESENT -> ABSENT 或 PRESENT -> VOIDED，UPDATE 为 PRESENT -> PRESENT。
- FR-18：系统发布必须生成可重算的系统变更清单，覆盖前后 commit、构建产物/镜像 digest、OpenAPI 前后 hash 与结构化 diff、Migration 有序列表及 hash、关键配置脱敏快照与 diff、批准引用、原因、操作者、时间、结果和回滚事实。

## 5. Non-Functional Requirements

- NFR-01：审计写入不可静默降级、异步补记或默认成功。
- NFR-02：敏感字段按策略脱敏或保存哈希，不在日志和导出中泄露密码、令牌、私钥或连接密钥。
- NFR-03：租户数据严格隔离，跨租户查询仅允许明确治理权限且必须审计。
- NFR-04：标准事件使用版本化规范 JSON，字符集 UTF-8，正式时间存储 UTC 并保留展示时区。
- NFR-05：账本查询性能不得通过跳过完整性验证或返回不完整证据换取。
- NFR-06：备份、归档和恢复不得改变事件身份、顺序、哈希或签名关联。
- NFR-07：从法规归档恢复时不得依赖生产数据库中仍然存在的事件、签名或证据行；归档包必须自包含其声明范围的审查所需内容。
- NFR-08：特权审计来源与业务数据库使用独立故障域或不可由同一应用权限改写的保护边界；具体产品必须经安全和运维确认，缺失时保持阻塞。
- NFR-09：覆盖登记、代码发现结果、策略版本、批准例外和测试映射必须生成 hash 固定的覆盖报告并纳入发布证据。

## 6. Acceptance Criteria

- AC-01：检查清单 2.1 至 2.10 每项均有生产控制、自动测试和运行证据来源。
- AC-02：任一受控业务写入在审计插入失败时不产生业务状态变化。
- AC-03：任意修改、删除、插入或换序审计事件都会使链或清单验证失败。
- AC-04：电子签名详情能从审计事件无歧义定位到签名人、时间、含义和被签内容哈希。
- AC-05：新增写入口缺少覆盖登记、原因规则或测试时 CI 失败。
- AC-06：周期审查不能在缺少冻结快照、质量签名或未关闭整改时关闭。
- AC-07：缺少 NTP/WORM/保存策略真实证据时，系统不得显示审计合规通过。
- AC-08：清空主数据库审计表后，仅使用正式法规归档包即可恢复指定范围的事件、前后状态、签名、证据和时间，并重算全部 hash。
- AC-09：固定时钟跨越至少三个审查周期并包含一次停机跨期后，每个应审周期均恰好形成一个批次；漏期、失败、补扫和逾期均有不可覆盖的运行证据。
- AC-10：CI 能发现未登记的 Controller、受控服务、Job、消费者、Migration 和脚本写入口；不适用项缺少批准人、理由或有效期时同样失败。
- AC-11：应用账号和普通管理员不能更新删除审计记录；特权账号模拟 DML/DDL 或关闭审计时，独立特权审计与外送证据能够发现并阻止合规状态通过。
- AC-12：CREATE、UPDATE、DELETE/VOID 分别验证显式状态信封，缺失状态不能通过事件校验。
- AC-13：对 OpenAPI、Migration 顺序、关键配置或镜像 digest 任一变化，系统变更清单均产生确定性 diff；缺少批准、原因或前后基线时发布门禁失败。

## 7. Dependencies and Blockers

- 质量/法规负责人批准保存期限矩阵、周期审查规则和 GxP 范围。
- 运维负责人提供受控 NTP、WORM 存储和独立恢复环境。
- 数据库负责人批准 append-only 权限模型及直接数据库写入禁令。
- 各领域负责人确认 before/after 快照中需要保留和需要脱敏的字段。
