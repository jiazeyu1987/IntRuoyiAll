## Entry and impact

Five new DCC `service/file` classes implement an explicit, one-shot local maintenance entry. The Runner is absent by default and requires profile `local-maintenance`, no `prod`, `production`, `backup`, `test` or `unit-test`, and `yudao.dcc.legacy-registration-maintenance.enabled=true`. Nonsecret properties provide `protected-root`, `request-file`, and `request-sha256`; none carries a credential. Root must separately fence unrelated startup writers and run an isolated process with `spring.main.web-application-type=none`. The Runner never stops other services. On a valid returned receipt it closes its application context, without `System.exit`.

The command consumes at most one invocation, including a declined or failed attempt. Before reading stdin it requires exact scope approval, all immutable input hashes, a complete sealed 25-claim/39-version/13-name scope, actual signed-quality document references and safe logging. Root supplies only an existing formal **access token** via runtime stdin with EOF; no password, user ID, default admin, login/create/refresh call or token file is supported. The token byte buffer is erased even on empty, oversize or malformed UTF-8 input. Java token Strings and formal platform objects cannot be reliably erased; they remain only in this isolated process's memory and must never be logged.

Authentication combines fresh formal `OAuth2TokenCommonApi.checkAccessToken`, exact existing access-token database row, equal scopes/type/user/tenant/expiry, and current enabled AdminUser DTO matching the official username/nickname. It excludes refresh-token compatibility, revoked/missing rows, foreign tenant/user type, stale identity and inherited tenant-ignore mode. An authenticated Spring principal derived solely from those read ports is bound for the existing Spring-proxied activation. Security and tenant contexts are restored in `finally`.

The executor's transaction performs current quality/schema reads and calls existing `activateVerifiedScope`; the existing scope/evidence/name registry and formal Gxp append share the physical transaction. It does not insert audit configuration, approval, signature, historical name, history, Master pointers or migration rows. Gxp failure rolls back activation. A failure after a possible commit must be reviewed from the actual returned receipt/current state; the command provides no automatic retry or undo.
