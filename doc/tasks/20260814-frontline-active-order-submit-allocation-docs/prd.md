# PRD - 一线报工活跃订单自动分配

## Purpose and Scope

本 PRD 定义一线生产提交与活跃订单分配的新目标流程：一线生产在提交时必须选择一个活跃订单；提交成功后，本次提交数量先自动分配到该活跃订单；即使提交数量超过该活跃订单的目标或剩余数量，也允许提交；生产组长在报工管理列表中看到该订单红色标识，并可继续把数量重新分配给其它活跃订单。

本 PRD 修正旧设计中“活跃订单剩余不足阻塞确认”的口径。

## Evidence Reviewed

- 用户确认的新业务流程。
- 旧生产组长工作台 PRD、开发计划和测试计划。
- 当前一线生产页面、组长报工管理页面、后端一线提交服务、组长分配服务的代码静态分析。
- 项目一线生产正式提交、组长报工可见性、写入型 E2E 门禁。

## Product Summary

系统以一线生产的现场选择为初始事实。员工选择活跃订单 O1 并提交数量 Q 后，系统立即把 Q 作为 O1 的初始分配。若 Q 超过 O1 当前可承接数量，提交仍成功，但该订单在生产组长报工管理列表中以红色标识，提示“需要组长调整”。组长可以接受、部分调整或全部调整到其它活跃订单，调整后保留审计记录。

## Target Users

- 一线生产员工：选择活跃订单、工序、员工、设备和数量后提交。
- 生产组长：在报工管理列表查看提交、识别红色超量订单、调整订单分配。
- 管理员 / 质量追溯人员：查看提交事实、初始分配、调整历史和当前分配状态。

## First Version Scope

- 一线生产提交必须携带本次选择的正式活跃订单身份。
- 一线提交成功后自动生成初始分配：目标订单为所选活跃订单，数量为本次提交产出数量。
- 初始自动分配允许超过所选活跃订单当前工序剩余数量，不阻塞提交。
- 生产组长报工管理列表按本次提交的当前分配状态显示红色超量标识。
- 生产组长可重新分配到其它当前活跃订单，保存当前分配版本并记录调整审计。
- 分配总量必须等于本次提交数量；允许某个订单超量，但不允许总量丢失或多分。

## Non-Goals

- 不改变 PQC 订单选择、检验任务和检验放行规则。
- 不把未加入活跃订单池的工单开放给一线或组长分配。
- 不做排产优化或自动寻找最佳订单算法。
- 不以未分配数量、前端临时预填或页面颜色替代正式分配事实。
- 不用直接 SQL、mock 数据或 admin-only 页面证明跨角色链路。

## Functional Requirements

### FR-01 一线选择活跃订单

- 一线生产提交前必须选择一个活跃订单。
- 活跃订单必须属于当前生产组长范围，并与当前路线、工序上下文一致。
- 提交载荷必须能精确表达 `activeOrderId`，不能只用 `workOrderId` 推断。

### FR-02 提交后自动初始分配

- 一线提交成功时，系统在正式事务中创建报工事件和初始订单分配。
- 初始分配模式为 `FRONTLINE_SELECTED` 或等价正式枚举，区别于后续 `FIFO` / `MANUAL`。
- 初始分配订单为一线选择的活跃订单，数量为本次提交产出数量。
- 初始分配创建失败时，整次一线提交必须失败并回滚，不得留下“报工成功但未分配”的半成品。

### FR-03 超量允许和红色标识

- 若初始分配数量超过该活跃订单当前工序可承接数量，系统仍允许提交成功。
- 生产组长报工管理列表必须对该事件和该订单显示红色标识。
- 红色标识应说明超量数量或待调整数量，例如“超出 20”或“待调整 20”。
- 红色标识不能只根据未分配数量计算；必须以当前分配订单与订单当前工序可承接数量对比。

### FR-04 组长后续调整

- 生产组长可把本次提交数量从初始订单调整到其它活跃订单。
- 调整后的总分配数量必须等于本次提交数量。
- 调整目标必须是当前生产组长可用的活跃订单。
- 调整应保留版本和审计，记录调整前订单、调整后订单、数量、操作者、时间、原因和分配模式。
- 若调整后不存在超量订单，列表红色标识应消失；若仍有订单超量，则继续红色标识。

### FR-05 可追溯展示

- 列表展示至少包含提交时间、员工、工序、所选活跃订单、提交数量、当前分配订单、超量标识和未处理状态。
- 详情展示初始分配和后续调整历史。
- 同一提交事件不可因为组长调整而丢失一线最初选择的活跃订单。

## Business Rules

- 一线提交必须选择活跃订单；缺少正式 `activeOrderId` 时禁止提交。
- 所选活跃订单必须是当前生产组长范围内的 ACTIVE 状态订单。
- 提交数量必须大于 0；损耗数量不能小于 0 且不能大于提交数量。
- 订单级初始分配允许超出订单剩余量。
- 分配总量必须始终等于本次提交数量。
- 后续调整只能使用活跃订单，不能分配给非活跃、已移除、已放行锁定或其它组长范围订单。
- 已放行锁定的分配不得被调整；如果包含锁定分配，只能调整未锁定部分，且总量仍需平衡。

## States and Transitions

- 活跃订单状态：未加入 -> ACTIVE -> REMOVED / RELEASED / CLOSED。
- 一线提交状态：草稿 -> 已提交 -> 已初始分配 -> 待组长查看 / 待调整 -> 已调整 / 无需调整。
- 分配状态：无分配 -> 初始自动分配 -> 组长手动调整 -> 后续版本调整 -> 放行锁定。
- 红色标识状态：无超量 -> 超量待调整 -> 调整后无超量 / 调整后仍超量。

## Edge Cases

- 提交数量等于订单剩余量：提交成功，自动分配，无红色超量标识。
- 提交数量大于订单剩余量：提交成功，自动分配全量到所选订单，红色标识超出部分。
- 所选活跃订单在提交瞬间被移除：提交失败，提示订单不再活跃。
- 同一工单存在多个活跃订单记录：必须按 `activeOrderId` 精确定位，不能按 `workOrderId` 任选。
- 组长把数量全部调整到另一个订单：当前分配展示新订单，初始选择仍在详情和审计中保留。
- 分配调整请求数量合计不等于提交数量：拒绝保存。
- 组长保存时目标订单已放行锁定：拒绝调整该订单。

## Acceptance Criteria

- AC-01：一线生产未选择活跃订单时不能提交。
- AC-02：一线生产选择 O1 提交 Q 后，系统生成报工事件和 O1=Q 的初始分配。
- AC-03：当 Q 大于 O1 当前工序剩余量时，提交仍成功，生产组长报工管理列表中 O1 红色标识。
- AC-04：组长可将 O1 的部分或全部数量调整到 O2，保存后当前分配和审计正确。
- AC-05：调整后分配总量始终等于提交数量。
- AC-06：非活跃订单、其它组长订单、已移除订单和已锁定订单不能作为新调整目标。
- AC-07：列表红色标识随当前分配重新计算，不依赖页面缓存或初次加载假数据。

## Open Questions

- 红色标识文案最终使用“超出 X”还是“待调整 X”需要产品确认；开发可先使用“待调整 X”。
- 初始分配模式枚举名称使用 `FRONTLINE_SELECTED`、`AUTO_SELECTED` 还是中文业务枚举，需要实现时与现有枚举统一。

## Product Blockers

- 若后端无法持久化 `activeOrderId`，不能实现精确的“本次选择活跃订单”。
- 若测试环境缺生产组长账号、一线账号、签名和可清理活跃订单，真实 E2E 不能放行。
