# 岗位需求分解矩阵开发任务表

## Purpose and Scope

基于 `岗位需求分解矩阵.xlsx` 中的主流程和衍生需求，将需求拆成可并行、可验收、可逐阶段集成的开发任务。第一阶段用于并行建设基础能力；第二阶段以后按业务链路逐步收敛，避免各模块对“活跃订单、完成、阻塞、放行”的理解不一致。

## Source Inputs

- 源矩阵：`C:\Users\BJB110\Desktop\文档\职责\岗位需求分解矩阵.xlsx`
- 主流程：计划确认、ERP/调拨、备料、生产报工、PQC 检验、批记录、放行。
- 衍生需求：班组基础维护、员工/设备/原因维护、QA 规程、PQC 提交与复核、质量异常、日结、审计和历史快照。

## Development Principles

- P1 阶段按能力模块并行开发，必须先冻结公共契约。
- P1.1 是 P1 的前置门禁，不参与并行开发；P1.2-P1.12 必须在 P1.1 契约冻结后再并行启动。
- P2 以后按业务依赖推进，不能跳过前序状态、数据和校验规则。
- 不引入 fallback、默认成功、mock 成功、空值补齐或吞异常。
- 正式批记录表单必须来自工序设置中的逐工序正式绑定，不得使用 `formBindings`、默认 `MAIN`、表单槽位或工序开始配置替代。
- 员工报工、PQC 提交、签名、设备、原因、规程版本都保留当时快照；后续配置变更只影响新业务。
- API-only 不能替代真实用户路径 E2E；写入型验收必须覆盖页面入口、权限、任务数据和清理证据。
- 调拨、报工、PQC、批记录、异常和放行所有写入链路都必须使用正式业务 ID 关联，禁止只靠名称、页面文案或前端缓存串联。

## Stage Overview

| 阶段 | 阶段目标 | 开发方式 | 完成标志 |
|---|---|---|---|
| P1 | 先冻结公共契约，再并行建设订单、调拨、报工、QA、PQC、批记录绑定和权限基础 | P1.1 先行，P1.2-P1.12 可并行 | 核心 ID、状态枚举、基础 CRUD/查询和角色权限可用 |
| P2 | 打通开工检查、报工分配、工序进度和 PQC 任务生成 | 依赖 P1 | 活跃订单可进入生产/PQC 主链路 |
| P3 | 打通批记录回填、过程检验汇集和退回补正追溯 | 依赖 P2 | 工序完成与 PQC 确认能形成批记录证据 |
| P4 | 打通异常、完整性检查、放行待办和放行审核闭环 | 依赖 P3 | 完整订单可放行，缺项或阻塞异常不可放行 |
| P5 | 完善日结、追溯、审计、历史快照和只读看板 | 依赖 P4 | 业务过程可追溯、可日结、可审计 |
| P6 | 联调、E2E、权限、并发、初始化和上线验收 | 依赖 P1-P5 | 正向链路和阻塞链路全部通过 |

| P6.11 | 数据迁移/初始化 | 初始化状态枚举、QA 基础配置、班组配置、原因字典、权限菜单 | 初始化脚本 | P1-P5 | 新环境初始化后可跑正向 E2E |
| P6.12 | 性能与并发校验 | 校验报工分配、PQC 提交、放行检查在并发下不重复、不超额、不脏写 | 并发测试报告 | P1-P5 | 并发确认不会重复回填或超额分配 |
| P6.13 | 上线验收 | 完成测试报告、缺陷修复、业务验收、发布检查 | 上线验收包 | P6.1-P6.12 | 正向链路、阻塞链路、权限、审计、并发均通过 |

## Milestone Gates

| 里程碑 | 验收标准 |
|---|---|
| M1 公共契约冻结 | 状态枚举、核心 ID、DTO、权限角色、核心表结构确认，不再随意改变字段语义 |
| M2 订单到报工分配打通 | 活跃订单能关联调拨，员工报工能被复核并分配到订单工序，工序进度正确 |
| M3 PQC 闭环打通 | QA 规程能生成 PQC 任务，PQC 能提交，PQC 组长能确认或退回，职责隔离生效 |
| M4 批记录闭环打通 | 工序完成后批记录可回填，PQC 确认后过程检验记录可汇集 |
| M5 放行闭环打通 | 完整订单能生成放行待办并放行，缺项或阻塞异常不能放行 |
| M6 上线可验收 | 正向链路、阻塞链路、权限、审计、历史快照、并发校验全部通过 |

## Cross-Stage Hard Gates

| 门禁 | 必须满足 |
|---|---|
| P1 并行启动门禁 | P1.1 公共契约冻结前，不得启动 P1.2-P1.12 的实现开发 |
| 调拨覆盖门禁 | 开工检查和放行检查不能只判断是否有关联调拨单，还必须判断物料、数量、批次和发货状态是否满足订单需要 |
| PQC 粒度门禁 | 首检、上午巡检、下午巡检、末检必须按订单、工序、日期/班次、轮次、规程版本和记录快照区分 |
| 批记录绑定门禁 | 缺正式逐工序批记录绑定或字段映射时，批记录回填和放行检查必须阻塞 |
| 异常责任门禁 | 所有阻塞放行的异常必须有责任角色、处理入口、当前状态和解除条件 |
| 历史快照门禁 | 配置、规程、人员、设备、原因、签名变更不得改写历史报工、PQC 或批记录 |

## Explicitly Out of P1

| 不纳入 P1 的内容 | 原因 |
|---|---|
| 自动生成 ERP 调拨申请或调拨单 | 当前矩阵明确本系统只同步和关联，不替代 ERP 生成调拨 |
| 复杂质量异常处理工作流 | P1 只需要能标记是否阻塞放行，完整处理流放到后续阶段 |
| 高级 FIFO 自动决策 | P1 只做建议和硬校验，避免自动分配错误扩大影响 |
| 复杂日结看板 | 日结依赖主链路状态稳定，放到 P5 |
| 大量配置中心扩展 | 只做报工、PQC、放行闭环直接依赖的配置 |

## Definition of Done

- 每个任务都有明确输入、输出、状态和责任角色。
- 每个行为变更都有 BDD 场景、RED、GREEN 和回归证据。
- 缺少正式前置条件时 fail fast，并在 UI/API 返回可追溯原因。
- 关键写入操作有审计、签名或历史快照。
- P6 完成前不得将静态合同、API-only 或手工数据库检查当作真实 E2E 替代。
