# PRD

## Purpose and Scope

定义“批次执行作废后负责人工作台任务闭环”的产品行为，确保已经下发到负责人工作台的任务在批次作废生效后不再可处理，同时保留完整审计链路。

本版本覆盖 6 项能力：

- 批次作废后进入终态。
- 负责人工作台待办与统计移除作废批次任务。
- 作废生效时取消同批次活动工作任务。
- 旧任务入口和旧链接继续被后端阻断。
- 作废、签名、归档失效、任务取消历史可追溯。
- 后续业务只能通过受控重开、补录、重执行或重新建批流程继续。

## Evidence Reviewed

- 用户问题：批次执行已给负责人工作台发任务后，如果批次执行被作废，正确流程应如何处理。
- `doc/tasks/20260726-edhr-personal-console-open-task-status/`：终态批次任务曾残留在个人控制台，修复方向是终态批次不可作为可操作待办。
- 当前系统设计文档：`docs/system/backend-api-design.md`、`docs/system/frontend-design.md`、`docs/system/data-model.md`、`docs/system/config-security-deployment.md`。
- 当前验收设计：`docs/acceptance/bdd-scenarios.md`、`docs/acceptance/tdd-plan.md`、`docs/acceptance/e2e-plan.md`、`docs/acceptance/test-data.md`。

## Product Summary

当批次执行作废审批或平台作废流程正式生效时，系统必须把该批次从生产执行态切换为审计终态，并同步关闭面向负责人的活动工作任务。用户刷新工作台后不应再看到该批次的待办或逾期任务；如果用户通过旧链接进入，系统应明确提示批次已作废且只能追溯审计。

## Target Users

- 负责人：接收和处理 eDHR 工作台任务的用户。
- 质量或生产审核人员：发起、审批或追溯批次作废的用户。
- 系统管理员或审计人员：核查批次状态、任务状态、签名、归档和变更事件的用户。

## First Version Scope

- 在作废生效点统一关闭活动任务，而不是只依赖前端隐藏。
- 仅取消待处理、处理中、逾期中的活动任务。
- 已完成和已取消任务保留原历史状态。
- 工作台列表、统计、审批中心待办、候选签名待办不得展示作废批次的可操作任务。
- 旧入口继续 fail fast，不新增可继续处理的兼容入口。
- 本次不做历史脏数据批量修复；如需修复既有作废批次残留任务，另走数据修复审批。

## Non-Goals

- 不物理删除工作任务、签名、表单、归档或变更事件。
- 不新增前端“静默成功移除”或接口失败时的本地假成功。
- 不放开作废批次的 `openTask` 处理权限。
- 不把作废后的任务自动转为可继续填写的只读或补录页面。
- 不在本功能内定义新的重开、补录、重执行业务流程细节。

## Functional Requirements

1. 作废终态：批次作废生效后，批次状态必须为 `VOIDED`，正常填写、审核、归档等处理动作被锁定。
2. 待办移除：负责人刷新工作台后，作废批次的可操作待办、逾期任务和统计数量必须消失。
3. 活动任务取消：作废生效时，同批次待处理、处理中、逾期任务必须变为已取消，并记录取消原因和完成时间。
4. 旧入口阻断：用户通过旧工作任务链接、旧菜单状态或缓存页面继续打开任务时，后端必须返回终态阻断错误。
5. 审计保留：作废原因、作废审批或签名、归档失效、任务取消状态、原任务负责人和时间戳必须可追溯。
6. 受控后续：作废批次不得复用原工作台任务继续处理；后续必须走已批准的重开、补录、重执行或新建批次流程。

## Business Rules

- 批次作废和活动任务取消应在同一正式生效流程中完成；任务取消失败时不得假装作废成功。
- 取消原因使用可审计文案，优先采用作废原因，格式为 `批次已作废：<原因>`。
- 已完成任务是历史事实，不能被重写为已取消。
- 工作台查询过滤是防御边界，不是唯一正确性来源；新作废必须真实取消活动任务。
- 历史脏数据只允许继续被终态过滤隐藏，不能在本功能中未经授权直接修复生产数据。

## States and Transitions

- 批次：可作废非终态 -> 作废生效 -> `VOIDED` 审计终态。
- 工作任务：待处理、处理中、逾期 -> 作废生效 -> 已取消。
- 工作任务：已完成 -> 作废生效 -> 已完成，保持不变。
- 工作任务：已取消 -> 作废生效 -> 已取消，保持不变。
- 归档：有效归档 -> 作废生效 -> 作废失效归档，保留追溯引用。

## Edge Cases

- 批次没有活动任务时，作废仍可按现有政策生效并保留审计。
- 批次只有已完成任务时，不应重写已完成历史。
- 用户打开已缓存的旧页面时，后端终态校验仍必须阻断提交。
- 作废原因缺失且现有流程要求原因时，必须失败并提示原因缺失。
- 历史作废批次仍存在活动任务时，本功能不自动修复；需要单独数据治理方案。

## Acceptance Criteria

- 作废生效后批次状态为 `VOIDED`，处理动作不可继续。
- 同批次活动工作任务变为已取消，原因以 `批次已作废：` 开头。
- 同批次已完成任务保持已完成，已取消任务保持已取消。
- 负责人工作台列表和统计不展示作废批次可操作任务。
- 旧任务链接调用失败且提示终态阻断，不返回可处理页面。
- 审计侧可看到作废事件、原因、归档失效和任务取消记录。

## Open Questions

- 是否需要为历史已作废但仍有活动任务的批次追加一次性数据修复。
- 是否需要在审计页面新增专门的“作废导致任务取消”筛选入口；当前版本只要求数据可追溯。

## Product Blockers

- 缺少可用测试账号、租户、真实工作台入口或测试批次数据时，真实 E2E 阻塞。
- 缺少任务状态、取消原因或完成时间字段时，必须先完成 schema 核对，不能用前端隐藏替代。
