# 测试服务器智能排产问题独立验证报告

## 结论

- 总体结论：`PARTIAL / BLOCKED`。代码、部署版本元数据和静态合同已确认多项真实问题；用户已补充 `zhaojie` 登录后的工艺路线截图，权限链路根因已通过测试库只读查询定位，其他筛选和指定工单仍缺少可控登录会话做最终页面复现。

- 首屏全部数据符合 2026-08-05 已验收的“标准列表默认空条件”契约；问题不是首屏无默认值，而是用户选择状态后界面看起来已经生效，实际仍需另点“查询”。

## 逐项判定

### 1. “可入池”返回全部 1499 条并包含已入池工单

- 判定：`HIGH-CONFIDENCE CONFIRMED（交互状态缺陷）/ 请求序列待登录取证`。
- 证据：首屏按正式契约不带 `admissionStatus`，因此显示全部记录；选择“可入池”只更新草稿和标签，不会自动发起查询，也没有“待应用”提示。
- 解释：选择后未另点“查询”时，列表继续保留首屏 1499 条并包含已入池工单，与当前实现完全一致。

### 2. “阻断”标签下显示 126 条可入池记录

- 判定：`HIGH-CONFIDENCE CONFIRMED（交互状态缺陷）/ 请求序列待登录取证`。
- 证据：条件 Tab 标签直接读取当前草稿条件；普通下拉变更仅更新草稿，不触发 `query`；只有点击“查询”等路径才刷新列表。
- 解释：若上一次已经执行“可入池”得到 126 条，再把下拉改为“阻断”但未点击查询，标签会显示“阻断”，列表仍保留 126 条可入池结果。

### 3. “已入池”标签下显示 1332 条阻断记录

- 判定：`HIGH-CONFIDENCE CONFIRMED（交互状态缺陷）/ 请求序列待登录取证`。
- 解释：若上一次已经执行“阻断”得到 1332 条，再把下拉改为“已入池”但未点击查询，会出现该现象。

### 4. 入池状态枚举疑似整体错位

- 判定：`NOT SUPPORTED`。
- 前端选项与展示映射均为：可入池=`READY_TO_ADMIT`、已入池=`ALREADY_ADMITTED`、阻断=`BLOCKED`。
- 后端按同样三个字符串生成状态，并以 `equals` 精确过滤；未发现 ordinal、数组下标或互换映射。
- 当前证据支持“草稿标签先于查询结果变化”，而不是枚举错位。

### 5. “完成筛选”命名不清晰

- 判定：`CONFIRMED`。
- 证据：页面字段名称确为“完成筛选”，选项为“未完成 / 全部 / 已完成”。字段语义实际是完成状态，建议后续需求使用“完成状态”。

### 6. 非冻结工单复选框禁用但无直接原因

- 判定：`CONFIRMED`。
- 证据：复选框可选性只依据冻结、已完成、已取消；代码虽然能生成这些阻断原因，但复选框本身没有 tooltip 或行内原因说明。阻断问题数并不是该复选框禁用依据。

### 7. 承诺交期早于计划时间但风险提示不明显

- 判定：`PARTIALLY CONFIRMED`。
- 证据：页面已有两种纯颜色提示：计划开工晚于最晚开工显示红色，计划完成日期晚于承诺交期显示橙色。
- 结论：不能认定“完全没有提示”，但只有颜色、没有图标、文字、逾期天数或行级风险标识，用户认为“不明显”成立；实时可见性仍待登录核对。

### 8. `SMOKE-BND-0623212519` 日期全空仍可重排和完成

- 判定：`行为由代码确认，业务规则待确认`。
- 证据：手动重排勾选只排除冻结、已完成、已取消，不校验承诺交期、最晚开工、计划开工和计划完成；人工完成后端同样不要求这些日期。
- 风险：人工完成缺少关键数据前置校验的风险较高；但“未排产工单缺少计划日期能否参与重排”可能是正常业务，需要产品规则区分，不能直接把所有空日期视为同一缺陷。

### 9. 物料清单缺失、当前工序为空仍开放操作

- 判定：`行为由代码确认，允许范围待业务确认`。
- 证据：列表会显示物料清单“缺失”和当前工序“-”；调整优先级、交期、冻结等治理操作没有基于这两个字段禁用，人工完成也未据此拦截。
- 建议判定口径：调整、交期和冻结可能用于补救或管控异常工单，不应在未确认规则前统一禁用；人工完成应单独确认更严格的完整性门禁。

### 10. 阻断记录要求工艺维护但 `zhaojie` 缺少权限

- 判定：`CONFIRMED（测试服权限迁移缺失）`。
- 页面证据：用户提供的 `zhaojie` 登录截图中工艺路线共 4 条，“操作”列全部为空；新增、导入、导出也未显示。
- 账号角色证据：测试库中 `zhaojie` 为 tenant `1` 的启用用户 `1074`，有效绑定启用的 `排产员/mes_scheduler` 角色 `910216`。
- 权限证据：该角色的 `5720` 父菜单和 `5721/mes:pro-route:query` 有效；`5723/mes:pro-route:update` 行被软删除；`5730/mes:pro-route:version-query` 菜单不存在。前端因此不会渲染“产品/编辑/版本”。
- 迁移证据：测试环境没有 `20260716_mes_route_version_permission_menu` 与 `20260728_mes_scheduler_route_flow_list_permission` 的应用记录；后者的正式目标就是为排产员补齐 `5723` 与 `5730`，并明确不授予删除权限 `5724`。
- 结论：不是有意的职责分离，也不是 `zhaojie` 未绑定排产员角色；根因是测试服务器缺少已经存在于仓库中的正式权限迁移。当前未获远端数据写入授权，因此只读定位后停止。

## 根因判断

1. `TableMultiFilter` 把草稿条件同时用于可见 Tab 标签，却只在显式查询时刷新数据，造成标签和结果口径短暂或持续不一致。
2. 页面没有自动查询或“待应用”状态，用户无法从标签判断当前表格究竟对应首屏、上一次查询还是正在编辑的条件。
3. 当前状态常量和后端精确过滤逻辑一致，不支持“枚举整体错位”判断。
4. 聚焦静态测试仍要求 8 月 4 日旧版“默认可入池”条件，但 8 月 5 日的后续正式任务已把排产工单和同步工单统一改为“首屏空条件”；测试合同未同步，不能把该失败用作默认条件回归证据。
5. `zhaojie` 的编辑按钮缺失来自测试库角色菜单数据：`mes_scheduler` 的 `5723` 绑定仍是软删除，`5730` 菜单尚未创建；现有正式迁移未在测试环境应用。
