# E2E Plan

## Purpose and Scope

本计划验证管理员通过真实页面配置原表到辅助模式的对应关系，并验证两名员工通过真实工作任务只填写各自负责的辅助行。Playwright 必须走现有菜单、弹窗、工作任务和执行页；API 仅用于最终状态、快照、审计和越权结果核验。

## Evidence Reviewed

- 批记录表单列表和现有“单元格规则”弹窗入口。
- `ExecutionPage.vue` 的原表/辅助模式切换、保存、提交和字段审计入口。
- `edhr-work-task/my-page` 的真实当前用户任务入口。
- 现有辅助模式真实 E2E 的全屏、任务切换和填写人关系验证方式。
- 项目 `docs/e2e-rules.md` 的真实数据、登录、Element Plus 和失败证据要求。

## User Paths

### P01 管理员完成填写配置

管理员从批记录表单列表打开目标草稿版本的“填写配置”，纠正五类字段，创建四个辅助行，为各行配置描述和员工，保存并重新打开确认。

验收点：

- 不离开当前列表进入第二个设计器。
- 点击辅助行和原表单元格可以双向定位。
- 两个单元格可组成一行并共享员工甲。
- 一个单元格可单独成行并分配给员工乙。
- 下拉框选项顺序保存后不变。
- 保存完成后两个现有接口均成功。

### P02 员工甲填写自己的辅助行

员工甲从“我的工作任务”打开真实 FILL/REWORK 任务，进入辅助模式，填写生产批号、实际数量和下拉结果。

验收点：

- 只显示员工甲负责的辅助行。
- 不显示员工乙负责的日期和签名辅助行。
- 切到原表后值立即一致。
- 员工乙单元格在原表中只读。
- 保存通过现有字段审计签名入口。

### P03 员工乙填写自己的辅助行

员工乙从自己的工作任务打开同一执行，填写日期和签名单元格。

验收点：

- 只显示员工乙负责的辅助行。
- 原表仍可看到员工甲已填写的上下文值，但不可修改。
- 日期和签名通过现有控件、签名记录和审计链保存。

### P04 后端拒绝越权写入

在 P02 的合法 UI 保存完成后，使用员工甲同一登录上下文构造一次针对员工乙坐标的字段写入请求，作为最终安全核验。

验收点：

- API 明确失败。
- 员工乙字段值未变化。
- 字段审计链没有产生越权记录。

### P05 版本与历史隔离

基于 V1 创建执行后，管理员在 V2 草稿中移动一个单元格、更换描述和填写人，再创建 V2 执行。

验收点：

- V1 执行仍按 V1 配置展示和授权。
- V2 执行使用新配置。
- V1 历史详情不读取 V2 的描述或下拉选项。

### P06 未配置辅助模式

打开一个执行快照中没有 `assistRows` 的旧版本。

验收点：

- 点击辅助模式显示“未配置辅助模式”。
- 页面不自动从 `fields` 归并生成行。
- 原表模式仍按冻结字段和权限工作。

## Browser or Client Steps

1. 运行登录前置检查，确认管理员、员工甲、员工乙属于同一测试租户且菜单权限有效。
2. 管理员通过左侧菜单进入批记录表单列表，按任务数据前缀筛选目标报表。
3. 点击“填写配置”，等待 `GET /cell-rules` 和 `GET /get-by-report` 成功。
4. 依次点击目标坐标，设置文本、数字、日期、签名、下拉框类型。
5. 在下拉框中新增、删除、排序选项，并确认至少两个有效值。
6. 新建 `AR_001`，输入描述，选择生产批号和实际数量两个单元格，分配员工甲。
7. 新建日期、签名和结果辅助行，分别分配员工乙、员工乙、员工甲。
8. 验证点击行高亮多个原表单元格，点击已映射单元格反向选中行。
9. 将一个测试单元格从一行移动到另一行并确认唯一归属，再移动回最终设计。
10. 点击“保存填写配置”，等待两个保存请求完成且只出现一次成功提示。
11. 关闭并重新打开弹窗，逐项核对规则、选项、行描述、顺序、坐标和填写人。
12. 按现有真实业务流程发布版本、创建批次执行和填写任务。
13. 员工甲登录，从“我的工作任务”打开任务，完成 P02。
14. 员工乙登录，从“我的工作任务”打开任务，完成 P03。
15. 回到员工甲上下文，完成 P04 的最终 API 越权验证。
16. 创建 V2 并完成 P05。
17. 打开无辅助行快照的旧执行完成 P06。

每次账号切换必须重新确认当前用户标识，不能只替换本地显示名称。

## API Verification

最终核验允许读取以下正式接口响应：

- `GET /mes/pro/batch-record-report/cell-rules`：规则、`assistRows`、下拉选项和 `rowKey` 读回一致。
- `GET /mes/pro/edhr-process-form-permission-rule/get-by-report`：每个 `scopeKey` 的候选来源和有效用户正确。
- 任务打开响应：返回当前用户有效的现有 `fillableScopeJson`，且同一行不同列可区分。
- 执行详情或快照接口：`fields` 与 `assistRows` 同时存在并带版本来源。
- 字段审计查询：合法保存有记录，越权请求无新增记录。
- 历史执行详情：V1 快照摘要与 V2 当前配置不同但稳定。

越权验证请求必须使用任务自有字段和测试账号，不得修改其他业务数据。

## Console and Log Checks

- Playwright 收集 `pageerror`、浏览器 `console.error`、失败 HTTP 响应和接口业务错误。
- 保存配置期间任一 API 失败都使测试失败；不能因出现第一步成功 toast 而忽略第二步失败。
- 员工页面不得出现权限扩大、快照解析失败、字段身份缺失或未捕获异常。
- 后端日志不得出现被吞掉的 JSON 解析、候选人解析或字段审计异常。
- 测试结束时输出管理员配置 ID、报表版本 ID、执行 ID、工作任务 ID、两名员工 ID 和字段审计修订号。

## Test Blockers

- 必须有可编辑且未被其他任务占用的草稿批记录版本；已发布版本不能直接修改。
- 必须有两个独立有效员工账号和一个可选的有效角色，不能用管理员冒充所有填写人。
- 必须确认本地 `8081/48081` 服务属于 `E:\IntRuoyi` 的 `int_main`，不能连接到其他 worktree 或旧 jar。
- 必须存在从 UI 创建或进入真实批次执行和工作任务的入口；若入口缺失，实现任务应按批准范围补齐并纳入 TDD。
- 测试数据或权限缺失时停止，不能改用 mock、直接 SQL 填值或 API-only 主流程。
