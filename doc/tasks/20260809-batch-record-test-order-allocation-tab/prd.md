## Test Definition Paragraphs

1. **工序共享报工池与分配范围**：报工按工序进入共享报工池，不存在“当前订单”；该工序组长只能把合格可分配数量分配给其可见的活跃工单。现有活跃工单需求不足时不得拒绝报工，尚未分配数量仍归属于本次报工。
2. **FIFO 固定顺序与部分分配**：FIFO 严格按照活跃工单列表的固定全局顺序分配，列表位置靠前的工单先于靠后的工单。报工不足时允许先部分满足最靠前工单并保留该工单未完成需求；报工超额时依次满足现有工单，超出需求的未分配数量继续保留在本次报工池。
3. **FIFO 草稿与空白手工分配**：FIFO 只生成可调整的分配草稿，组长可以在草稿上修改、拆分或转移未放行数量，也可以从空白状态开始手工分配；手工调整不要求继续遵循 FIFO，但仍受工序范围、可分配数量和订单当前工序剩余需求约束。
4. **未放行调整与已放行锁定**：未放行分配可以修改、删除、拆分或从 A 工单转移给加急 C 工单；已放行分配必须以绿色显示并锁定，不得修改、删除或转移。部分放行时只锁定已放行部分，剩余未放行部分仍可调整。
5. **分配订单列与管理/历史视图**：报工管理列表必须有“分配订单”列，展示每个工单及其分配数量，并将已放行项显示为绿色。报工提交后永久保留历史；只要存在未分配数量或未放行分配就留在报工管理，未分配数量为零且全部分配均已放行后从管理列表移除并可在报工历史查询。
6. **合格可分配数量关系**：报工数量必须区分合格可分配数量与不合格、冻结或待检数量；只有合格数量可以进入订单分配。必须满足“合格可分配数量 = 已放行锁定数量 + 未放行预分配数量 + 尚未分配数量”，任何分配不得突破本次报工的合格可分配数量或目标工单当前工序剩余需求。
7. **调整增减审计**：未放行数量在工单间调整时不得覆盖原归属，必须形成可追溯的增减记录，例如 A 工单 `-100`、C 工单 `+100`，并记录操作人、操作时间、原工单、目标工单和调整原因。
8. **并发重校验与工单状态变化**：确认分配时必须在并发保护下重新校验报工可用数量和工单当前工序剩余需求，防止重复占用。工单减量、暂停或取消时，未放行数量退回原报工池；已放行数量不得自动退回，后续纠错必须走正式冲销流程。

## Business Rules

- 本任务中的八段文字是未来生产功能的验收合同，而不是模拟数据或“功能已完成”标记。
- “按工序分配”和“组长可见活跃工单”是候选范围，不引入“当前订单”概念。
- FIFO 的早晚只取活跃工单列表的固定全局位置；手工分配可以覆盖未放行草稿顺序。
- 放行是本次测试合同中的不可修改边界；部分放行必须按数量局部锁定。
- 历史记录永久存在，管理列表是仍需处理的工作台视图，两者不是同一生命周期状态。
- 所有失败前置必须显式展示，不添加 mock、fallback、默认成功或静默降级。

## States and Transitions

测试定义 UI 本身沿用现有测试任务状态：源码固定定义 -> 持久化定义（如已创建/更新）-> CODE_READONLY 执行 -> 终态结果。页面加载时若存在持久化定义，则必须恢复其结构化描述。

八段文字要求未来生产功能至少能区分：尚未分配、已预分配但未放行、已放行锁定、全部分配且全部放行。未放行数量可以重新分配；已放行数量不可逆转移；完成后的报工退出管理工作台但历史记录保留。

## Edge Cases

- 报工量小于最靠前工单需求时，文字必须明确“部分满足”，不能把整次分配描述为失败。
- 报工量大于所有活跃工单需求时，文字必须明确“未分配数量保留”，不能要求强制分完。
- 同一次分配部分放行时，只锁定对应数量，不能把整行全部锁定或全部开放。
- 活跃工单跨分页时，FIFO 仍按固定全局列表位置，不得按当前可见页重新排序。
- 页面存在同名持久化测试项或缺少结构化描述时，沿用现有 fail-fast 规则。
- 测试租户、权限、运行服务或真实菜单入口缺失时，验证必须阻塞并记录缺失前置，不得改用 mock 页面。
