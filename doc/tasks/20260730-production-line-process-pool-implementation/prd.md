# PRD

## Goal

在现有 IntRuoyi MES 报工、记录本/eDHR、生产工单和批记录能力上，新增生产一线报工工序池闭环，使一线员工在“报工”入口完成简化填写和电子签名后，同时生成报工信息、记录本原始数据和工序池提交事件，并支持 PQC、FIFO 和时间轴追溯。

## Scope

- F1：新增正式工序池和“工序池提交事件”。
- F2：实现报工 + 记录本 + 工序池的一体提交。
- F3：实现固定几类一线模板，第一版覆盖生产简化模板和 PQC 简化模板。
- F4：实现设备账号内切换实际员工和对应 UI/模板切换。
- F7：实现基于生产工单计划开始时间的 FIFO 分配基础逻辑。
- F8：实现工序池提交事件时间轴 / 甘特图只读查询。

## Non-Goals

- 不实现排产系统。
- 不把现有余量池改名为工序池。
- 不在一线提交阶段按上下限裁剪原始值。
- 不实现完整审核副本编辑模块，但必须保留审核副本状态/关联边界。
- 不允许用 mock、默认成功或 API-only 替代真实路径验证。

## User or System Scenarios

- 一线生产员工在设备账号登录的机器上切换到自己，选择当前授权工序，填写上工序输入数量、设备参数、输出数量、损耗数量，电子签名后提交。
- PQC 员工在简化模板中只选择检测成功或失败，电子签名后提交，并形成过程检验记录。
- 管理人员查看工序池时间轴，知道某天谁在什么设备、什么工序、什么生产工单下提交了什么。
- 系统从工序池按生产工单计划开始时间 FIFO 分配数量，并锁定已分配的数量片段。

## Functional Requirements

- AC-01：系统必须新增正式工序池模型和工序池提交事件，不能以 `mes_pro_feedback_surplus_pool` 作为主模型。
- AC-02：每条工序池提交事件必须保存服务端提交时间、唯一电子签名、登录账号、实际员工、设备、工作站、生产工单、路线、工序、模板类型、原始 payload、报工来源和记录本来源。
- AC-03：PQC 成功/失败必须保存为工序池过程检验记录，并关联提交事件。
- AC-04：一线报工入口必须一次提交并在同一事务内形成报工、记录本原始条目/事件和工序池提交事件。
- AC-05：组合提交必须保留原始超限值，不得在一线提交阶段按上下限裁剪或拒绝。
- AC-06：固定生产模板必须只展示当前工序简单字段：上工序输入数量、设备、设备参数、输出数量、损耗数量。
- AC-07：PQC 固定模板第一版只允许检测成功或检测失败。
- AC-08：设备账号必须绑定 `X >= 1` 个工艺路线，账号内只能切换绑定路线下工序。
- AC-09：工序内只能切换绑定员工；切换员工不改变登录账号、不二次验证，电子签名代表实际员工身份。
- AC-10：一线提交不受工艺路线前后置顺序限制，但路线仍作为权限和追溯上下文保存。
- AC-11：同一工序允许多人多次分片提交，工序完成按数量累计判断。
- AC-12：FIFO 只面向生产工单，按生产工单计划开始时间升序分配；计划开始时间缺失时阻塞。
- AC-13：FIFO 分配明细必须追溯到工序池、提交事件、数量片段、生产工单、工序和分配数量。
- AC-14：已 FIFO 分配的原始记录或数量片段不得修改。
- AC-15：时间轴 / 甘特图必须按服务端提交时间只读展示事件，支持日期、员工、工序、设备、模板类型、生产工单过滤。
- AC-16：时间轴详情必须可追溯原始 payload、PQC、FIFO、审核副本状态和修改历史摘要，且不提供写操作。
- AC-17：批记录表单、表单槽位 `formBindings`、工序开始配置三条链路不得混用。

## Non-Functional Requirements

- 所有缺失前置条件必须 fail fast。
- 不允许 fallback、静默降级、吞异常、默认员工、默认模板、默认路线或默认成功。
- 一线提交、FIFO、原始记录修改、时间轴查询必须具备结构化来源字段和审计证据。
- 前后端错误必须真实暴露，不得通过空数据或成功 toast 掩盖。

## Dependencies and Constraints

- 依赖现有 MES 报工服务、生产工单服务、批记录/eDHR 记录和电子签名能力。
- 依赖正式数据库迁移和 MyBatis/DO/Mapper 契约。
- 依赖测试租户、设备账号、员工、设备、工作站、生产工单、路线、工序、模板和签名测试能力。
- 多 worktree 并行存在共享 schema 依赖，主线程合并时必须先融合 F1 基础模型，再融合依赖模块。

## Acceptance Criteria

- AC-01 至 AC-17 全部有对应 RED/GREEN/REGRESSION 或明确 blocker 证据。
- 21 条需求门禁 R01-R21 全部在主线程 review 中 PASS。
- 6 个 worktree 的变更均已 review，未通过项已退回修复。
- 融合进 `int_main` 后系统级定向验证通过。
