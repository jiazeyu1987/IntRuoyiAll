# PQC 生产放行 MVP 补齐

## Task Goal

在独立 worktree 中补齐最新文档要求的 PQC 生产放行前端闭环，并在验证通过后融合进 `int_main`：提供 `待放行`、`已放行`、`已作废`、`已返工`、`已让步放行` 五个状态页签；待放行记录只提供 `放行` 和 `不合格审查`；放行必须使用当前 PQC 负责人电子签名；不合格审查复用现有统一不合格评审流程。

## Milestones

- [x] M0：核对现有生产放行、不合格评审、签名和追溯代码，确认差距。
- [x] M1：先补 BDD 与前后端 RED 测试，锁定五状态列表、动作和签名合同。
- [x] M2：实现后端 PQC 放行分页查询和签名校验。
- [x] M3：实现专用 PQC 生产放行页面、五状态页签及两个操作入口。
- [x] M4：完成 GREEN、相关回归和真实页面验证。
- [x] M5：完成收尾并按用户要求融合到 `int_main`。

## Expected Verification

- 后端测试覆盖五类状态查询、候选权限、签名成功、签名失败、冻结拦截和重复放行。
- 前端静态合同覆盖五个页签、待放行两个动作、无拒绝动作、签名确认弹窗、成功刷新和查看批记录。
- `mvn -pl yudao-module-mes -am -DskipTests compile`、目标 JUnit、`pnpm ts:check` 和相关静态回归通过。
- 真实 E2E 使用 Playwright 从真实页面入口验证；缺账号、签名或正式待放行数据时记录精确 blocker，不用 API-only 冒充通过。

## Applicable Experience Gates

- 生产放行必须使用正式申请、PQC 候选、冻结状态、批次执行和不合格评审数据，不增加 mock、默认成功或静默降级。
- 电子签名由后端权威校验；前端密码不得持久化、回显或写入日志。
- 列表状态与请求参数必须同步；页签切换后从后端按目标状态重新加载，不在前端伪造状态。
- 不合格审查继续复用统一评审单和 QA 处置状态机，不新建第二套异常流程。
