# 活跃订单放行资料开发方案 V2

## 目标

第一版以“真实历史数据支撑双 100%，生产组长申请后能走到生产负责人放行”为目标。开发时限制能不增加就不增加，但必须保证四件事：来源真实、映射明确、资料完整、可测试可追溯。

## 实施原则

- 不直接改活跃订单进度造成功路径。
- 不绕过生产组长/PQC 组长历史列表和历史表单。
- 不用 `formBindings`、默认 `MAIN` 或工序开始配置替代正式批记录。
- 不制造签名、审核人或时间。
- 不直接放行，只提交生产负责人待办。
- 缺数据或缺映射时返回 blocker，不生成假资料。

## 分阶段开发

### M0 实现前置收敛

- 先确认过程检验单和损耗单的正式承载；若只能确认其中一类，首版成功路径只验收已确认承载，未确认部分返回 blocker。
- 先确认生产负责人来源；首版默认复用 `RELEASE_APPROVE`，不新增第二套负责人配置。
- 先确认损耗单最小字段映射；字段未确认时不开发兜底损耗单。
- 首版不拆多个独立服务：以 `MesTeamLeaderActiveOrderReleaseApplicationService` 为入口，内部方法或包内小组件完成来源校验、映射、写入和待办创建；后续复杂度上来后再提取独立服务。
- 首版双 100% 来源校验不重建完整进度计算体系，只校验当前进度背后的正式来源记录、历史表单、汇集明细、签名和 source hash 可追溯。

### M1 入口和申请状态

- 后端新增或完善 `active-order/release/apply` 申请接口。
- 活跃订单列表返回申请状态、阻塞摘要、批次执行 ID、待办 ID。
- 前端增加“申请放行”按钮、确认框、行级 loading、状态展示和 blocker 展示。

### M2 双 100% 来源校验

- 后端不能只看活跃订单进度字段。
- 生产进度校验必须能追溯到生产提交、生产组长确认、生产历史表单和相关工序完成记录。
- 检验进度校验必须能追溯到 PQC 提交、PQC 组长复核、PQC 历史表单和过程检验汇集明细。
- 若进度为 100% 但历史来源缺失，申请返回 blocker。

### M3 批记录映射

- 按产品、路线版本、工序定位正式批记录表单。
- 从生产历史数据读取一线生产填写人、设备、设备参数、数量、损耗、提交签名时间。
- 从生产组长确认记录读取审核人、审核意见、审核签名时间。
- 按字段映射写入正式批记录执行和字段审计。

### M4 过程检验单映射

- 按产品、路线工序和 QA 文件定位检验项目。
- 从 PQC 历史数据读取检验员、设备、项目结果、实测值、判定、提交签名时间。
- 从 PQC 组长复核读取审核人、复核结论、复核签名时间。
- 按字段映射写入正式过程检验单。

### M5 损耗单映射

- 从生产报工和损耗历史读取损耗数量、损耗原因、工序、产品、批号和处理说明。
- 校验损耗合计、数量边界和模板必填字段。
- 按字段映射写入正式损耗单；无损耗时只在模板支持无损耗口径时生成确认项。

### M6 批次执行和负责人放行

- 创建或复用正式 eDHR 批次执行。
- 将批记录、过程检验单、损耗单挂到同一批次执行。
- 资料完成性检查通过后创建或复用 `RELEASE_APPROVE` 生产负责人待办。
- 放行状态进入 `PENDING_RELEASE_APPROVAL`，不直接 `RELEASED`。

### M7 追溯和幂等

- 申请表保存活跃订单、来源快照 hash、批次执行、放行事务、负责人待办、资料摘要和 blocker。
- 同一活跃订单同一来源快照重复申请返回既有结果。
- 来源变化后重新预检。

## 映射关系设计

### 主键链路

`activeOrderId -> workOrderId -> productId -> routeId/routeVersionId -> routeProcessId/processId -> batchExecutionId -> batchTaskId/formExecutionId -> releaseTransactionId -> releaseApprovalWorkTaskId`

### 生产到批记录

- 源：一线生产提交事件、生产历史表单、设备参数、损耗明细、生产组长确认。
- 目标：对应工序正式批记录表单字段。
- 关键映射维度：`activeOrderId + routeProcessId + processId + submitEventId + batchRecordReportId + fieldCode/cellKey`。
- 人员：填写人来自一线生产提交人；审核人来自生产组长确认人。
- 时间：填写时间来自提交签名时间；审核时间来自组长确认签名时间。

### PQC 到过程检验单

- 源：一线 PQC 提交、PQC 历史表单、QA 文件项目、PQC 组长复核、汇集明细。
- 目标：正式过程检验单字段。
- 关键映射维度：`activeOrderId + routeProcessId + qaRegulationVersionId + pqcTaskId + aggregateDetailId + fieldCode`。
- 人员：填写人来自 PQC 检验员；审核人来自 PQC 组长。
- 时间：填写时间来自 PQC 提交签名时间；审核时间来自 PQC 组长复核签名时间。

### 损耗到损耗单

- 源：生产提交损耗字段、损耗原因明细、损耗快照、报工/调拨追溯。
- 目标：正式损耗单字段。
- 关键映射维度：`activeOrderId + routeProcessId + productionSubmitEventId + lossReasonId + fieldCode`。
- 人员：填写人来自生产提交人；审核人优先来自生产组长确认人。
- 时间：填写时间来自生产提交签名时间；审核时间来自生产组长确认签名时间。

## 完成性检查

- 批记录：目标表单必填字段全部有来源；设备和参数满足工序/批记录要求；填写/审核签名来源存在。
- 过程检验单：QA 文件要求的项目全部有结果；设备和标准符合产品/工序；PQC 组长复核通过；填写/审核签名来源存在。
- 损耗单：损耗数量和原因一致；无损耗口径有模板支持；必填字段和签名来源存在。
- 放行：批记录、过程检验单、损耗单均完成后才创建负责人待办。

## 推荐接口

- `POST /mes/pro/process-pool/team-leader/active-order/release/apply`
- `GET /mes/pro/process-pool/team-leader/active-order/release/get?activeOrderId=...`
- 活跃订单列表扩展放行状态字段。

## 最小新增数据

- 第一版只新增申请记录表，用于幂等、状态、来源快照和对象关联。
- 第一版不新增字段映射快照表；优先复用批记录字段审计、PQC 汇集明细、损耗来源记录和操作审计。
- 只有现有审计无法证明字段来源时，才在后续版本新增字段映射快照表。
- 不新增平行批次执行主表。
- 不新增无来源的临时资料表。

## 验证顺序

1. 静态合同测试锁定禁止直接改进度、禁止 `formBindings` 替代、禁止直接放行。
2. 后端单测覆盖来源校验、映射、完成性、幂等和 blocker。
3. 前端静态合同覆盖按钮、确认、状态和 blocker。
4. 真实测试数据 fixture 生成生产/PQC 历史数据。
5. Playwright 走生产组长申请和生产负责人放行。

## 第一版降复杂度边界

- 不把每个模块先拆成独立 service；先保证申请主链路能走通。
- 不为未确认的过程检验单/损耗单承载写临时适配；未确认就 blocker。
- 不为了测试方便写进度字段；测试 fixture 必须产生历史数据和历史表单。
- 不新增字段级追溯表，除非现有审计无法支持验收。

## 暂不做

- 自动触发。
- 批量申请。
- 新增复杂审批流。
- 历史脏数据自动修复。
- 无模板情况下的兜底表单。
