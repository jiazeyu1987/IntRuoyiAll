# 生产组长活跃订单异常操作整合

## Task Goal

将生产组长“异常”页签的订单异常上报能力合并到活跃订单池行操作中：每行提供“移除”和“报异常”，异常上报仅填写异常原因；已上报异常的生产订单 ID 显示为红色，并从后续自动、手工工作分配中排除。

## Milestones

- [x] M1：确认现有活跃订单、异常上报和工作分配正式数据链路
- [x] M2：以 BDD 和失败测试固定新交互、接口及分配约束
- [x] M3：实现后端异常状态投影、异常上报校验及分配拦截
- [x] M4：实现前端行内“移除 / 报异常”、红色标识并删除异常页签
- [x] M5：完成相关单元、静态回归与真实页面 E2E 验证
- [x] M6：完成任务清理、经验沉淀和收尾记录
- [x] M7：复现并锁定运行 Jar 仍校验旧异常原因编码的回归
- [x] M8：刷新本机稳定运行 Jar，完成登录态接口与真实页面复验

## Expected Verification

- 后端：异常上报服务、活跃订单列表、FIFO 分配、手工分配的定向 JUnit 测试通过。
- 前端：活跃订单池与最小异常上报静态契约测试通过，旧“异常”页签契约已更新。
- E2E：通过生产组长真实页面从活跃订单行打开“报异常”，填写原因并提交；刷新后生产订单 ID 显示红色，且该订单不再出现在工作分配候选中。
- 回归：前端相关静态测试与后端受影响模块测试通过。

## Current Status

completed：运行 Jar 请求合同已刷新，真实页面上报、并发运行态接管后的复验和任务清理均通过。

## 设计约束检查

- `是否引入 fallback/降级/吞异常`：否。
- `是否从根因和长期维护角度解决`：是；以统一的“未关闭异常状态”查询服务作为列表、自动分配、手工分配和重复上报的共同约束来源。
- `是否存在临时补丁或绕过`：否。

## Applicable Experience Gates

- 前端按钮行为必须有真实点击结果，不能只更换文案；行级异常上报需绑定当前活跃订单。
- 活跃订单及分配约束必须使用后端正式活跃池与异常记录，不以仅前端过滤代替服务端校验。
- 写入型 E2E 必须使用可追踪的任务数据，并通过真实页面路径完成；接口仅用于最终只读核验。
- 本次沿用既有异常表结构，不新增数据库迁移；接口仅接收用户填写的异常原因，内部分类码由异常服务固定写入。
