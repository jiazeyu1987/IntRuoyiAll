# eDHR 偏差管理 PRD

## Purpose and Scope

本 PRD 定义 eDHR 偏差从批记录级发起、单次处理、电子签名、关闭或转入不合格评审、批次控制和追溯的首版业务行为。偏差只关联一份正式批记录；一份批记录可以关联多条偏差。

## Evidence Reviewed

- 用户提供的《偏差处理记录表》：单张连续表格分为偏差基础信息和偏差调查与处理两部分。
- resource/相关文档/电子批记录系统的审核要求8.25.xlsx：重点要求位于 C15、C18、C34、C35、C36；通用签名、审计追踪和归档要求见 C5–C10、C38–C40。
- 当前系统批记录详情、活跃订单批记录详情、批记录追溯、不合格评审、电子签名和批次冻结服务。
- 任务内执行日志记录了工作区快照限制和现有实现边界。

## Product Summary

偏差管理模块提供统一的批记录级偏差登记、处理、关闭和查询能力。管理界面包含全部、未处理、已处理三个列表页签；用户可打开偏差详情查看发起内容、处理内容、电子签名和关联不合格审批。活跃表单/批记录详情及批记录追溯均增加“偏差”页签。

系统区分两个偏差等级：

- 普通偏差。
- 重大偏差（亦称关键偏差，两者是同一等级）。

用户最后确认的两档等级覆盖 Word 原表中的三级选项；界面只显示“普通偏差”“重大（关键）偏差”。不建立原表“主要偏差”到新等级的自动映射，不导入或改写历史等级。

只有重大（关键）偏差可以由 QA 发起不合格审批，并且只有该等级的常规偏差处理流程需要管理者代表签名。

## Target Users

- 已获管理员赋予“偏差发起”权限的业务人员：发起偏差。
- 获得偏差处理、验证或批准权限的人员：填写并签署对应处理环节；一个账号可以承担多个角色。
- QA：关闭偏差；对重大（关键）偏差手动发起不合格审批；按权限完成 QA 评审。
- 获得 PQC 生产放行权限的人员：按现有不合格评审流程选择让步放行、作废或返工。
- 质量负责人、重大（关键）偏差的管理者代表：完成对应批准签名。
- 管理员：向用户角色手动授予偏差权限。
- 获得偏差查询权限的用户：查看当前租户全部偏差及详情，列表不限制为本人发起。管理员通过角色授予权限，不自动给所有登录账号授权。

## First Version Scope

1. 以正式批记录为唯一业务关联对象，一条偏差只能关联一个批记录。
2. 一份批记录可关联多条偏差；上市放行成功后禁止新增关联偏差。
3. 创建偏差编号 PC-YYYYMM-流水号。
4. 按参考记录表录入发起和处理内容；每条偏差至多一份处理记录，常规关闭前必须完成；允许原记录修订和重新验证，不新增第二份处理单。
5. 按偏差等级及签署节点执行电子签名、内容绑定和审计。
6. 提供全部、未处理、已处理列表和偏差详情。
7. 为批记录详情/活跃表单详情及批记录追溯提供“偏差”Tab。
8. 未关闭偏差与待处置不合格评审分别阻止指定批次动作。
9. QA 可以在批记录上下文手动对重大（关键）偏差发起不合格审批；一张审批可关联同一批记录下多条重大（关键）偏差。
10. 通过不合格审批创建成功自动关闭所选偏差，跳过偏差表自身验证和批准流程；待处置的不合格审批继续冻结批记录。
11. 让步放行、作废和返工沿用受控不合格评审流程，并由处置结果控制后续操作。
12. 在线追溯保留偏差、处理、签名和审批结果；偏差随 PDF/归档导出的改造作为审核表衍生建议单列，未默认为本次必交范围。

## Non-Goals

- 偏差与具体表单、单元格、工序、订单或生产提交事件建立主关联。
- 一条偏差跨批记录关联。
- 对同一偏差创建第二份独立处理单。验证不合格后可修改原处理记录并再次验证，不另建处理轮次。
- 自动把每个参数超限告警转成偏差单。审核要求只说明强制说明或冻结，不要求自动生成偏差。
- 由偏差模块替代既有不合格评审、PQC 生产放行或上市放行流程。
- 上市放行后新增、改写或补挂偏差。
- 以 API 或数据库写入代替业务人员在正式页面完成流程。

## Functional Requirements

### FR-01 偏差发起权限

管理员通过现有用户/角色/菜单权限管理方式手动授予偏差发起权限。服务端每次发起都校验权限。未获授权人员不得通过直接调用接口绕过权限。一个用户允许被授予多个偏差角色。

### FR-02 批记录关联与生命周期门禁

发起时必须选择当前租户下存在的正式批记录。一条偏差只存一个正式批记录 ID，提交后不可改绑。上市放行完成后拒绝新增偏差，并展示明确原因；该校验与上市放行动作必须串行保护，不能靠前端缓存状态判断。

QA 可从批记录入口对关键偏差发起不合格审批，不以“已推送到 PQC 生产放行”为前提。若入口只有活跃订单身份，后端必须通过正式来源关系返回准确的批记录身份；前端不得自行把订单 ID、批号或表单 ID 当成批记录 ID。若当前生命周期尚未建立可关联批记录，需要在开发 P1 解决该正式身份的形成时机，再验收“推送前发起”；不能将推送后样本替代此场景，也不能用一个常驻错误页冒充完成。

### FR-03 编号生成

编号使用 PC-YYYYMM-0001 格式，YYYYMM 按 Asia/Shanghai 服务器日期确定。流水号按租户、年月独立递增；四位不足补零，超过 9999 后自然扩位。偏差正式提交时在同一事务中分配编号，失败回滚且不生成可见成功记录；已正式分配的号码不复用。数据库唯一约束防止并发重复。

### FR-04 发起内容

按记录表发起部分采集：

- 发现部门、发现人、发现时间、发现地点/工序。
- 产品名称及规格、涉及批号、设备/系统。
- 偏差上报日期、接收人。
- 偏差类别（可多选）：生产过程、生产过程/公用工程、检验过程、验证/确认过程、物料管理、文件记录、产品放行、其他体系偏差。
- 偏差现象详细描述，包含发生过程、异常现象、偏离标准、发现依据和初步影响。
- 现场紧急处置措施。
- 偏差等级：普通或重大（关键），以及判定依据。
- 编制人、编制日期及编制人电子签名。

发现人、接收人是人员字段；记录表没有将其标为单独签名节点。需签名的发起编制人必须使用电子签名。

### FR-05 单份处理记录

每条偏差至多一份处理记录：未开始处理时可以尚无记录，首次保存时建立，之后始终更新同一记录。常规关闭前必须完成该记录；关键偏差转不合格审批允许保留未完成或尚未建立的处理记录。处理人可录入、修改：

- 调查日期、计划完成日期、实际完成日期、调查组成员。
- 原因调查与根源分析，包含直接/根本原因及人员、设备、物料、方法、环境、测量等因素。
- 影响范围：产品、数量、批次、已放行产品流向及质量/安全/有效性影响。
- 同类偏差历史、风险评估结论。
- 产品处理措施、是否执行不合格品控制程序及评审编号。
- 整改责任人、预计完成日期。
- 是否执行纠正预防程序、CAPA 单编号和附件。
- 处理编制人、编制日期及电子签名。
- 整改验证/确认、验证结论、验证人、验证日期和电子签名。
- 偏差部门负责人、QA、质量负责人签名；重大（关键）偏差常规关闭流程还需管理者代表签名。

修改同一记录必须写入修改原因、修改前后值、操作者和服务器时间。受修改字段影响的签名必须判为失效并重新签署；不得保留看似有效但未绑定当前内容的签名。

### FR-06 常规处理及关闭

常规路径的正式关闭条件同时满足：

1. 发起编制人签名有效。
2. 唯一处理记录的调查、处置、整改与结论完整，处理结论为“闭环完成，准予归档”，处理编制人签名有效；“未闭环，持续跟踪”不能常规关闭。
3. 验证结论为整改合格，验证人签名有效。
4. 偏差部门负责人签名、QA 关闭确认和质量负责人批准均有效。
5. 重大（关键）偏差还需管理者代表批准；普通偏差不要求该节点。

QA 与质量负责人没有先后关系。QA 先签时只是保存关闭确认，仍属未处理；最后一个必要节点完成时，由服务端原子转为正式关闭。任何缺项、验证不合格或签名失效都不能常规关闭。

验证不合格时修改同一份处理记录并重新验证，不新建处理单。内容版本变化后，处理编制、验证、部门负责人、QA、质量负责人、管理者代表等对原内容的有效签名均失效；历史签名仍可查。新增一个签名不算内容修改，不能使同版其他角色签名失效。

各人签署自己的事实：处理人签调查处置正文，验证人签验证结论，部门负责人签处理结论，QA/质量/管理者签当前依据。第一次追加后续结论属于该环节正常签署，不回写正文导致前置签名失效；已签验证或部门结论发生修订时仅失效依赖它的后续签名。QA与质量两份并列批准不互相作为前置。

关闭即归入已处理。首版工程边界为关闭后只读，不提供删除、重开或改绑动作；历史修订和签名仍可查。

### FR-07 重大（关键）偏差转不合格审批

仅 QA 可在正式批记录上下文对一条或多条尚未关闭的重大（关键）偏差发起不合格审批。所选偏差必须都属于同一批记录。用户看到并操作的主体是批记录，不是活跃订单。

QA 可以对尚未关闭的一条或多条关键偏差直接发起同一批记录的不合格审批，不要求先完成偏差表自身的验证或任何批准步骤；单份调查/处理记录可未完成，也不构成该入口门槛。创建评审、QA 发起签名、批记录冻结、偏差关联和所选偏差自动关闭必须在一个事务中完成；任一步失败则全部回滚。该路径跳过偏差表自身的验证、QA关闭确认、质量负责人批准和管理者代表批准签字；不合格审批自身的签名与后续处置仍完整执行。普通偏差不能关联不合格审批。自动关闭所选偏差不等于解除批次冻结；待处置评审独立持续限制批次。

### FR-08 批次推进限制

只要关联批记录存在未关闭偏差（任一等级）或待处置不合格评审，就从服务端禁止以下四项操作：

1. 一线生产提交。
2. 一线 PQC 提交。
3. PQC 生产放行。
4. 批次执行中的上市放行。

这是“偏差未关闭限制”和“不合格评审冻结”两个独立阻断来源，不能用单一可随意清空的 frozen 标志代替。关闭一条偏差不解除其他未关闭偏差；处置一张评审也不解除其余偏差、评审或已有外部冻结。

查询、偏差处理、修改、验证、签名、QA 发起不合格审批和不合格评审处置必须继续可用，否则流程无法解除自身阻断。新偏差门禁仅加在上述四项正式写动作，不扩大到开工、所有检验操作或读取接口；原系统已有的其他安全限制仍执行。后台查询失败、正式关联缺失时返回明确错误，不能默认允许。

### FR-09 不合格审批处置

QA 或持有 PQC 生产放行处置权限的人员，按现有审批页和电子签名规则处理待审审批，可选择让步放行、作废或返工。处置结论签署并持久化后，相关批记录操作再依据该处置状态及既有业务门禁决定是否可以继续。作废批次保持作废且不能恢复生产或放行；返工必须进入受控返工路径；让步放行仅允许既有审批授权范围内的放行，不绕过其他放行前置条件。

### FR-10 列表和详情

提供全部、未处理、已处理三个 Tab，均使用 UnifiedListTemplate 和后端分页/筛选，不允许仅前端过滤伪造状态分页。每行对应一条偏差，打开后显示发起、唯一处理记录、签名状态、当前偏差状态和关联不合格审批。

“已处理”按偏差自身关闭状态分类；若其所关联审批仍待处置，详情仍醒目标示“待处置不合格审批/批次受限”。

### FR-11 批记录详情与追溯

用户要求的正式批记录/活跃表单详情增加“偏差”Tab，显示所属批记录全部偏差。历史追溯和批次详情自己的追溯抽屉提供相同数据的只读视图。每条偏差展示发起内容、唯一处理记录或尚未处理说明、电子签名、关闭方式和所关联不合格审批结果。

查询最终使用正式 batchExecutionId；当现有入口仅带 activeOrderId 时，后端按正式来源关系解析并返回批记录身份，补齐宿主传参，不要求用户手填技术 ID。正常入口必须完成这条链路；只有来源真实缺失、歧义或错误时才显示上下文错误。

工程上用显式展示位置与只读属性控制共享组件，不能仅由 FORMAL_BATCH_SOURCE_DETAIL 自动开启写操作。历史追溯内嵌的正式表单不再重复插入主偏差 Tab；普通订单/PQC/NCR详情不因复用组件自动新增偏差入口。缺少查询权限显示无权查看；查询成功且为空显示“没有偏差”；请求失败显示错误，三者不能混淆。

### FR-12 归档与只读

本次必交为在线批记录追溯可查看完整偏差、处理、签名、不合格评审及处置结果，上市放行后不能新增或改写关联资料。

审核表 C40 的完整电子副本要求提示未来还需将偏差纳入 PDF/归档导出；是否本次同时修改导出尚未获明确范围决定，因此记为候选扩展，不作为本次功能验收通过的必要条件，也不宣称本模块单独满足整张审核表。若另行纳入，须同时设计归档快照、签名显示和导出测试。

## Business Rules

| Rule ID | 规则 |
| --- | --- |
| BR-01 | 只有两档：普通偏差、重大（关键）偏差；“重大”和“关键”同义。 |
| BR-02 | 一条偏差只属于一份正式批记录；一份批记录可有多条偏差。 |
| BR-03 | 编号按租户和上海时区年月分段递增、唯一、不可回收。 |
| BR-04 | 常规关闭须满足 FR-06 全部签名：发起编制、处理编制、验证合格、部门负责人、QA、质量负责人；关键等级加管理者代表。QA 与质量负责人不分先后。 |
| BR-05 | 关键偏差转不合格评审时由 QA 明确发起；成功时自动关闭选中的偏差，绕过偏差表自身验证/批准；评审继续承担批次阻断。 |
| BR-06 | 同一张不合格评审可关联同一批记录的多条关键偏差；不允许关联普通偏差或其他批次偏差。 |
| BR-07 | 未关闭偏差和待处置不合格评审都阻止四项指定动作。 |
| BR-08 | 上市放行后拒绝新增偏差。 |
| BR-09 | 同一处理记录允许修改；修改须审计并使受影响的签名失效；不能静默覆盖签名事实。 |
| BR-10 | 同一账号可以承担多个偏差角色；每个签名节点仍记录独立意图、身份验证和被签内容。 |

## States and Transitions

### 偏差常规路径

正式提交并签署 → OPEN（待处理）→ 原处理记录填写/修订 → 验证合格并收集 FR-06 全部签名 → CLOSED，closeReason=NORMAL_COMPLETED（常规闭环）。验证不合格时仍 OPEN，修改同一记录再验证。

首版不提供发起草稿持久化。处理内容可保存未完成状态，但保存不等于签署或关闭。编号只在正式提交事务分配。

### 关键偏差不合格审批路径

已发起且未关闭的关键偏差 → QA 选择同批一条或多条偏差并发起审批 → 审批创建成功、偏差自动关闭并关联评审，同时评审状态待处置且批次继续冻结 → 评审完成处置 → 按让步放行、返工或作废的正式状态控制后续操作。

### 列表分类

- 全部：当前租户有权查看的所有正式偏差；本模块不提供删除正式偏差的功能。
- 未处理：偏差自身状态尚未关闭。
- 已处理：偏差自身状态已关闭。若审批仍待处置，则额外标记审批待处置，不能误示为批次可继续。

## BDD Scenarios

- BDD: 授权用户发起普通偏差 -> Given 用户具备偏差发起权限且目标批记录未上市放行, When 用户完成发起字段和电子签名后提交, Then 系统生成唯一编号并在未处理列表显示该偏差。
- BDD: 关键偏差进入不合格评审 -> Given QA 选择同一批记录下的一条或多条未关闭关键偏差, When QA 签名发起不合格审批, Then 系统在一个事务内关联评审、自动关闭所选偏差并保持批记录冻结。
- BDD: 未关闭偏差限制批次推进 -> Given 批记录关联未关闭偏差, When 用户执行一线生产提交、一线 PQC 提交、PQC 生产放行或上市放行, Then 后端拒绝对应动作并指出阻断偏差。
- BDD: 追溯区分无偏差和查询错误 -> Given 正式批记录查询正常返回空集合或返回服务失败, When 用户打开偏差 Tab, Then 空集合显示“没有偏差”且失败显示错误。

## Edge Cases

- 两个用户并发创建偏差：同租户同月份流水号不重复，不吞唯一键冲突后伪报成功。
- 批记录已完成上市放行：明确拒绝新增。
- 偏差只关联到其他租户批记录：明确拒绝且零写入。
- 多条已选关键偏差中有任一条属于另一批记录、已关闭或等级不符：整体拒绝，不能部分自动关闭。
- 创建不合格审批、写签名、链接偏差或冻结批次的任一步失败：事务整体回滚。
- 活跃表单详情无偏差：显示“没有偏差”；加载失败：显示错误。
- 偏差已关闭但不合格评审待处置：列表为已处理，同时仍显示冻结状态。
- 批次同时存在其他未关闭偏差：某个不合格评审处置完成后仍不得解除其他偏差带来的限制。
- 已签字段被修改：审计留痕并重新签署；签名图片或姓名显示不得替代服务端授权/身份验证。

## Open Questions

已确认的主流程无待用户重复确认项。以下首版工程取舍与新业务请求分开：

- 同批已有待处置不合格评审时，保留现有“一批一个待审评审”的规则，不静默追加已签关联集合，也不新建第二张；返回既有评审编号，未关联偏差保持开放。当前评审可正常处置，之后仍开放的关键偏差可再发起下一张。用户确认的“一张评审关联多条关键偏差”通过创建时多选实现。
- 关闭后只读，不增加正式更正/重开流程；后续需要时另定审计和重签规则。
- PDF/归档导出改造、参数超限自动发单和跨系统出库联锁未纳入本次明确开发范围；在线追溯和指定四项拦截必须完成。
