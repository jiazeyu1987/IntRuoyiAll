# 四项修复的主流程验收顺序

状态：prepared，未执行真实页面验收。依据 HTML v1.6，先完成主链，再补受影响细节。

1. 在真实后台配置中核对正式启用审核人。通过产品目录页面新建任务自有项目和产品，填写正常业务编码、负责人、文件夹模板及三组默认属性，提交审核并批准。核对选定负责人能进入新项目；不复用已知错误租户的旧测试项目。
2. 从项目目录或上传页选择刚批准的项目及其项目文件夹，核对产品实际编码、名称和默认属性。独立选择正式文件类型及真实原件；该原件可以不在项目文件模板中。正常新上传全程只选一个项目文件夹，不出现额外 NAS 存储目录选择。
3. 修改本次申请属性，填写初始版本、编号和预设生效日期，核对实际会签部门及批准人，先取消提交确认再重新确认。核对取消保留资料、确认后进入真实会签，文件项目位置与内部存储映射一致，默认属性未被本次修改反写。
4. 主流程按会签、批准、必要培训、文控审核、受控、下发核对；本批不改变已经确认的生命周期、签名、文件负责人及生效后旧版作废规则。未选培训不产生培训节点；需要培训时由文控上传本次线下培训文件。
5. 对另一个任务自有项目申请，分别核对冻结审核人待办及审核通过后的批准待办，从现有统一审批中心打开准确申请。审核或批准驳回后，原申请人从实际站内信打开原申请、修改后重提；旧申请决定和属性保留，新申请重新进入审核。

上述动作全部由 Playwright 在真实前端页面完成。SQL 或 API 仅只读核对项目产品来源、正式 OWNER、映射位置、文件状态、消息及申请历史；不能创建业务记录、代办审批或伪造签名。登录、界面加载或离线测试不单独视为主流程 PASS。

验收前置：实际库须执行经主管理审核及具体授权的新增结构/模板迁移；最新统一源码须完成定向验证、类型、前端构建及后端源码包核对。使用唯一 `int_qms` 本机槽位 0，前端 8061、后端 48061，启动前核对端口和归属，不影响 48081 或其他任务服务。

尚未执行的细节单列：多用户权限候选边界、历史缺失位置、模板配置冲突处置等。发生主流程失败先定位具体正式来源或事务边界，不用猜值、绕过门禁或重复提交掩盖失败。
